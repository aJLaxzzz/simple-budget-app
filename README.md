# Личный бюджет

> Материалы проверки: отчёт сохранён; прежние PNG, ZIP и журналы вынесены из репозитория. [Архив и восстановление](docs/reviews/README.md). Указанные ниже результаты относятся к датам исходных проверок.


Веб-приложение для ведения месячного бюджета: доходы и расходы по категориям, аналитика по месяцу и за год, диаграммы. Запускается локально, данные хранятся у тебя на диске.

- **Бэкенд:** Go  
- **Фронт:** HTML, CSS, JavaScript (без npm)  
- **Данные:** `data.json` (все месяцы и операции), `categories.json` (категории), `planner.db` (планировщик)

Текущее состояние планировщика, результаты проверок и ограничения: **[приёмка этапа 14](STAGE14-ACCEPTANCE.md)**. Последующие разделы по этапам описывают развитие API; актуальные дополнения находятся в отчёте приёмки.

Актуальное упрощение интерфейса: **[UX 2.0 — этап 1](UX2-STAGE1.md)** — четыре основных раздела, старт с календаря, быстрый ввод и группировка задач. Старые ссылки сохранены.

## Как пользоваться

Сначала собери актуальную версию командой `go build -o budget .` из папки проекта (нужен Go версии, указанной в `go.mod`). Затем запусти `start-budget.command` двойным кликом или выполни `./budget` из папки проекта. Скрипт откроет браузер; если приложение уже запущено на выбранном адресе, откроет ещё одну вкладку. Данные сохраняются при каждой успешной операции. Закрытие и обновление вкладок не выключают сервер.

Для остановки нажми **Ctrl+C в терминале запуска**. Процесс также принимает **SIGTERM**: `kill -TERM <PID>` для известного PID именно этого приложения. Сервер прекращает принимать подключения и до 35 секунд ожидает текущие запросы. HTTP-команды остановки нет; старые вкладки с вызовом `/api/shutdown` не могут завершить новый сервер.

## Возможности

- **Главная** — список месяцев по годам (вкладки), автосоздание нового месяца по московскому времени, удаление месяца.
- **Страница месяца** — доходы/расходы по дням и категориям, диаграммы, остаток за месяц.
- **Аналитика за год** — сводка по году, остаток по месяцам, накоплено за год, диаграммы по категориям и месяцам.
- **Категории** — настройка категорий расходов и доходов прямо в приложении (без правки кода).
- **Бэкап** — кнопка «Скачать бэкап» в шапке: скачивается файл с данными. На новом компе или в новом клоне проекта положи файл в папку — данные подхватятся.
- **Поиск** — по описанию, категории, сумме по всем месяцам.

## Требования

- [Go](https://go.dev/) 1.24+ (SQLite-драйвер закреплён в `go.mod`; CGO не требуется)

## Запуск из терминала

```bash
git clone https://github.com/aJLaxzzz/simple-budget-app.git
cd simple-budget-app
go build -o budget .
./budget
```

Открой **http://127.0.0.1:3001** или **http://localhost:3001**. По умолчанию сервер слушает только `127.0.0.1:3001`.

## Иконка в Dock или в «Программы» (Mac)

После сборки выполни `chmod +x start-budget.command`. Файл можно запускать двойным кликом и закрепить в Dock. Окно Терминала остаётся открытым для журнала и остановки через Ctrl+C.

Для запуска через Automator создай программу с действием «Запустить оболочный сценарий»:

```bash
exec /ПУТЬ/К/ПАПКЕ/simple-budget-app/start-budget.command
```

Укажи свой путь, заключив его в кавычки, если есть пробелы. При таком запуске остановить сервер можно командой `kill -TERM <PID>`. Закрытие браузера его не останавливает. Рекомендуемый локальный вариант с доступной кнопкой Ctrl+C — запуск `.command` через Терминал.

## Настройки запуска и контроль доступа

Все настройки задаются переменными окружения; `.env` автоматически не читается.

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `BUDGET_ADDR` | `127.0.0.1:3001`; IP и порт, например `127.0.0.1:3100` или `[::1]:3001`. `localhost` нормализуется в `127.0.0.1` |
| `BUDGET_DATA_DIR` | Текущая рабочая директория; существующий каталог с `data.json` и `categories.json` |
| `BUDGET_STATIC_DIR` | `static` относительно рабочей директории; обязательные файлы интерфейса |
| `BUDGET_PASSWORD` | Не задан; общий пароль длиной от 32 символов для HTTP Basic, пользователь `budget` |
| `BUDGET_TLS_CERT` / `BUDGET_TLS_KEY` | Не заданы; пути к сертификату и закрытому ключу PEM |
| `BUDGET_ALLOWED_HOSTS` | Точный адрес прослушивания и, для loopback, `localhost:порт`; можно задать список Host через запятую, например `localhost:3100,127.0.0.1:3100` |

Пример настройки локального порта и каталога данных:

```bash
BUDGET_ADDR=127.0.0.1:3100 BUDGET_DATA_DIR="/абсолютный/путь/к/данным" ./budget
```

Каталог данных должен уже существовать. Приложение не копирует, не перемещает и не мигрирует JSON. При запуске `.command` рабочая директория — папка проекта. Для запуска бинарника из другой папки укажи абсолютные пути к данным и `static` явно. Не запускай несколько процессов с общим каталогом данных.

**Локальный режим:** доступ разрешён только loopback-клиентам с разрешённым Host. Это доверие локальным процессам Mac, а не персональная авторизация пользователя ОС. Для дополнительного пароля можно задать `BUDGET_PASSWORD` и на loopback.

**Внешний адрес:** изменение одного `BUDGET_ADDR` недостаточно — приложение откажется запускаться без общего пароля и TLS-сертификата/ключа. Для `0.0.0.0` или `[::]` также обязателен явный `BUDGET_ALLOWED_HOSTS`. Wildcard в списке Host запрещён; указывай адрес именно в том виде, как его отправляет браузер, включая нестандартный порт. Сертификат должен соответствовать этому адресу и быть доверенным клиентом. Tailscale, прокси и развёртывание здесь не настраиваются.

При включённом пароле браузер показывает стандартный запрос логина: `budget` и заданный пароль. Проверка выполняется сервером до маршрутизации для **всех** API и файлов интерфейса, включая финансовый экспорт. Пароль не передаётся в URL и не записывается приложением на диск. Используй случайный секрет, передавай его через окружение; не помещай его в Git, `.command` или команды, сохраняемые в истории оболочки. Ключи и сертификаты храни за пределами репозитория. Для смены пароля нужен перезапуск; полноценной системы пользователей и сеансов нет.

Дополнительно проверяются Origin и `Sec-Fetch-Site`; изменяющие запросы принимаются только с `Content-Type: application/json`. Сторонним сайтам не выдаются CORS-разрешения. Заголовки `X-Forwarded-*` не используются для обхода проверки адреса клиента или HTTPS.

Статика раздаётся по явному списку `publicAssets` в `static.go`: HTML, стили бюджета и планировщика, основные JS-файлы и модули `js/planner/`. Списков директорий и fallback на рабочий каталог нет. JSON, БД, бэкапы, конфигурации и другие файлы не публикуются даже при случайном размещении внутри `static`. Символические ссылки на месте ресурсов запрещены. Ресурсы читаются в память при старте; после изменения frontend перезапусти сервер. При отсутствии каталога или обязательного ресурса сервер завершает запуск с ошибкой.

## Бэкап и перенос данных

В шапке приложения кнопка **«Скачать бэкап»** — скачивается файл с текущим содержимым `data.json`.

**Восстановление на другом компе или в новом клоне:**

1. Скопируй скачанный файл в папку проекта.
2. Переименуй его в **`data.json`** (или замени им существующий `data.json`).
3. Запусти приложение — все месяцы и операции отобразятся.

При желании можно так же сохранить и подставить **`categories.json`** (категории расходов/доходов).

## Надёжность хранения и проверка изменений

Финансовые данные сохраняются после каждой успешной операции API. Запись идёт во временный файл рядом с исходным, затем файл синхронизируется и атомарно заменяет исходный. При ошибке до замены сервер возвращает HTTP 500 и откатывает изменение в памяти; интерфейс показывает ошибку и сохраняет открытую форму. Новые файлы имеют права `0600`, для существующих сохраняются прежние права.

Отсутствующий JSON означает новое хранилище в памяти; файл появляется при первом успешном изменении. Пустой, повреждённый, недоступный или неподдерживаемый JSON останавливает запуск с сообщением об ошибке, без перезаписи файла. Неизвестные поля также отклоняются, чтобы не потерять их при последующем сохранении. Старое поле `income`, отсутствие списка `incomes` и старый массив категорий поддерживаются. Чтение старых форматов не переписывает файлы; обычное редактирование сохраняет поддерживаемый текущий формат.

API-запросы к финансовым данным выполняются под общей блокировкой. Это защищает один процесс сервера; одновременная работа нескольких процессов с теми же JSON и внешнее редактирование файлов во время работы не поддерживаются. При потере ответа сети результат записи может быть неизвестен: сначала обнови данные, затем решай, повторять ли операцию.

После атомарной замены выполняется синхронизация каталога. Если она не удалась, запись уже применена: сервер оставляет новое состояние и пишет предупреждение в журнал. Полную устойчивость к отключению питания следует проверять отдельно на целевой файловой системе. Резервные копии по-прежнему нужны; существующий экспорт содержит только финансовый `data.json`.

Автоматические проверки (Go, Node.js с поддержкой `node:test`; для браузерных тестов нужен Playwright из `package-lock.json`):

```bash
go test ./...
go test -race ./...
go vet ./...
node --test tests/*.test.cjs
node --check static/js/app.js
```

Go-тесты используют собственные временные каталоги и синтетические данные, не изменяют пользовательские JSON. Интеграционные тесты открывают временные loopback-порты и запускают отдельные тестовые процессы для проверки SIGINT/SIGTERM. Проверяются финансовые операции, аналитика, поиск, бэкап, старые форматы, ошибки чтения/записи, откат памяти и параллельные запросы. Проверяются также права доступа, безопасная статика и корректное завершение текущих запросов. JS-тесты проверяют ответы API, отсутствие ложного успеха и отсутствие запросов остановки при выгрузке страницы.

## Хранилище планировщика (инфраструктура)

При запуске сервер открывает `planner.db` в `BUDGET_DATA_DIR` (по умолчанию папка проекта). Финансовые `data.json` и `categories.json` остаются отдельными файлами, миграции SQLite их не читают и не меняют. Backend API проектов и задач подключён к существующей защите сервера. API рабочих сессий также подключён к защите сервера. Интерфейс проектов, задач, входящих и рабочих сессий доступен в разделе «Планы». Повторения, шаблоны, очередь внимания и импорт производственного календаря реализованы; актуальная приёмка описана в `STAGE14-ACCEPTANCE.md`.

Используется `database/sql` и `modernc.org/sqlite v1.39.1`. Настройки соединения: `foreign_keys=ON`, `busy_timeout=5000`, `journal_mode=WAL`, `synchronous=FULL`, `trusted_schema=OFF`. Один SQL connection и блокировка Store последовательно выполняют операции; составные изменения проходят через `Store.Transaction`. Callback транзакции не должен вызывать другие методы Store или самостоятельно завершать транзакцию. Новые файлы БД и снимки создаются с правами `0600`.

Один процесс приложения владеет одной базой: неблокирующий OS flock на `planner.db.lock` удерживается до закрытия БД. Повторный процесс получает понятную ошибку. Файл `.lock` остаётся после остановки, но OS-блокировка освобождается при закрытии или аварийном завершении; удалять его вручную во время работы нельзя. Символьные ссылки на файл БД и hardlink не поддерживаются. Политика рассчитана на локальную файловую систему macOS/Linux; сетевые файловые системы и сторонние инструменты, игнорирующие блокировку приложения, не поддерживаются. Сервер закрывает Store после завершения HTTP-запросов.

SQL-миграции встроены из `internal/planner/migrations`. Весь набор новых миграций и запись их контрольных сумм выполняются одной транзакцией. Уже применённые SQL-файлы нельзя редактировать: добавляй следующую миграцию. Проверяются `application_id`, `user_version` и журнал миграций; более новая, неизвестная или изменённая версия отклоняется. Неизвестную БД приложение не переинициализирует.

Таблицы: проекты, задачи, сессии, серии, версии правил, экземпляры, паузы, шаблоны и версии шаблонов, история, состояние внимания, настройки, годы и дни производственного календаря. Версии шаблонов, правил и события истории защищены от UPDATE. У изменяемых сущностей есть `revision` и timestamps; проверку ожидаемой revision и запись событий выполняет сервис проектов и задач. SQL-триггеры запрещают циклы, третий уровень задач и несогласованный проект родителя/ребёнка. Перенос проекта родительской задачи распространяется на её детей одной транзакцией. Связи с историей не удаляются каскадно.

Планировщик использует civil dates `YYYY-MM-DD`, локальное время `HH:MM` и настройку `Europe/Moscow`. Моменты событий сохраняются отдельно в UTC. `overdue` не хранится как конечный статус. Правила повторений пока представлены версионированными JSON-снимками; их бизнес-валидация и расчёт дат относятся к следующему этапу.

### Производственный календарь

Интерфейс `Calendar.IsWorkingDay` различает `Weekdays` (пн–пт) и `RussianProductionCalendar`. Во втором режиме отсутствие данных возвращает `ErrCalendarUnavailable` с годом. Автоматического перехода на пн–пт нет.

`Store.ImportCalendarYear` атомарно принимает полный год (365/366 дат), источник и классификацию дней: рабочий, нерабочий, сокращённый. Сохраняются причины, источник, контрольная сумма входных данных и revision года. Это интерфейс для будущего импорта проверенных официальных данных, а не проверка подлинности источника. Загрузка из сети не реализована; праздники не зашиты и не генерируются. Тестовые календари явно синтетические и не включаются в пользовательскую базу.

### Снимки и восстановление

В Go-интерфейсе доступны `Store.Export(ctx, path)` и `Store.Restore(ctx, path)`. HTTP-маршрутов, кнопок и объединённого архива пока нет. Экспорт требует нового пути с расширением `.sqlite` или `.db`; существующие файлы не заменяет.

Экспорт использует `VACUUM INTO`, затем проверяет `integrity_check`, `foreign_key_check`, версию и журнал миграций. Рабочий SQLite-файл при активном WAL напрямую не копируется. На время снимка операции этого Store ожидают окончания экспорта. После успешной проверки снимок публикуется атомарно.

Восстановление принимает самостоятельный снимок, создаёт приватную временную копию, проверяет её и сравнивает фактическую схему с текущей. Затем заменяет строки только известных таблиц одной транзакцией с проверкой связей. SQL-схема из снимка не выполняется. Ошибка валидации, вставки или commit оставляет прежние данные. Поддерживаются снимки текущей версии схемы; конвертация старых снимков пока не реализована. Для проверки и восстановления нужно свободное место под снимок и журнал транзакции. Файлы `.db`, `.sqlite`, WAL/SHM и блокировки исключены из Git.

## Backend API проектов и задач

Все маршруты ниже находятся под `/api/planner` и используют тот же контроль доступа, что и финансовый API. JSON имеет имена полей в `snake_case`. Создание возвращает `201` и `Location`, чтение/изменения — `200`.

С этапа 14 создание проектов, задач и сессий поддерживает необязательный `request_id`. Интерфейс всегда передаёт его: точный повтор после потери ответа возвращает созданный объект без дубля; другой payload с тем же ключом даёт HTTP 409. Изменения по-прежнему требуют `expected_revision`.

| Метод и маршрут | Действие |
|---|---|
| `POST /projects` | Создать проект; достаточно `title` |
| `GET /projects?status=planned&archived=false` | Список с прогрессом; архивные по умолчанию скрыты |
| `GET /projects/{id}` | Проект, все его задачи и прогресс |
| `PATCH /projects/{id}` | Название, описание, статус, `start_date`, `due_date` |
| `POST /projects/{id}/complete` | Завершить проект |
| `POST /projects/{id}/cancel` | Отменить проект |
| `POST /projects/{id}/archive` | Архивировать без удаления истории и задач |
| `POST /tasks` | Создать задачу; обязательное поле `title` |
| `GET /tasks?status=planned&project_id=…` | Список задач; `project_id=` выбирает задачи без проекта |
| `GET /tasks/{id}` | Задача и состояние её открытых подзадач |
| `PATCH /tasks/{id}` | Название, описание, приоритет, статус, даты, время, проект, родитель |
| `POST /tasks/{id}/complete` | Завершить с явно указанной фактической датой |
| `POST /tasks/{id}/reschedule` | Изменить `planned_date` и, при необходимости, `scheduled_time`; дедлайн не меняется |
| `POST /tasks/{id}/cancel` | Отменить |
| `POST /tasks/{id}/restore` | Восстановить завершённую/отменённую задачу в `planned` |
| `GET /history?object_type=task&object_id=…&limit=50&offset=0` | История задачи или проекта; `limit` 1–100 |

Входные статусы: `planned`, `in_progress`, `completed`, `cancelled`; приоритеты: `low`, `normal`, `high`. На создании доступны только `planned` и `in_progress`. Между открытыми статусами можно переходить; из открытого — завершить или отменить. Закрытую задачу сначала восстанавливают отдельным действием. Восстановление проекта и удаление объектов на этом этапе не предусмотрены.

В PATCH отсутствие поля сохраняет прежнее значение. `null` очищает необязательную дату, время или связь. Для подзадачи нужны `project_id` и `parent_task_id` корневой задачи того же проекта. Корень с подзадачами нельзя переместить во входящие: сначала нужно явно изменить структуру. Создание и редактирование задач в архивированном проекте запрещены; задача может быть перемещена из архива в доступный проект. Даты — `YYYY-MM-DD`, время — `HH:MM` и только при наличии плановой даты.

Каждое изменение требует `expected_revision`. Для перемещения корня нужны актуальные версии всех детей в `related_revisions`; для завершения родителя с открытыми детьми — версии всех открытых детей. Служебные поля (`revision`, timestamps, история, ID) клиент записывать не может. При конфликте возвращается `409` с `error.current`, содержащим ID и актуальную revision конфликтующей записи. Изменения и история откатываются целиком, если конфликтует любой участник.

Пример завершения родителя с сохранением открытых подзадач:

```json
{
  "expected_revision": 3,
  "completed_date": "2026-11-10",
  "children_decision": "keep_open",
  "related_revisions": {"child-id": 2}
}
```

`completed_date` обязательна при любом переходе задачи в `completed`, в том числе через PATCH; дата в будущем по московскому времени запрещена. `completed_at` — точный UTC-момент внесения завершения, а не подстановка в фактическую дату. `children_decision=complete` завершает открытых детей той же фактической датой. `keep_open` оставляет их статусы прежними: завершённый родитель с открытыми детьми допустим и возвращает `completed_with_open_children=true`, `open_children=N`. Завершение всех детей не меняет родителя автоматически. Восстановление очищает текущие поля завершения, но прежняя дата остаётся в событии истории.

Завершение и отмена проекта меняют только проект. Задачи не закрываются молча; `progress.open_tasks` показывает количество открытых записей дерева. `total`, `completed` и процент считаются только по листьям; отменённые листья исключены из знаменателя и показаны в `cancelled`. Исторические `skipped` также исключены и показаны отдельно. При нулевом знаменателе процент равен 0. Архивирование — отдельная отметка `archived_at`, не новый статус.

События истории содержат `action`, `object_type`, `object_id`, `actor=owner`, UTC-время, `operation_id` и `changes` с прежними/новыми значениями. Изменение нескольких полей одним запросом записывает одно основное событие со всеми изменёнными полями; перенос/завершение детей добавляет их события с тем же `operation_id`. История и данные сохраняются одной транзакцией. История выдаётся от новых событий к старым; offset-пагинация при одновременных вставках не является фиксированным снимком.

Единый формат ошибок:

```json
{"error":{"code":"revision_conflict","message":"…","current":{"id":"…","revision":4,"created_at":"…","updated_at":"…"}}}
```

Коды: `400` — некорректный JSON, неизвестные/служебные поля; `401/403` — отказ доступа; `404` — отсутствующий объект; `405` — неподдерживаемый метод; `409` — конфликт revision; `422` — недопустимые значения или переходы; `500` — внутренняя ошибка. Тело запроса ограничено 128 KiB. Списки проектов и задач пока без пагинации; история поддерживает `limit/offset`.

Схема обновляется миграцией `002_project_archive.sql`; `001_initial.sql` не изменена. Снимки старой версии схемы требуют отдельного обновления перед восстановлением текущей версией приложения.

## Backend API рабочих сессий

Сессия принадлежит существующей задаче или подзадаче и имеет свою дату. Завершение сессии не завершает задачу, перенос не меняет `planned_date` и `due_date` задачи. Пересечения сессий разрешены.

| Метод и маршрут | Действие |
|---|---|
| `POST /api/planner/sessions` | Создание: обязательны `task_id` и `date` |
| `GET /api/planner/sessions?task_id=…&status=planned` | Список, фильтры необязательны |
| `GET /api/planner/sessions/{id}` | Получить сессию |
| `PATCH /api/planner/sessions/{id}` | Изменить `date`, `start_time`, `end_time`, `timezone` |
| `POST /api/planner/sessions/{id}/reschedule` | Перенести: обязательна новая `date`, время можно изменить отдельно |
| `POST /api/planner/sessions/{id}/complete` | Завершить с обязательной `completed_date` |
| `POST /api/planner/sessions/{id}/cancel` | Отменить |
| `POST /api/planner/sessions/{id}/restore` | Восстановить в `planned` |
| `GET /api/planner/history?object_type=session&object_id=…` | История с обычными `limit` и `offset` |

У каждой сессии есть `revision`, `created_at`, `updated_at`; любое изменение требует `expected_revision`. Методы действий принимают только поля соответствующего действия, изменение служебных полей и `task_id` запрещено. Ошибки используют тот же JSON-формат и коды, что и API задач.

API создаёт только `planned`; доступны переходы `planned → completed/cancelled` и явное восстановление закрытых сессий. Закрытые сессии нельзя редактировать, переносить или повторно закрывать до восстановления. Старый внутренний статус `in_progress` из схемы 001 учитывается как активный, но через новый API не назначается.

Дата имеет формат `YYYY-MM-DD`. Время либо полностью отсутствует, либо заданы обе границы `HH:MM`, причём окончание строго позже начала в пределах одного дня. PATCH с `start_time: null, end_time: null` убирает интервал. Единственный поддерживаемый timezone — `Europe/Moscow`; по умолчанию используется он. Смена часового пояса устройства ничего не меняет.

`completed_date` — фактический календарный день выполнения; `completed_at` — UTC-момент внесения завершения. Будущая фактическая дата по Москве запрещена. Восстановление очищает текущие поля завершения, сохраняя их прежние значения в истории.

### Закрытие задач с активными сессиями

Завершение или отмена задачи с активными сессиями требует `sessions_decision: "cancel"` и актуальные версии **всех** затрагиваемых сессий в `session_revisions`. Это относится и к PATCH статуса. При отсутствии решения API возвращает `422`, код `sessions_decision_required`, и список сессий с версиями в `error.current`. Несовпадение версии даёт `409`; вся операция откатывается.

```json
{
  "expected_revision": 3,
  "completed_date": "2026-11-10",
  "children_decision": "complete",
  "related_revisions": {"child-id": 2},
  "sessions_decision": "cancel",
  "session_revisions": {"root-session-id": 1, "child-session-id": 4}
}
```

В модель не добавлен статус `skipped`, поэтому решение «сохранить пропущенными» сейчас недоступно. Все отменённые сессии остаются в базе и истории. Отменяются не только будущие, но и прошедшие активные сессии: у закрытой задачи не остаётся активной работы. Завершённые и ранее отменённые сессии сохраняются без изменений.

При `children_decision=complete` проверяются и отменяются активные сессии всех завершаемых детей. При `keep_open` дети и их сессии остаются открытыми. Отмена задачи по-прежнему не отменяет подзадачи автоматически. Восстановление задачи не восстанавливает её сессии; каждую сессию восстанавливают явно. Создать или восстановить активную сессию у закрытой задачи нельзя — сначала нужно восстановить задачу.

Все изменения задач, сессий и их истории выполняются одной транзакцией с общим `operation_id`. При ошибке любого события истории откатывается вся операция. Миграция `003_session_completion.sql` добавляет фактическую дату и проверку парных границ времени; миграции 001 и 002 не изменены. Старые записи не переписываются: если ранее вручную была создана сессия с одной границей времени, её нужно исправить явным редактированием перед дальнейшими действиями.

## Интерфейс планировщика (этап 7)

Откройте «Планы» в верхнем меню. Раздел работает на существующем Go-сервере, дополнительных команд запуска или сборки frontend не требуется.

- `#/plans/inbox` — входящие: задачи без проекта и плановой даты. Быстрый ввод требует только названия. После назначения проекта или даты задача остаётся в системе и исчезает из входящих. Завершённые и отменённые записи доступны через фильтр статуса.
- `#/plans/projects` — карточки проектов, фильтр статуса и архив. Карточка показывает прогресс, рассчитанный backend по конечным задачам; отменённые элементы учитываются отдельно. Страница проекта показывает дерево задач и позволяет добавлять подзадачи, изменять, завершать, отменять и архивировать проект.
- `#/plans/tasks` — задачи с поиском, фильтрами проекта и статуса. Подзадача выводится один раз; если родитель скрыт фильтром, отображается его название.
- Редактор задачи открывается справа, на узком экране — во всю ширину. В нём доступны поля задачи, подзадачи, рабочие сессии и история с загрузкой по 10 событий. Escape закрывает редактор; hash сохраняет открытый раздел и задачу, работают переходы браузера назад/вперёд. Фильтры задач сохраняются в URL.

Завершение требует фактическую дату (предлагается сегодняшний день в `Europe/Moscow`), отдельное решение по открытым подзадачам и согласие на отмену затрагиваемых активных сессий. Интерфейс передаёт `expected_revision`, `related_revisions`, `sessions_decision` и `session_revisions`; успех показывается только после ответа сервера. Завершение проекта по текущему контракту не завершает его задачи. Архивирование необратимо через текущий API — интерфейс предупреждает об этом перед действием.

При HTTP 409 черновик остаётся в форме. Сначала нужно загрузить и просмотреть актуальную версию, затем явно принять её для повторного сохранения либо заменить черновик серверными данными. При повторном применении сохраняются изменения другого клиента в полях, которые локально не редактировались. Ошибки сети и сохранения не очищают форму. Черновики задач и проектов сохраняются при переходах внутри открытой страницы, но не записываются на диск и не переживают полную перезагрузку браузера. Пока идёт запрос, повторная отправка формы заблокирована; после обрыва связи результат создания следует проверить перед повторением запроса.

Новые ресурсы перечислены в `publicAssets` (`static.go`). Пользовательские строки в модуле планировщика выводятся через DOM API и `textContent`, без вставки HTML. Открытие «Планов» не вызывает финансовые API и не создаёт бюджетный месяц. Backend и SQLite-схема на этом этапе не меняются.

### Модули и проверки frontend

- `static/js/planner/core.js`: безопасные DOM-компоненты, запросы, даты по Москве, маршруты, формы и обработка конфликтов.
- `static/js/planner/views.js`: входящие, задачи, проекты, дерево и загрузка представлений.
- `static/js/planner/editor.js`: редакторы, подтверждения, сессии и история.
- `static/css/planner.css`: стили, ограниченные разделом планировщика, боковая панель и адаптация к узкому окну.

Для unit-тестов достаточно Node.js; Playwright нужен только для тестов, не для работы приложения:

```bash
npm ci
npm test
npm run test:browser
```

Браузерные тесты по умолчанию используют установленный Google Chrome. Альтернатива: `npx playwright install chromium`, затем `PLAYWRIGHT_CHANNEL=chromium npm run test:browser`. Тестовый сервер собирается автоматически, слушает `127.0.0.1:31371` и получает **новый временный каталог** с искусственными финансовыми JSON и SQLite. Существующий сервер на этом порту не переиспользуется. После тестов сервер останавливается; временные данные остаются для диагностики, снимки интерфейса и трассы ошибок — в игнорируемом Git каталоге `test-results/`. Проверяется побайтовая неизменность тестовых финансовых JSON. Пользовательские данные из каталога проекта не используются.

Проверки покрывают навигацию, создание задач и подзадач, дерево и прогресс, перенос между проектами, завершение с детьми и сессиями, отмену/восстановление, конфликт версий, сетевые ошибки, XSS, историю, архив и компоновку 1440/390 px. Браузер запускается с часовым поясом устройства `America/Los_Angeles`, чтобы отдельно проверить независимость московских дат.

Списки задач и проектов пока загружаются целиком: пагинации этих списков в текущем API нет. Календарь, повторения, шаблоны, PWA и объединённый архив на этом этапе не добавлялись.

## Календарь планировщика (этап 8)

В «Планах» появился раздел «Календарь» (`#/plans/calendar`). На широком экране первый вход открывает месяц, на ширине до 700 px — неделю. Режим, выбранный день и фильтры сохраняются в hash; ссылка раздела помнит последний выбор в пределах вкладки через `sessionStorage` (при недоступном хранилище — в памяти страницы).

- **Месяц:** понедельник–воскресенье, 4–6 недель, названия и до трёх событий в ячейке, «Ещё N» открывает полный день. На узком экране месячная сетка компактная, с индикаторами событий; подробности открываются нажатием на день.
- **Неделя:** на десктопе семь колонок, отдельная строка без времени и прокручиваемая сетка суток. На телефоне — недельная лента и только расписание выбранного дня. Фильтры на телефоне свёрнуты, чтобы освободить место для задач.
- **День:** все события выбранной даты, рабочие сессии и задачи без времени. Пересечения раскладываются по соседним колонкам. У задачи нет длительности: размер её блока — только способ отображения, не новый интервал работы.

Нажатие на название открывает существующий редактор. Меню `⋯` позволяет перейти к проекту, выполнить задачу/сессию или перенести её. Дедлайн и отдельная плановая дата обозначены как индикаторы: кнопки самостоятельного выполнения у них нет. Задачу можно выполнить из её редактора. Завершение использует прежние диалоги фактической даты, выбора по подзадачам и отмены активных сессий.

На десктопе перенос также работает перетаскиванием на дату или час. При переносе сессии на час сохраняется её интервал; если он выходит за границу дня, форма оставляет прежнее время и предлагает исправить его вручную. Перенос в секцию «Без времени» очищает время. Изменение плановой даты не меняет дедлайн, изменение сессии не меняет задачу. Используются существующие `POST /tasks/{id}/reschedule` и `POST /sessions/{id}/reschedule` с `expected_revision`. Редактор использует `reschedule` для изменения только даты/времени; комплексное редактирование нескольких полей остаётся одной транзакцией PATCH.

Перенос не отображается как успешный до ответа backend. При ошибке карточка остаётся на прежнем месте, введённые дата и время — в форме; при 409 нужно явно просмотреть актуальную запись и принять её версию или загрузить данные заново. Неизменённые локально поля времени при повторном применении берутся из актуальной записи. Новые события автоматически не рассылаются другим вкладкам: для обновления достаточно переключить период или перезагрузить страницу.

Кнопки, меню и формы доступны с клавиатуры. В месяце стрелки перемещают фокус по дням, Enter открывает день; в мобильной недельной ленте стрелки переключают день и сохраняют фокус. Все календарные вычисления используют компоненты даты, а не фиксированное количество миллисекунд. «Сегодня» и фактические даты выполнения определяются в `Europe/Moscow` независимо от часового пояса браузера.

### API календаря

`GET /api/planner/calendar?from=YYYY-MM-DD&to=YYYY-MM-DD`

Обе границы **включительные**. Максимум 93 дня и 5000 событий. Некорректный, обратный, чрезмерно длинный или слишком плотный диапазон возвращает 422 с понятной ошибкой; данные не обрезаются молча. Другие HTTP-методы возвращают 405. Маршрут проходит существующий контроль доступа.

Ответ содержит `from`, `to`, `timezone: "Europe/Moscow"`, `items` и лёгкий справочник `projects` (только ID, название и отметка архива, без вычисления прогресса).

У события есть `type`, `id`, `revision`, `task_id`, `task_revision`, `parent_task_id`, `title`, `date`, `start_time`, `end_time`, `status`, `task_status`, `priority`, `project_id`, `project_title`, `project_archived`.

| type | Значение |
|---|---|
| `task` | Задача на плановую дату без неотменённых сессий |
| `session` | Конкретная рабочая сессия; ID и revision принадлежат сессии |
| `planning` | Отдельная плановая дата задачи, у которой есть сессии на других датах |
| `deadline` | Дедлайн, отличный от плановой даты, либо дедлайн задачи без плановой даты |

Сессия на той же дате заменяет плановую карточку задачи. Это относится также к выполненным сессиям, чтобы завершённая работа не дублировалась в истории календаря. Отменённые сессии сохраняются отдельными историческими записями и не подавляют плановую дату задачи; по умолчанию они скрыты. Проверка наличия сессий выполняется независимо от видимого диапазона, поэтому тип индикатора не меняется при переключении месяца и дня. Несколько сессий одной задачи остаются отдельными периодами работы. Никакие дополнительные задачи или экземпляры повторений не создаются.

Запрос выполняет три выборки через UNION ALL по существующим индексам `tasks_planned`, `tasks_due`, `sessions_date`, в одной читающей транзакции. История событий не загружается, запросов на каждую видимую задачу нет. Фильтры проектов и состояний применяются к полученной проекции; скрывается также сессия, если скрыт конечный статус её задачи. После изменения проекция видимого периода запрашивается заново.

Дополнительно добавлен `GET /api/planner/tasks/{id}/context`: согласованный снимок одной задачи, её непосредственных детей и активных сессий этого дерева, включая даты вне календарного окна. Он нужен существующему диалогу завершения и редактору вместо загрузки всех задач/сессий приложения. При открытии редактора для выбора родителя дополнительно запрашиваются задачи только выбранного проекта. Все изменения по-прежнему выполняются прежними сервисами и проверками версий.

Схема SQLite и миграции не менялись: нужные таблицы и индексы уже существуют. Производственный календарь РФ, регулярные задачи, шаблоны и очередь внимания не затронуты. Финансовые JSON не читаются и не изменяются календарными операциями.

## Расчёт повторений и предпросмотр (этап 9)

Движок `internal/planner/recurrence` не зависит от HTTP, SQLite, системных часов или часового пояса устройства. Он получает правило, явную опору, номер цикла и интерфейс производственного календаря. `CalculateCycle` — общий расчёт одного цикла; `Preview` использует его для списка. Сейчас расчёт **ничего не создаёт и не изменяет**: ни задачи, ни серии, ни экземпляры, ни историю. Миграции 001–003 и финансовые JSON не меняются.

### Правила и календарная арифметика

- `schema_version: 1`; `unit`: `days`, `weeks`, `months`, `years`; `interval` — положительное целое число. 45 дней — ровно 45 календарных дней, а не полтора месяца.
- `mode: "schedule"` считает каждый цикл от исходной опоры. Результат предыдущей корректировки или ручного переноса не используется как новая опора.
- `mode: "completion"` считает только следующий цикл от подтверждённой фактической даты выполнения либо явно назначенной новой опоры. Перенос, пропуск и отмена сами по себе новую опору не дают.
- `allowed_days.mode`: `any`, `weekdays` (пн–пт), `weekends` (сб–вс), `selected`, `ru_production`. Только для `selected` требуется `weekdays`, например `[1, 3, 7]`; номера ISO: понедельник = 1, воскресенье = 7. Пустые списки и дубликаты запрещены.
- `adjustment`: `next`, `previous`, `nearest`, `none`. При равном расстоянии `nearest` выбирает следующий день. Разрешённая базовая дата всегда остаётся на месте. `none` допустим только с `any`: при ограничении дней требуется направление на случай недопустимой даты.
- `timezone` по умолчанию `Europe/Moscow`; другие зоны отклоняются. `Date` — календарная строка `YYYY-MM-DD`, а не точный момент времени. Арифметика использует компоненты даты и `AddDate`, без длительностей в миллисекундах.

При месячных и годовых повторениях сохраняется желаемый день **исходной опоры**. Несуществующий день ограничивается последним днём целевого месяца, без накопления сдвига:

| Правило и опора | Следующие базовые даты |
|---|---|
| 45 дней от 2026-01-01 | 2026-02-15, 2026-04-01, 2026-05-16 |
| 2 недели от 2026-12-20 | 2027-01-03, 2027-01-17, 2027-01-31 |
| 1 месяц от 2026-01-31 | 2026-02-28, 2026-03-31, 2026-04-30 |
| 1 год от 2024-02-29 | 2025-02-28, 2026-02-28, 2027-02-28, 2028-02-29 |

В режиме от выполнения новая фактическая дата становится новой опорой: если месячная задача реально выполнена 28 февраля, следующий базовый день — 28 марта. Для расписания от 31 января он остаётся 31 марта. Разные циклы могут иметь одинаковую скорректированную дату и не объединяются: ежедневные циклы 21, 22 и 23 ноября 2026 года с переносом на следующий будний день сохраняют три номера цикла, даже если все попадают на 23 ноября.

### API предпросмотра

`POST /api/planner/recurrence/preview` использует существующую защиту всех API. Пример JSON-тела:

```json
{
  "rule": {
    "schema_version": 1,
    "mode": "schedule",
    "unit": "days",
    "interval": 45,
    "allowed_days": {"mode": "weekdays"},
    "adjustment": "next",
    "timezone": "Europe/Moscow"
  },
  "anchor": {"date": "2026-01-01", "cycle_index": 0, "kind": "schedule"},
  "count": 5
}
```

Ответ содержит нормализованное `rule`, `anchor`, `requested_count`, `items`, `status`, необязательную `reason` и `calendars`. У каждого элемента: `cycle_index`, `anchor_date`, `base_date`, `adjusted_date`, `allowed_days`, `adjustment`, `shift_days`, `reason_code`, `reason`, `conditional`. Для примера первый цикл имеет базовую дату `2026-02-15`, скорректированную `2026-02-16`, сдвиг `1`; второй — `2026-04-01` без сдвига. Номера циклов не выводятся из даты.

По умолчанию список начинается с `anchor.cycle_index + 1`. Необязательный `start_cycle` позволяет продолжить расписание с заданного глобального номера; значение, равное опорному циклу, включает саму опору. Для режима от выполнения разрешён только непосредственно следующий цикл.

Опоры режима `completion`:

- `kind: "completion"` и `date` — подтверждённая фактическая дата предыдущего выполнения.
- `kind: "reanchor"` и `date` — явно подтверждённая новая опора, например после пропуска.
- `kind: "unconfirmed"`, без `date` — опоры ещё нет: ответ `200`, `status: "needs_anchor"`, пустой `items`.

При подтверждённой опоре от выполнения возвращается только один следующий цикл. Если запрошено больше одного, `status: "awaiting_completion"` объясняет, почему дальнейших дат нет; при одном — `ready`. Условные завершения не предполагаются, поэтому `conditional` всегда `false`. Предпросмотр принимает проектируемую опору клиента; при материализации её подтверждение нужно получать из сохранённого факта выполнения или явного решения пользователя.

Лимиты: `count` от 1 до 50; базовые и скорректированные даты не дальше 100 календарных лет от опоры; поиск допустимого дня — максимум 366 дней в выбранном направлении; поддерживаются годы 0001–9999. Переполнение чисел, выход за диапазон, неизвестные правила и противоречия дают явную ошибку. При ошибке частичный список не возвращается. Неверный JSON, типы или неизвестные поля (включая вложенные) — `400`; недопустимое правило/дата/лимит — `422`; иной HTTP-метод — `405`. Формат ошибок прежний: `{"error":{"code":"…","message":"…","current":…}}`.

### Производственный календарь и воспроизводимость

`ru_production` читает существующие таблицы календаря, учитывая `working`, `nonworking` и `shortened` (рабочий сокращённый день). Годы загружаются по необходимости в одном согласованном снимке SQLite, с проверкой полноты каждого года. Ответ `calendars` содержит использованные годы, `source`, `checksum` и `revision`. Одинаковые входные данные и одинаковая версия календаря дают одинаковый результат. Обновление календаря может изменить новый расчёт; метаданные позволяют определить причину.

Отсутствующий или неполный год возвращает `422`, `error.code: "production_calendar_unavailable"`, `error.current.year`. Это относится и к году, в который попал поиск переноса. Подмена обычными буднями запрещена. Автоматическая загрузка/проверка подлинности официальных источников здесь не реализована: используется существующий импорт полного проверенного календаря. В тестах применяются явно помеченные искусственные данные, они не включаются в пользовательскую БД.

### Переход к материализации на этапе 10

Существующих `series`, `series_versions.rule_json` и `occurrences` достаточно для расчётной модели, новая миграция сейчас не нужна. В JSON версии можно хранить типизированные `Rule`, исходный `Anchor` и границы глобальных номеров циклов. `ResolveVersionWindows` проверяет непересекающиеся полуоткрытые области по **базовой дате и номеру цикла**; открытый конец предыдущей версии определяется следующей версией без изменения старой записи. Скорректированная дата не выбирает версию правила.

Будущий материализатор должен выбрать версию и подтверждённую опору, вызвать тот же `CalculateCycle`, затем транзакционно сохранить отдельные `base_date`, `adjusted_date`, глобальный `cycle_index`, версию правила и сведения об использованном календаре. Нужен согласованный снимок календаря на весь расчёт. Перед вставкой следует проверять уже существующий цикл **по серии и номеру**, включая предыдущие версии: текущий SQLite UNIQUE включает также `rule_version_id` и сам по себе не предотвращает дубль между версиями.

Существующие `manual_date`, закрытые экземпляры и их история должны сохраняться; функция расчёта их не принимает и не переписывает. Материализатор отвечает за идемпотентность, ревизии и выбор будущих записей, которые разрешено менять. Горизонт создания 60 дней относится к этапу 10, а не к лимиту этого предпросмотра. Сейчас материализация, изменение серий, паузы, пропуски и UI редактора повторений не реализованы.

## Материализация регулярных задач (этап 10)

Повторения теперь создают обычные задачи в SQLite. Они доступны в существующих списках, редакторе и календаре, с собственными ID, revision, статусом, сессиями и историей. Расчёт использует `recurrence.CalculateCycle` этапа 9. Финансовые JSON и их бизнес-логика не изменены; интерфейс настройки повторений пока не добавлен.

### API серий

Все маршруты используют существующую серверную проверку доступа:

| Маршрут | Назначение |
|---|---|
| `POST /api/planner/series` | Создать серию, версию снимка задачи и первый цикл атомарно; начать заполнение горизонта |
| `GET /api/planner/series?after=ID` | Список по 20 серий; ответ `items`, `next_after` |
| `GET /api/planner/series/{id}?limit=100&offset=0` | Правило, снимок задачи, состояние расчёта и экземпляры; `limit` 1–100, `has_more` для пагинации |
| `POST /api/planner/materialize` | Идемпотентно расширить горизонт ограниченной порцией |
| `GET /api/planner/history?object_type=series&object_id=ID` | История серии с существующими `limit` и `offset` |

Пример создания стрижки каждые 45 дней:

```json
{
  "request_id": "unique-client-request-uuid",
  "task": {"title": "Стрижка", "description": "", "priority": "normal"},
  "first_date": "2026-11-16",
  "rule": {
    "schema_version": 1,
    "mode": "schedule",
    "unit": "days",
    "interval": 45,
    "allowed_days": {"mode": "any"},
    "adjustment": "none"
  }
}
```

`request_id` обязателен: одна и та же операция с тем же содержимым возвращает ту же серию, включая параллельные запросы и повтор после потери ответа. Тот же ключ с другим содержимым возвращает `409 idempotency_conflict`. Успешное создание/повтор возвращает `201`. Для нового создания клиент генерирует новый ключ.

`task` поддерживает название, описание, приоритет, необязательные `project_id`, `parent_task_id`, `scheduled_time`. Вместо `task` можно передать `existing_task_id` и обязательную актуальную `expected_revision`. Исходная задача становится циклом № 0 с прежним ID, статусом, дедлайном, сессиями и историей. Если у неё уже есть плановая дата, `first_date` должна совпадать с ней; дата существующей задачи не переносится молча. У активной задачи без даты назначается первое выполнение. У завершённой сохраняется прежняя плановая дата, даже если она отсутствовала. Несовпадение revision возвращает `409`; повторное подключение уже связанной задачи отклоняется.

Поддерживаются отдельные задачи и подзадачи. Превращение задачи с детьми в повторяющееся дерево отклоняется: копирование деревьев здесь не реализовано. Снимок версии содержит только поля шаблона задачи; абсолютный дедлайн и сессии исходной задачи не копируются в новые циклы. Последующие ручные изменения экземпляра не изменяют снимок.

### Первое выполнение и режимы отсчёта

Первое выполнение — **цикл № 0**: `first_date` становится его базовой датой, интервал не прибавляется. Допустимые дни и перенос применяются тем же движком. Явно выбранное первое выполнение создаётся даже за пределами стандартного горизонта. При подключении существующей задачи её отличающаяся дата сохраняется как ручная. Последующие циклы имеют номера 1, 2 и далее независимо от даты и версии правила.

Для расписания от `2026-11-16` с интервалом 45 дней даты будут `2026-11-16`, `2026-12-31`, `2027-02-14`. Незавершённые и просроченные задачи не блокируют следующие. Ручной перенос одного цикла не сдвигает расписание, совпадающие скорректированные даты не объединяют циклы.

В режиме `completion` первое выполнение создаётся по `first_date`, а опора **последующих** циклов хранится отдельно в `series_runtime.anchor_date/anchor_cycle`. Пока задача активна, следующего цикла нет. При завершении опорой становится именно `completed_date`, а не плановая дата или время запроса. Уже завершённая исходная задача сразу предоставляет подтверждённую фактическую опору. Раннее завершение может дать следующую дату раньше первоначальной плановой даты; область первой версии этого режима допускает такой случай.

Завершение задачи, обработка её активных сессий, история, обновление опоры и создание следующего цикла выполняются **одной транзакцией** и с общим `operation_id`. Это работает и при завершении родителя вместе с повторяющейся подзадачей. Если следующий цикл находится за горизонтом, сохраняется опора, а задача появится при расширении. Повтор завершения со старой revision возвращает `409`; повтор уже выполненного действия с актуальной revision — `422`. Дополнительный экземпляр не создаётся.

Отмена экземпляра расписания не останавливает расписание. Отмена ожидающего экземпляра режима от выполнения переводит серию в `needs_anchor`, без автоматического продолжения. Назначение новой опоры и восстановление описаны ниже, в разделе этапа 11. Завершение рабочей сессии по-прежнему не завершает задачу и не запускает следующий цикл.

### Горизонт, простой сервера и календарь

Стандартный горизонт — 60 календарных дней включительно: сегодня по Москве и следующие 59 дней. Материализатор учитывает **скорректированную** дату: например, цикл с базовой датой за горизонтом может потребоваться сейчас при переносе назад. Неизменённые базовые даты всегда считает движок этапа 9.

При создании серии транзакция включает первый цикл и до 100 следующих циклов. Большое отставание продолжается последующими порциями. Фоновый обработчик запускается при старте Go-сервера и затем проверяет горизонт каждую минуту. Порции восстановления/страницы серий обрабатываются с промежутком в секунду, освобождая хранилище между сериями. При SIGINT/SIGTERM обработчик отменяется и завершается до закрытия SQLite. Вкладка браузера для работы не нужна.

Курсор `next_cycle`, ожидающий экземпляр, подтверждённая опора и запрошенный горизонт сохраняются в SQLite. После длительного выключения сервер продолжает с сохранённого цикла и восстанавливает весь пропущенный период порциями. Прошлые незавершённые задачи остаются обычными доступными задачами с прошедшей датой; полноценная очередь внимания ещё не реализована.

Тело явного расширения:

```json
{"through": "2027-03-31"}
```

Пустой объект использует стандартный горизонт. Допускаются `series_id` для одной серии либо `after_series_id` для следующей страницы. `through` — включительная граница; она не уменьшает уже запрошенный горизонт. Явное расширение ограничено двумя годами от текущей даты (`422 materialization_range_limit`). За этой границей календарь продолжает показывать уже существующие задачи с заметным сообщением об ограничении создания повторений. Один запрос обрабатывает максимум 20 серий, по 100 новых циклов каждой. Ответ содержит `through`, `results` с `series_id`, `created`, `pending`, необязательной `error`, общий `pending` и `next_after_series_id`.

Если есть `next_after_series_id`, нужно продолжить следующую страницу. Если хотя бы у одной серии есть `pending`, после обхода страниц следует начать ещё один проход. Состояние сохраняется после каждой успешно обработанной серии. Ошибка одной серии полностью откатывает её текущую порцию и возвращается в `results[].error`; другие серии продолжают работу. `HTTP 200` такого пакетного ответа сам по себе не означает успех всех серий — клиент проверяет `error`. Ошибки входных данных возвращаются обычными `400/422`.

Календарь делает защищённый **POST материализации перед GET проекции** и обрабатывает страницы/порции. GET остаётся читающим и не создаёт задач. Ошибки отдельных серий выводятся заметным сообщением над календарём; уже существующие события остаются видимыми. Очень большое отставание ограничено 100 запросами за одну загрузку страницы: интерфейс предлагает продолжить, фоновая обработка при этом работает независимо. Все задачи и календарные события получили дополнительные необязательные `occurrence_id`, `series_id`, `rule_version_id`, `cycle_index`; прежние поля и ID сохранены.

### Миграция и гарантии целостности

Новая `004_task_series.sql` добавляет:

- Уникальный индекс `occurrences(series_id, cycle_index)` **без версии правила**. Один цикл невозможно вставить повторно под другой версией.
- Обратную отложенную ссылку `occurrences.task_link → tasks.occurrence_id`, обязательную для экземпляров задач, в дополнение к существующим FK и UNIQUE у `tasks.occurrence_id`. Нельзя зафиксировать экземпляр без задачи, две задачи одного экземпляра или отвязать существующую задачу.
- `calculation_json` со сведениями о расчёте и источниках календаря; неизменность происхождения экземпляра.
- `pending_completion` и частичный уникальный индекс одного ожидающего цикла серии, поддерживаемый триггерами связывания/смены статуса задач.
- `series_runtime` для курсора, опоры, ожидающего экземпляра и горизонта; уникальный ключ запроса создания в `series`.

Миграции 001–003 не редактировались. Если в старой БД уже есть конфликтующие циклы или экземпляры задач без задач, миграция отклоняется целиком: история не очищается и не объединяется автоматически. Экспорт/восстановление SQLite расширены таблицей `series_runtime`; проверяется восстановление опоры и ожидающего цикла вместе с задачами и историей.

Материализация не обновляет существующие задачи: ручные даты, названия, описания, приоритеты, статусы, сессии и фактические завершения сохраняются. Новые задачи берутся из неизменяемого `source_snapshot_json` конкретной версии. Создание имеет `actor: "system"`; подключение существующей задачи — `recurrence_linked`, `actor: "owner"`. Происхождение и общий ID операции доступны в истории задачи/серии.

### Ограничения и проверки

При создании серии появляется одна версия правила. Этап 11 добавляет управление версиями, паузами, пропусками и опорой (см. ниже). Повторяющиеся проекты и шаблоны реализованы в этапе 12 ниже. Редактор регулярных дел и визуальная очередь внимания не реализованы.

Для режима РФ требуется полный импортированный производственный календарь всех нужных лет. Отсутствие календаря не подменяется буднями. Если он нужен для следующего цикла при завершении задачи, вся операция завершения откатывается с явной ошибкой; после загрузки календаря её можно повторить. При обновлении календаря ранее созданные экземпляры не пересчитываются.

Основные файлы этапа: `series_model.go`, `series_repository.go`, `series_service.go`, `series_http.go`, `materialize.go`, `migrations/004_task_series.sql` внутри `internal/planner`. Интеграции: `migrate.go`, `service.go`, `repository.go`, `dto.go`, `http.go`, `calendar_projection.go`, `calendar_repository.go`, `backup.go`, `server.go`, `static/js/planner/calendar.js`. Тесты: `internal/planner/series_test.go`, `server_test.go`, `tests/materialize.test.cjs`, `tests/browser/series.spec.cjs`, `tests/browser/calendar.spec.cjs`.

Проверки охватывают создание/подключение задач, раннее фактическое завершение, оба режима, ручные правки, конкурентные запросы, SQL-ограничения, транзакционные откаты с сессиями/детьми, календарь РФ, простой и повторное открытие БД, фоновые проходы с тестовыми часами, снимки и восстановление, календарный POST перед GET и неизменность финансовых JSON. Команды прежние: `go test ./...`, `go test -race ./...`, `go vet ./...`, `npm test`, `npm run test:browser`, `git diff --check`.

## Этап 11: управление повторениями

Новые маршруты используют существующую защиту API и формат ошибок. Календарный движок остаётся единственным источником расчёта дат. Финансовые JSON не читаются и не записываются этими операциями.

### API и предпросмотр

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/planner/series/{id}/preview` | Предпросмотр команды серии без записи |
| `POST /api/planner/series/{id}/change-rule` | Новая версия правила с заданного цикла |
| `POST /api/planner/series/{id}/pause` | Пауза с включительными границами |
| `POST /api/planner/series/{id}/resume` | Досрочное окончание указанной паузы с сегодняшнего дня по Москве |
| `POST /api/planner/series/{id}/archive` | Остановка создания новых циклов, сохранение существующих |
| `POST /api/planner/series/{id}/reanchor` | Явная новая опора после пропуска/отмены в режиме от выполнения |
| `POST /api/planner/occurrences/{id}/reschedule` | Перенос одного цикла; закрытый цикл восстанавливается с прежним ID |
| `POST /api/planner/occurrences/{id}/restore` | Восстановление того же цикла |
| `POST /api/planner/occurrences/{id}/complete` | Завершение с обязательной фактической датой |
| `POST /api/planner/occurrences/{id}/cancel` | Явная отмена |
| `POST /api/planner/occurrences/{id}/skip` | Явная регистрация пропуска |
| `POST /api/planner/occurrences/{id}/review` | Оставить пропущенным, отметить рассмотренным |
| `GET /api/planner/incidents` | Все зарегистрированные пропуски/отмены, включая обработанные |
| `GET /api/planner/history?object_type=series&object_id={id}` | История серии с существующей пагинацией |
| `GET /api/planner/history?object_type=occurrence&object_id={id}` | История конкретного цикла и обработки пропусков |

`GET /series/{id}` дополнен `pauses`, `versions`, `anchor_kind`. У экземпляров `rule_version_id`, `base_date`, `adjusted_date` показывают текущую расчётную привязку; `original_rule_version_id`, `original_base_date`, `original_adjusted_date` сохраняют происхождение. `manual_date` и `manual_override` описывают ручное исключение. Дата задачи может отличаться от расчётной.

Перед **любой командой серии** сначала отправьте её тело на `/preview`. Например:

```json
{
  "action": "pause",
  "expected_revision": 8,
  "start_date": "2026-12-01",
  "end_date": "2026-12-31",
  "reason": "Отпуск"
}
```

Ответ содержит текущее/предлагаемое правило, строки `rows` с `before_date` → `after_date`, revision задач и экземпляров, ручные исключения, защищённые состояния, конфликты пауз и `calendar_errors`. `unchanged_outside_scope` — количество существующих циклов вне рассматриваемого диапазона. Для ещё не созданных циклов выводится образец до 10 дат в пределах уже запрошенного горизонта; это явно обозначенные строки `not_materialized`/`future_pause_skip`. Предпросмотр не материализует задачи и не записывает историю.

Для применения отправьте то же тело на соответствующий маршрут действия, добавив `preview_token` из ответа и новый `request_id`. В `action` используются значения `change_rule`, `pause`, `resume`, `archive`, `reanchor`. Токен проверяется при повторном расчёте внутри транзакции: изменение задач, сессий, пауз, версии календаря или московской даты возвращает `409 preview_changed` с новым предпросмотром. При изменении revision серии возвращается обычный `409`. Отсутствующие официальные календарные данные перечислены в предпросмотре; применение отклоняется с `422`, без замены календаря обычными буднями.

`request_id` обязателен для новых команд серии и экземпляра. Точный повтор возвращает сохранённый первый ответ даже со старой revision; тот же ключ с другим содержимым — `409 idempotency_conflict`. Результат команды и квитанция записываются в одной транзакции. Неуспешная команда квитанцию не создаёт. Для изменённого запроса после просмотра конфликта нужен новый ключ.

### Один цикл и изменение правила

«Только это выполнение» использует `/occurrences/{id}/reschedule` с `planned_date`. Существующий `/tasks/{id}/reschedule` также регистрирует ручное исключение. База и номер цикла сохраняются, будущая опора расписания не сдвигается. Снятие даты через редактор тоже считается ручным исключением и не отменяется материализатором.

Для «это и будущие» используется единственная команда `change_rule` с `rule`, `from_cycle` и, для режима `schedule`, `first_date`. Эта дата — **базовая дата цикла `from_cycle`**, а не новая дата цикла № 0; допустимые дни применяются движком. «Вся серия с сохранением истории» — та же команда с `from_cycle: 0`, без второго маршрута с дублирующей семантикой. Поля названия, описания, приоритета, проекта, дедлайна и сессии существующих задач не меняются.

Для режима `completion` поле `first_date` запрещено: подтверждённая фактическая опора сохраняется, новый интервал применяется к ней. Нельзя менять режим отсчёта существующей серии. Завершённые, отменённые, пропущенные, начатые экземпляры и ручные исключения защищены; прошедшие открытые даты также не переписываются. Выполненная/начатая рабочая сессия означает, что работа уже начата. В предпросмотре видна причина сохранения каждого рассматриваемого экземпляра.

Правила и снимки шаблонов в `series_versions` неизменяемы. Новая таблица `series_version_scopes` задаёт непересекающиеся полуинтервалы номеров циклов `[from_cycle, until_cycle)`; `null` означает отсутствие верхней границы. Триггеры SQLite запрещают пересечения. Полностью вытесненная область становится пустой, версия и её история остаются. Защищённые существующие экземпляры сохраняют свою прежнюю привязку как исключения; каждый новый цикл получает ровно одну версию по области применения.

Исходные поля `occurrences` не переписываются. Новая таблица `occurrence_schedule` хранит единственную текущую привязку изменяемого экземпляра. SQL-защита исходного происхождения, UNIQUE `(series_id, cycle_index)` и взаимные связи задачи/экземпляра этапа 10 сохранены. Два цикла на одной дате допустимы, второй экземпляр одного цикла — нет.

### Паузы и продолжение

Пауза проверяется по скорректированной расчётной дате **до ручного переноса**. Обычные ещё не начатые циклы расписания переводятся в `skipped`. Для будущих циклов материализатор создаёт связанную задачу сразу в пропущенном состоянии и долговечную запись пропуска в одной транзакции. Такие задачи не попадают в календарь и не становятся обычными просроченными. Отдельная задача даже для пропуска сохраняет ограничения связи этапа 10 и позволяет восстановить тот же ID.

Ручной перенос, начатая работа, активные сессии и дочерние задачи защищены от автоматического закрытия. Конфликт ручной даты с паузой виден в предпросмотре; применение сохраняет исключение. Эти сохранённые открытые задачи могут оставаться просроченными — это не пропуски. Пересекающиеся периоды пауз отклоняются.

По окончании периода расписание продолжается от прежних базовых дат. `resume` принимает `pause_id`: исходный период не удаляется, добавляется `resumed_on`. Будущие нерассмотренные пропуски именно этой паузы в режиме расписания восстанавливаются с прежними ID; прошлые, рассмотренные и вручную перенесённые не меняются. Факты восстановленных пропусков остаются с `resolution: restored`. После перезапуска материализатор использует сохранённые паузы и курсор, догоняет пропущенный период ограниченными порциями без дублей.

В режиме от выполнения пауза сохраняет уже ожидающий активный цикл; пропустить или отменить его можно только отдельной явной командой. Это действует и при смене правила, которая переносит его расчётную дату в существующую паузу: дата меняется после предпросмотра, статус остаётся активным (`change_date_pause_pending_preserved`). Если после подтверждённого завершения следующий рассчитанный цикл попал в паузу, создаётся **один** пропуск и серия становится `needs_anchor`. Цепочка предполагаемых выполнений не создаётся.

### Пропуски, история и будущая очередь внимания

Просрочка — вычисляемое состояние открытой задачи, а не пропуск или отмена. Для каждого пропуска/отмены `occurrence_incidents` хранит собственный ID, цикл, плановую дату, причину, источник `pause`/`user`, время регистрации и сведения о рассмотрении. Факт события защищён SQL-триггером от изменения. Последующая отмена пропуска добавляет **новое событие отмены**, не заменяет `kind: skipped`. Восстановление и фактическое завершение также не удаляют запись пропуска. Повторные пользовательские пропуски одного цикла дают отдельные факты; автоматический пропуск одного цикла одной паузой уникален.

Примеры чтения (доступна пагинация `limit` 1–100, `offset`, необязательный `series_id`):

```text
/api/planner/incidents?kind=skipped&disposition=needs_decision
/api/planner/incidents?kind=skipped&disposition=processed
/api/planner/incidents?kind=cancelled
/api/planner/incidents?series_id=SERIES_ID
```

Первый запрос — источник для будущего раздела «Требуют внимания». `attention_state` одновременно поддерживает одно состояние рассмотрения на экземпляр: `needs_decision`, пока есть хотя бы один нерассмотренный факт, иначе `processed`. Отдельные факты одного цикла не следует считать отдельными задачами в будущем счётчике. Без фильтра `disposition` возвращаются **все** факты, даже если связанная задача уже выполнена. `task_status` показывает её нынешнее состояние; `kind` описывает историческое событие. Явная отмена сразу считается рассмотренным решением.

Команда экземпляра требует трёх актуальных версий: `expected_revision` экземпляра, `expected_task_revision`, `expected_series_revision`, плюс `request_id`. Пример обработки пропуска:

```json
{
  "request_id": "unique-command-id",
  "expected_revision": 3,
  "expected_task_revision": 2,
  "expected_series_revision": 12,
  "completed_date": "2026-11-15"
}
```

Это тело отправляется на `/occurrences/{id}/complete`. `reschedule` принимает `planned_date`, `skip`/`cancel` — необязательную `reason`, `review` оставляет статус `skipped`. При закрытии задачи действуют прежние контракты `sessions_decision`, `session_revisions`, `children_decision`, `related_revisions`: правила сессий и дерева не обходятся. Обработка закрывает нерассмотренные факты с конкретной `resolution`, но не стирает историю прежних завершений.

В режиме от выполнения восстановление последнего закрытого цикла возвращает тот же ID и единственную ожидающую ветку. Альтернатива — команда серии `reanchor` с `anchor_date`: следующий цикл считается через интервал от явно указанной новой опоры. Если после этого пытаются восстановить старый цикл, сервер возвращает `409 completion_branch_conflict` с затрагиваемыми экземплярами. Пока новая опора ещё не породила преемника, `branch_decision: replace_anchor` явно отменяет эту опору и возвращает старый цикл. После появления следующих циклов восстановление старой ветки запрещено. Старый закрытый цикл можно завершить исключительно для истории с `branch_decision: historical_only`; это не запускает ещё одну последовательность. Обычный редактор задач пока не предоставляет эти новые решения — для повторяющихся экземпляров нужно использовать специализированный API.

Изменения задач, сессий, экземпляров, областей версий, пауз, фактов, состояния внимания, курсора и квитанций фиксируются одной SQLite-транзакцией вместе с `history_events`. Ошибка записи любого события откатывает всё изменение. Составные события получают общий `operation_id`; автоматические действия паузы имеют `actor: system`. Архивирование не удаляет задачи и историю. Экспорт/восстановление SQLite включает все новые таблицы и записи идемпотентности.

## Этап 12: шаблоны и повторяющиеся проекты

Шаблоны используют существующие `project_templates` и неизменяемые `template_versions`. Каждая версия содержит самостоятельный JSON-снимок описания проекта и дерева. Сессии, история, фактические даты, статусы реальных задач и ссылки на реальные задачи в снимок не входят. Отсутствующий приоритет нормализуется в `normal`, новые проекты и все новые задачи создаются в `planned`.

### API шаблонов

Все пути ниже имеют префикс `/api/planner` и используют прежний контроль доступа.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /templates?archived=false&limit=50&offset=0` | Список шаблонов, максимум 100 на страницу |
| `POST /templates` | Создать шаблон с первой версией |
| `GET /templates/{id}?version_id=...` | Получить выбранную версию с деревом; по умолчанию последнюю |
| `POST /templates/{id}/versions` | Создать новую неизменяемую версию |
| `POST /templates/{id}/archive` | Архивировать шаблон |
| `POST /templates/{id}/instantiate` | Создать обычный самостоятельный проект |
| `POST /templates/{id}/preview` | Предпросмотр дат и состава без записи |
| `GET /history?object_type=template&object_id={id}` | История шаблона с прежней пагинацией |

Создание:

```json
{
  "request_id": "unique-template-command",
  "snapshot": {
    "title": "Генеральная уборка",
    "description": "Уборка квартиры",
    "due_offset": 3,
    "tasks": [
      {"key": "rooms", "title": "Комнаты", "planned_offset": 0, "due_offset": 2},
      {"key": "kitchen", "parent_key": "rooms", "title": "Кухня", "priority": "high", "planned_offset": 1},
      {"key": "supplies", "title": "Купить средства", "planned_offset": -1},
      {"key": "notes", "title": "Разобрать заметки"}
    ]
  }
}
```

`key` — уникальный локальный ключ задачи внутри шаблона, до 100 байт; `parent_key` ссылается только на корневой ключ того же снимка. При обновлении сохраняйте ключи логически тех же задач: это позволяет сохранить их ID в уже созданных проектах. Циклы, отсутствующие родители и третий уровень вложенности отклоняются. Поддерживаются `description`, `priority`, `scheduled_time` формата `HH:MM`; время требует `planned_offset`.

`planned_offset` и `due_offset` независимы, измеряются календарными днями и допускают значения от −3650 до 3650. Пропущенное поле или `null` означает отсутствие даты. `due_offset` самого проекта также необязателен. Смещения считаются через календарную арифметику от **скорректированного начала конкретного экземпляра**, в системе календарных дат Europe/Moscow. Рабочие дни применяются только к началу регулярного проекта; даты дочерних задач дополнительно не корректируются. Например, скорректированное начало в понедельник с задачей `planned_offset: -1` даёт воскресенье.

Создание/новая версия возвращают `201` и `{ "template": ... }`. Для `/versions` нужны `request_id`, `expected_revision` шаблона и полный новый `snapshot`. Это не изменяет уже существующие проекты или серию автоматически. `/archive` принимает `request_id` и `expected_revision`, возвращает `200`. Архивный шаблон нельзя использовать для новых ручных проектов, новых серий или переключения версии; существующие серии продолжают работать со своими сохранёнными снимками. Их остановка — отдельное архивирование серии.

Для `/instantiate` передайте:

```json
{"request_id":"unique-project-command","expected_revision":1,"start_date":"2026-12-20"}
```

Необязательный `template_version_id` выбирает конкретную версию этого шаблона. `expected_revision` относится к текущей записи шаблона, даже при выборе старой версии. Ответ `201` содержит `{ "project": ... }` с новым деревом и `template_version_id`. Дата начала обязательна для однозначного расчёта относительных дат.

`/preview` принимает `start_date`, необязательные `template_version_id`, `expected_revision`, `rule`, `count`. Без `rule` показывает один обычный проект; с правилом `schedule` — от 1 до 20 циклов (по умолчанию 5) с `candidate` и рассчитанным составом `project`. Правило имеет прежний формат движка повторений. Первый цикл приходится на указанную дату с применением допустимых дней, без лишнего интервала. Предпросмотр не создаёт проекты, задачи, версии и события истории.

### Серии проектов и независимость экземпляров

Используется прежний `POST /series`, расширенный источником проекта:

```json
{
  "request_id": "unique-project-series",
  "source_type": "project",
  "template_id": "TEMPLATE_ID",
  "expected_revision": 1,
  "first_date": "2026-12-20",
  "rule": {
    "schema_version": 1,
    "mode": "schedule",
    "unit": "weeks",
    "interval": 2,
    "allowed_days": {"mode": "any"},
    "adjustment": "none"
  }
}
```

Можно указать `template_version_id`. `expected_revision` проверяет запись шаблона. `task` и `existing_task_id` с проектным источником запрещены. Проекты поддерживают только `schedule`; запрос `completion` отклоняется. Контракты серий отдельных задач сохранены, для них `source_type` можно по-прежнему не передавать.

`GET /series` и `GET /series/{id}` возвращают оба типа. Проектная серия содержит `project_template`, `template_version_id`; области версий дополнены снимком и ID версии шаблона. В проектном экземпляре вместо `task` возвращается `project`, включая конкретные задачи и подзадачи, а также `source_type: project`, `project_status`, `template_version_id`. У компактного пропуска `compact: true`, проект ещё отсутствует. Исходные и текущие расчётные даты/версии правила сохранены, как на этапе 11.

Каждое создание сначала выделяет новые ID проекта и всех задач, затем связывает корни и подзадачи. Даты, исходные статусы, ссылка на версию шаблона и история фиксируются вместе. Изменение одного экземпляра не затрагивает соседние экземпляры или снимок шаблона. Незавершённый старый проект не блокирует следующий. Сессии никогда не копируются.

Проектный источник подключён к тому же `CalculateCycle`, курсору `series_runtime`, фоновому обработчику и `POST /materialize`. Стандартный горизонт остаётся 60 дней. Одна порция проектной серии обрабатывает до 5 циклов (каждый шаблон — максимум 500 задач), освобождая хранилище между порциями. `created` считает циклы, включая компактные пропуски. Большой период догоняется существующим протоколом `pending` и фоновыми проходами; первые ответы могут содержать только уже обработанную порцию. Перезапуск использует сохранённый курсор, UNIQUE `(series_id, cycle_index)` не зависит от версии правила.

В календаре отображаются обычные конкретные задачи экземпляра с `project_id`. Сам проект не добавляет дублирующие карточки. Задачи без дат остаются в проекте. Существующие UI календаря и редактора задачи не переписывались.

### Изменение правила и версии шаблона

Для проектов доступны прежние команды серии `/preview`, `/change-rule`, `/pause`, `/resume`, `/archive`, плюс новая `/change-template`. Все применяемые команды требуют `expected_revision`, `preview_token` из актуального предпросмотра и `request_id`; точный повтор возвращает сохранённый результат.

`change_rule` использует прежние `rule`, `from_cycle`, `first_date` и требует `tasks_date_decision: keep | shift`. `keep` сохраняет даты дочерних задач; `shift` пересчитывает их относительные даты от нового начала. При смене только расписания уже созданный проект сохраняет собственную версию дерева, даже если более поздние циклы используют другую версию шаблона. Новые циклы получают снимок новой версии серии.

Для применения версии шаблона сначала отправьте на `/series/{id}/preview`:

```json
{
  "action": "change_template",
  "expected_revision": 12,
  "from_cycle": 3,
  "template_version_id": "NEW_TEMPLATE_VERSION_ID"
}
```

Потом отправьте то же тело с `request_id` и полученным `preview_token` на `/series/{id}/change-template`. Новая версия должна принадлежать тому же шаблону. Команда создаёт новую неизменяемую версию серии с областью от `from_cycle`, не сдвигая прежнюю календарную опору правила.

Предпросмотр включает существующий `project` с деревом, `proposed_project` с будущим составом/датами, версию шаблона, причины сохранения экземпляров, сессии, конфликты пауз и ошибки производственного календаря. Завершённые, начатые, вручную перенесённые, отредактированные пользователем и имеющие сессии проекты защищены целиком. Снимок исходного состояния каждого созданного проекта позволяет обнаружить и ручные изменения дочерних задач, включая перемещение задачи из проекта. Остальные существующие будущие проекты могут получить новый состав с сохранением ID задач по локальным ключам.

Удаление ключа из состава требует `removed_tasks_decision: cancel`. Эти задачи **не удаляются**: они остаются в прежнем проекте отменёнными, с историей. Без подтверждения применение возвращает 409. Автоматическая смена родителя уже существующей задачи не поддерживается: возвращается конфликт без частичной записи. Добавлять новые корневые задачи и подзадачи можно. Новые экземпляры получают только состав соответствующей версии, без исторических отменённых элементов старых экземпляров.

В одной массовой команде допускается до 100 рассматриваемых проектов и суммарно до 5000 задач. Более широкая операция отклоняется до записи; нужно сузить границу/период. Образец ещё не материализованных циклов ограничен 10 датами в текущем горизонте. Отсутствующий официальный календарь РФ остаётся явной ошибкой, а не заменяется буднями.

### Паузы, пропуски, закрытие и восстановление

Период паузы определяется по скорректированному началу до ручного переноса. Для ещё не созданного цикла создаются компактный экземпляр и факт `skipped` в существующей `occurrence_incidents`, без проекта и дерева. Для уже созданного, не изменённого и не начатого проекта пауза сохраняет проект/задачи с их ID и переводит открытые задачи в `skipped`. Проекты с ручными изменениями, начатой работой или сессиями сохраняются и отмечаются в предпросмотре как защищённые.

Прежний `GET /incidents` включает проектные пропуски и отмены, с `source_type`, `project_id` при наличии и `project_status`. Фильтры `series_id`, `kind`, `disposition`, пагинация и `attention_state` работают также для компактного пропуска. Рассмотрение, отмена, перенос и выполнение не удаляют исходный факт пропуска.

Для команд `/occurrences/{id}/skip|restore|reschedule|complete|cancel|review` проекта передавайте `request_id`, `expected_revision` экземпляра, `expected_series_revision` и `expected_project_revision`. Для компактного пропуска последняя равна 0 или отсутствует. `expected_task_revision` и `children_decision` относятся к сериям одиночных задач и здесь не используются.

При закрытии уже созданного проекта нужны `related_revisions` затрагиваемых открытых задач и явное решение:

- `skip`: `tasks_decision: skip_open`.
- `cancel`: `tasks_decision: cancel_open`.
- `complete`: `tasks_decision: complete_open` и фактическая `completed_date` для завершаемых задач.

Если есть активные сессии, дополнительно нужны прежние `sessions_decision: cancel` и `session_revisions`. Завершённые задачи не меняют статус или фактическую дату. Новые активные задачи/восстановление отдельных задач в закрытом регулярном проекте запрещены до восстановления самого экземпляра. Обычное закрытие регулярного проекта через `/projects/{id}` возвращает 409 с указанием специализированного маршрута, чтобы не обойти подтверждения. Обычные проекты сохраняют прежний API.

`restore` существующего проекта с закрытыми им задачами требует `tasks_decision: restore_closed` и их `related_revisions`. Восстанавливаются только задачи, закрытые операцией над этим экземпляром, с прежними ID; выполненные остаются выполненными. Если закрытая задача впоследствии изменена/перемещена, возвращается конфликт. Отменённые сессии автоматически не оживают. Компактный пропуск разворачивается в проект из сохранённой версии шаблона; ID цикла остаётся прежним. При прямом завершении компактного пропуска требуется `complete_open`; версии ещё не существовавших задач назначаются сервером в той же транзакции.

`reschedule` принимает `planned_date` как новую дату начала и обязательное `tasks_date_decision: keep | shift`. `shift` сдвигает плановые даты и дедлайны открытых задач на календарную разницу, требует их `related_revisions` и сохраняет даты завершённых задач; сессии и дедлайн самого проекта не переносятся. Перенос закрытого экземпляра одновременно восстанавливает его; для существующего дерева также требуется `restore_closed`. Перенос начала через обычный редактор проекта оставляет задачи на прежних датах и регистрируется как ручное исключение.

`review` оставляет проект пропущенным, убирая его из активной очереди рассмотрения. Досрочное `resume` восстанавливает будущие нерассмотренные пропуски соответствующей паузы, в том числе разворачивает компактные записи; рассмотренные и ручные исключения остаются. Проекты поддерживают только расписание: `reanchor` не применяется. Если внутри проекта пользователь создал отдельную повторяющуюся задачу, составное закрытие проекта возвращает конфликт; сначала нужно отдельно архивировать эту серию и переместить её экземпляры из проекта. Проверяется также сохранённый источник серии: одного переноса уже созданных задач недостаточно, если серия продолжает создавать новые задачи в этом проекте.

### Хранилище, история и проверки

Добавлена только миграция `006_project_templates.sql`; прежние миграции не редактировались. Она добавляет взаимную отложенную ссылку `occurrences.project_link → projects.occurrence_id` и различает компактное/материализованное состояние. Нельзя зафиксировать полный экземпляр без проекта, подменить его связь или создать два проекта одного цикла. Ранее существовавшие корректные проектные связи сохраняются; необъяснимый экземпляр без проекта и без закрытого исхода отклоняет миграцию целиком.

`project_instances` хранит исходное состояние экземпляра и соответствие ключей новым ID для защиты ручных изменений. `project_closed_tasks` фиксирует, какие задачи и в каких версиях закрыла операция пропуска/отмены. `history_events` транзакционно расширяется ссылкой `template_id` с сохранением прежних ID, payload, времён и operation_id; сохраняется запрет изменения событий. Новые таблицы включены в согласованный экспорт и восстановление SQLite, с проверкой внешних ключей и целостности.

Создание серии/версии/цикла/проекта/всего дерева, массовая смена версии, закрытие задач и сессий, инциденты, история и квитанции идемпотентности выполняются транзакционно. ## Этап 13 — регулярные дела, шаблоны и внимание

В `Планы` добавлены hash-разделы `#/plans/series`, `#/plans/templates`,
`#/plans/attention` и `#/plans/settings`. Редакторы регулярности и шаблонов
открываются справа, на узком экране занимают всю ширину. Обычные задачи,
сессии и бюджет сохраняют прежние маршруты. В редакторе задачи кнопка
«Повторять» привязывает **исходную** задачу через `existing_task_id`, без копии.

Конструктор предлагает простые варианты и расширенные настройки интервала,
допустимых дней и корректировки. Расчёт делает Go; frontend не вычисляет
даты повторений. Для режима от выполнения показывается первое запланированное
выполнение и только подтверждённое продолжение. У существующей серии режим
отсчёта сохраняется согласно контракту этапа 11. Изменение всей серии и
«начиная с выполнения» используют один `change-rule` с разным `from_cycle`.

Перед применением правила, паузы, возобновления, архивирования, новой опоры
или обновления состава проектов показывается предпросмотр. `preview_token`
и ревизия проверяются сервером. Ручные исключения, закрытые и начатые проекты,
сессии и пользовательские изменения защищены. Изменение шаблона само по себе
не меняет созданные проекты: для них есть отдельное действие в серии.
Удаление задач шаблона требует подтверждения `removed_tasks_decision=cancel`.

Действия с регулярными выполнениями используют `/occurrences/{id}/…`:
перенос, выполнение с фактической датой, пропуск, отмена, восстановление,
рассмотрение. У проекта явно подтверждаются открытые задачи и активные
сессии. Возвращается исходный экземпляр, выполненные дочерние задачи
сохраняются. Для старой цепочки от выполнения доступны запись только в
историю и замена ещё не использованной опоры; конфликт с уже созданным
продолжением не обходится. Перенос через существующий календарь продолжает
использовать task reschedule: этот серверный путь уже регистрирует ручное
исключение серии.

Все команды новых форм используют стабильный `request_id` до получения
подтверждённого ответа. При сетевой ошибке повторяется **тот же payload**;
при 409 изменения не применяются, черновик остаётся, нужен новый просмотр.
Во время отправки кнопки блокируются. Пользовательские строки создаются
через DOM/textContent, без HTML-интерполяции.

### Дополнения к API

Все маршруты находятся под прежней защитой `/api/planner`.

| Маршрут | Назначение |
| --- | --- |
| `POST /api/planner/series/preview` | Предпросмотр создания, включая цикл 0: `{rule, first_date, count:1..10, existing_task_id?}`. Для завершённой исходной задачи опора берётся из SQLite. Ничего не записывает. |
| `GET /api/planner/occurrences/{id}` | Согласованный контекст `{series, occurrence}` для версий составной команды. |
| `GET /api/planner/attention?tab=needs_decision\|overdue\|skipped\|processed&series_id=&limit=50&offset=0` | Список и глобальный счётчик `count` необработанных проблем. `limit` 1–100. |
| `GET /api/planner/attention/{id}?type=task\|project\|occurrence` | Ревизия настройки напоминания (0, если ещё не создана). |
| `POST /api/planner/attention/{id}` | Отложить: `{type, expected_revision, snoozed_until, request_id}`. Повтор идемпотентен, история записывается транзакционно. |
| `GET /api/planner/templates/{id}/projects` | Связанные обычные и регулярные проекты (до 500 последних). |
| `GET /api/planner/production-calendar` | Загруженные годы, полнота, источники, версии, контрольные суммы, даты обновления. |
| `GET /api/planner/production-calendar/bundled/{year}` | Подготовленные полные календари 2026 и 2027. GET не импортирует данные. |
| `POST /api/planner/production-calendar/preview` | Проверка документа и сравнение дней: `{calendar}` → `changed_days`, `expected_revision`, `preview_token`. |
| `POST /api/planner/production-calendar/import` | Подтверждённый импорт: `{calendar, expected_revision, preview_token, request_id, source_confirmed:true}`. |

`GET /series` и `GET /series/{id}` дополнены `template_id`, `next_date`,
`last_completed_date`, `unresolved_count`; детальная карточка — `upcoming`
(не более 5 ближайших активных выполнений).
`POST /series` принимает необязательный `end_date`: включительная граница
**автоматического создания** по скорректированной дате. Она не удаляет
существующие выполнения и не запрещает их явный ручной перенос. Граница
задаётся при создании; изменение этой границы у существующей серии пока
не предоставлено. Архивирование останавливает дальнейшее создание.

Обычный проект с независимыми неархивными сериями задач нельзя молча
завершить, отменить или архивировать: сервер возвращает 409
`nested_series_conflict`. Их нужно сначала отдельно остановить/разобрать.
Это также проверяется при изменении статуса через PATCH.

### Очередь внимания и сохранность истории

Просрочка — серверная проекция открытых задач: прошла плановая дата **или**
дедлайн относительно Europe/Moscow. Полночь ничего не удаляет и не меняет
статус. Недатированные задачи в неё не попадают. Пропуски и отмены приходят
из `occurrence_incidents`, учитывается `attention_state`. Одна актуальная
проблема не считается одновременно просроченной задачей и инцидентом.

«Рассмотрено» снимает активное требование решения, но не означает выполнение.
Во вкладке «Пропущенные» запись остаётся даже после последующей отмены;
«Обработанные» показывает принятые решения. Повторные события одного цикла
доступны в истории серии и через исходный `/incidents` с пагинацией.
Пропуски паузы группируются с раскрытием выполнений. Напоминания с имеющимся
`snoozed_until` не включаются в активный счётчик до указанной даты; действие «Отложить напоминание» сохраняет дату без изменения статуса или
рассмотренности инцидента. Доступно для открытых просроченных задач и
необработанных пропусков.

### Проверяемый производственный календарь

Добавлена миграция `007_calendar_imports.sql` (старые миграции не меняются).
`calendar_imports` хранит неизменяемый документ каждого импорта, источник,
дату публикации, версию, SHA-256, ревизию года и ID операции. Таблица включена
в экспорт и транзакционное восстановление SQLite. Эта же миграция добавляет
`series_runtime.end_date`. Финансовые JSON не участвуют.

Комплект содержит **2026** для федеральной пятидневной недели:

- [Постановление Правительства РФ от 24.09.2025 №1466](https://static.government.ru/media/files/4jeB8hNKm69ggOa9yDiYOli6YoAyM21i.pdf): 3 января → 9 января; 4 января → 31 декабря.
- Статьи 95, 111 и 112 ТК РФ: федеральные праздники, обычные выходные,
  предпраздничные дни; в 2026 переносы совпавших праздников дают 9 марта и
  11 мая. [Разъяснение производственного календаря на государственном портале «Работа России»](https://web-cgu-demo01.k8s.trudvsem.ru/information-pages/calendar-2026).
- Контроль: 365 календарных дней, 247 рабочих (включая 4 сокращённых),
  118 нерабочих. Сокращённые: 30 апреля, 8 мая, 11 июня, 3 ноября.

Файл `internal/planner/calendars/2026.json` подготовлен из этих документов,
а не загружается из предполагаемого официального JSON API. При запуске
сервера он **не импортируется автоматически**: в настройках есть проверка
и явное подтверждение. Календарь не экстраполируется на следующие годы.

На этапе 14 добавлен **2027** для федеральной пятидневной недели. Постановление
Правительства РФ от 17.09.2026 №1187: 2 января → 5 ноября, 3 января → 31 декабря,
20 февраля → 22 февраля. Текст сверён по [КонсультантПлюс](https://www.consultant.ru/document/cons_doc_LAW_544706/)
и [Гаранту](https://base.garant.ru/414931980/); дополнительные выходные сверены с
[официальным календарём Банка России](https://www.cbr.ru/other/holidays/).
Официальная публикация 18.09.2026 №0001202609180037 указана в метаданных;
прямой портал публикации во время проверки отвечал тайм-аутом. Подробности
проверки и контрольные даты приведены в [отчёте](STAGE14-ACCEPTANCE.md#производственный-календарь).
Контроль: 365 дней, 247 рабочих (в том числе 4 сокращённых), 118 нерабочих.
20 февраля — рабочая сокращённая суббота; 22 февраля, 5 ноября и 31 декабря — выходные.
Оба года требуют предварительной проверки и явного подтверждения импорта
в «Планы → Настройки». Никакого автоматического изменения пользовательской базы.
Региональные праздники и сменные графики не моделируются. Для отсутствующего
года расчёт возвращает явную ошибку, не заменяя календарь обычными буднями.

Формат подготовленного файла (полный образец — bundled/2026):

```json
{
  "schema_version": 1,
  "year": 2026,
  "source": "https://static.government.ru/media/files/4jeB8hNKm69ggOa9yDiYOli6YoAyM21i.pdf",
  "published_at": "2025-09-24",
  "version": "2026.1",
  "days": [{"date": "2026-01-01", "kind": "nonworking", "reason": "Ст.112 ТК РФ"}],
  "checksum": "SHA-256 полного документа по описанному ниже правилу"
}
```

Пример выше сокращён: импорт требует **каждую** дату года ровно один раз.
Допустимы `working`, `nonworking`, `shortened`; любой рабочий выходной
задаётся явно в `days`. Источник — HTTPS URL официальных доменов Правительства,
правового портала или Роструда. Сервер не запрашивает произвольные URL.
SHA-256 вычисляется по UTF-8 JSON без `checksum`, без отступов, с порядком
полей как в образце; `days` сортируются по дате, поля дня — date/kind/reason;
канонизация соответствует Go `encoding/json.Marshal` (включая HTML escaping).

Проверка URL, структуры и checksum не доказывает подлинность нормативного
документа: подготовитель должен сверить даты и метаданные с официальным
источником, пользователь подтверждает это перед импортом. Для неизвестного
года нет fallback на понедельник–пятницу. Полнота, checksum, ревизия и токен
проверяются до записи; данные года, аудит и квитанция команды сохраняются
одной транзакцией. Ошибка не оставляет частично заменённый год.

Импорт не переписывает существующие экземпляры. Новые циклы используют
обновлённый календарь. Пересчёт уже созданных будущих выполнений — отдельный
`change-rule` с тем же правилом, новым предпросмотром и подтверждением.
Защищённые и ручные экземпляры сохраняются, а старый preview_token после
изменения используемого года становится неактуальным.

### UX 2.0 — этап 2: редактор и общие действия

Задача открывается в правой панели на широком экране и на всю ширину до 768 px.
Название и плановая дата доступны сразу; «Проект и подзадача», «Параметры»,
«Периоды работы» и «История» раскрываются по необходимости. Заполненные значения
видны в сводках. Сохранение выполняется явно; закрытие изменённой формы предлагает
сохранить, отменить изменения или продолжить редактирование. Ошибки и 409 сохраняют черновик.

Меню `···` в списках, проекте, календаре и редакторе использует общий модуль
`actions.js`. Перенос предлагает сегодня, завтра, через неделю или выбранную дату
по Москве. Для задачи используется `/tasks/{id}/reschedule`, для периода работы —
`/sessions/{id}/reschedule`, для регулярного выполнения — `/occurrences/{id}/reschedule`.
Последний маршрут теперь принимает необязательное `scheduled_time` (`HH:MM`,
`null` — убрать время, отсутствие поля — сохранить). Дата, время, исключение и
история записываются одной существующей транзакцией, с проверкой всех revisions
и `request_id`. Для экземпляров проектов это поле запрещено. Миграция не нужна.

Дата регулярной задачи в редакторе доступна для просмотра; действие «Перенести
выполнение» открывает общий перенос. Настройка будущего расписания остаётся в
редакторе серии с предпросмотром. Перемещение отдельного регулярного выполнения
между проектами недоступно: интерфейс объясняет ограничение и предлагает открыть серию.
Обычный родитель перемещается вместе с подзадачами через существующую транзакцию.

В карточке проекта действия собраны в меню, даты и статус редактора сворачиваются.
Изменение дат проекта не обещает перенос дочерних задач. После быстрого создания
можно нажать «Открыть» в уведомлении; автоматического перехода в большую форму нет.

Подробный отчёт и сравнение экранов: [UX2-STAGE2.md](UX2-STAGE2.md).

## UX 2.0 — этап 3: оформление

В редакторах задач и проектов есть необязательный раскрываемый выбор «Оформление»:
12 цветов, 66 локальных иконок Lucide, поиск и категории. Выбор изменяет черновик;
данные сохраняются только обычной кнопкой «Сохранить», с проверкой revision.
Иконки и сдержанные цветовые акценты используются в списках, проектах и календаре.
Период работы получает оформление своей задачи. Статус, приоритет и нарушение срока
отображаются отдельно от персонального цвета.

Собственные `color_id` и `icon_id` независимы. `null` означает наследование:
задача/подзадача → собственное значение → собственное значение родителя → проект →
нейтральный цвет `slate` и стандартная иконка задачи. У проекта стандартная иконка
`lucide:folder`. Явный `slate` — собственный нейтральный цвет, а не наследование.
Эффективные `effective_color_id` / `effective_icon_id` вычисляет сервер при чтении.
Изменение проекта или перемещение дерева меняет унаследованный вид без записи
цвета в дочерние задачи и без изменения их revision, дат или истории.

Миграция `008_appearance.sql` добавляет nullable-поля оформления с ограничениями
цветов и внешними ключами на `planner_icons`, сам каталог и `icon_events`.
Миграции 001–007 не изменены. Существующие записи получают нейтральное/унаследованное
оформление. Миграция применяется обычным механизмом при запуске обновлённого сервера.
Финансовые JSON не участвуют.

Оформление включено в снимки задач серий, версии шаблонов проектов и состав создаваемого
проекта. Повторная материализация не сбрасывает настройки существующего выполнения.
Изменение шаблона создаёт новую версию; применение к будущим проектам остаётся отдельной
операцией с существующим предпросмотром. Начатые проекты и проекты с ручными изменениями
защищены. Вычисляемые поля оформления не считаются ручными изменениями при сравнении
с исходным снимком, в том числе у проектов, созданных до миграции 008.

### Каталог и изображения

«Планы» → шестерёнка → «Мои иконки»: загрузка нескольких файлов, переименование,
удаление из выбора. Поддерживаются PNG и WebP до 1 MiB и 1024 × 1024 px.
Сервер проверяет реальный формат и размеры до декодирования, затем кодирует пиксели
в новый PNG. Произвольный SVG, повреждённые изображения и лишние поля отклоняются.
Метаданные и посторонние данные исходного файла не сохраняются.

Нормализованный PNG хранится BLOB в SQLite, с SHA-256 и размерами. Повторная загрузка
одинакового нормализованного изображения возвращает существующую активную иконку.
Лимит пользовательского каталога — 512 изображений и 32 MiB, включая удалённые
из выбора. Удаление мягкое: задача, история и неизменяемый шаблон сохраняют ссылку
и изображение; место автоматически не освобождается. Редактирование пикселей уже
существующей иконки не поддерживается — загрузите новое изображение.

Все маршруты используют существующий контроль доступа:

| Запрос | Контракт |
| --- | --- |
| `GET /api/planner/icons` | Массив активных встроенных и пользовательских иконок с названием, категорией, revision и checksum |
| `POST /api/planner/icons` | `{ "name": "Название", "data": "base64 файла" }`; 201 для нового изображения, 200 при повторе |
| `PATCH /api/planner/icons/{id}` | `{ "name": "Новое название", "expected_revision": 1 }` |
| `DELETE /api/planner/icons/{id}` | `{ "expected_revision": 1 }`; убирает из каталога выбора, сохраняет используемое изображение |
| `GET /api/planner/icons/{id}/image` | Защищённое изображение, `private, no-store`, `nosniff`; доступен также HEAD |

Встроенные идентификаторы — `lucide:<имя>`, пользовательские — `custom:<непрозрачный ID>`.
Идентификаторы не являются путями к пользовательским файлам. Изображения не размещаются
в `static`. Встроенные SVG входят в бинарник через `go:embed`; браузер получает их как
изображения, без вставки SVG/HTML пользовательской строкой.

`color_id` и `icon_id` принимаются существующими POST/PATCH задач и проектов; PATCH
по-прежнему требует `expected_revision`. Служебные effective-поля недоступны для записи.
Изменение оформления и событие `history_events` сохраняются одной транзакцией.
Каталог имеет отдельный транзакционный журнал `icon_events`.

Экспорт включает BLOB, каталог и журнал. Перед экспортом/восстановлением проверяются
SQLite integrity/foreign keys, SHA-256 изображений и возможность их декодирования.
При повреждении изображения восстановление отклоняется до изменения рабочей базы.
Как и прежде, снимок для восстановления должен соответствовать текущей версии схемы;
старый снимок не обновляется неявно при восстановлении.

Категории встроенных иконок (по 6): дом и быт, работа, здоровье, спорт, покупки,
путешествия, обучение, развлечения, техника, финансы, разное. Полный список названий
и ID: [catalog.json](internal/planner/icons/catalog.json).
Источник: [Lucide](https://github.com/lucide-icons/lucide), пакет `lucide-static@0.468.0`;
[лицензия](internal/planner/icons/LICENSE) и [метаданные загрузки](internal/planner/icons/SOURCE.md)
включены в репозиторий. Для WebP используется `golang.org/x/image v0.32.0`.
Зависимости от CDN не добавлены.

### Плановая дата и крайний срок

Плановая дата — день предполагаемой работы, крайний срок — последний допустимый день.
Оба значения необязательны. Плановая дата видна сразу, крайний срок — в «Параметрах»
и в сводке свёрнутого раздела. Перенос плановой даты не меняет крайний срок.
Планирование после крайнего срока разрешено с предупреждением; завершение после него
тоже разрешено и сохраняет указанную фактическую дату.

В списках и очереди внимания различаются «Не выполнено по плану» и «Просрочен крайний
срок». Крайний срок истекает после окончания календарного дня Europe/Moscow, а не
по часовому поясу браузера. Приоритет классификации: истёкший крайний срок, затем
прошедшая плановая дата. Закрытые и пропущенные задачи не попадают в активные группы.
API внимания сохраняет совместимый `source: overdue`, уточняя причину в `reason`.

## UX 2.0 — этап 4: повторение и шаблоны в карточках

В карточке задачи доступны «Сделать регулярной», краткое описание настроенного
повторения, «Изменить повторение» и «Сохранить как шаблон». Общее меню действий
используется также в списках, календаре и конкретных выполнениях. Пауза и прекращение
повторений проходят через прежний серверный предпросмотр. Прекращение архивирует
серию: история и уже созданные, в том числе будущие, выполнения остаются. Отдельный
перенос по-прежнему регистрирует исключение через occurrence, не меняя расписание.

Исходная задача подключается через существующий `POST /api/planner/series` с
`existing_task_id` и `expected_revision`: её ID, история, оформление и фактическая
дата сохраняются. Завершённая задача в режиме от выполнения использует подтверждённую
фактическую дату. Отменённую задачу сначала нужно восстановить. Повторение дерева
подзадач на уровне одной задачи не поддерживается: для дерева используется проект.

Четыре главных раздела сохранены. В «Задачах» добавлено представление «Шаблоны задач»
(`#/plans/task-templates` и `#/plans/task-templates/{id}`). Старые маршруты входящих,
задач, проектов, календаря, серий, проектных шаблонов, внимания и настроек работают.
Глобальный `+` предлагает также «Создать из шаблона»: тип заготовки, название,
контекстная дата/проект и сохранение. Дата из календаря подставляется; вне календаря
задача по умолчанию создаётся без даты. Быстрый ввод обычных задач не изменён.

### Версионированные шаблоны задач

Миграция `009_entity_templates.sql` расширяет существующую таблицу
`project_templates` дискриминатором `template_kind` (`project` по умолчанию, `task`).
Неизменяемые снимки обоих видов хранятся в прежней `template_versions`. Внутренний
снимок шаблона задачи содержит ровно одну корневую заготовку без дат. В публичной
команде для задачи используется компактный `snapshot`:

```json
{
  "request_id": "unique-command-id",
  "source_task_id": "existing-task-id",
  "expected_revision": 3,
  "snapshot": {
    "title": "Подготовить отчёт",
    "description": "Проверить цифры перед отправкой",
    "priority": "normal",
    "color_id": "blue",
    "icon_id": "lucide:briefcase"
  }
}
```

`source_task_id` необязателен. При его наличии `snapshot` можно опустить: сервер
снимет текущие название, описание, приоритет и эффективное оформление исходной
задачи. Это сохраняет узнаваемость и при создании самостоятельной задачи, ранее
наследовавшей цвет проекта. Сам шаблон не содержит ID, статус, историю, абсолютные
даты, родителя, проект, периоды работы, инциденты или правило повторения. Дерево
подзадач не копируется в шаблон отдельной задачи.

Новые защищённые маршруты:

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/planner/task-templates?archived=false&offset=0` | Список, страницы по 50 |
| `POST /api/planner/task-templates` | Сохранить заготовку, в том числе из задачи |
| `GET /api/planner/task-templates/{id}` | Последняя версия и состояние |
| `POST /api/planner/task-templates/{id}/versions` | Переименовать/изменить через новую версию |
| `POST /api/planner/task-templates/{id}/archive` | Архивировать, сохранив историю и созданные задачи |
| `POST /api/planner/task-templates/{id}/instantiate` | Создать задачу; необязательные `project_id`, `planned_date` |
| `POST /api/planner/projects/{id}/template-preview` | Предпросмотр дерева/дат из существующего проекта |
| `POST /api/planner/projects/{id}/save-template` | Атомарно сохранить шаблон и, при наличии `rule`, повторение |

Все изменяющие команды используют `request_id`; команды существующего объекта —
`expected_revision`. Результат возвращается в прежней оболочке команд:
`template`, `task`, `project`, `series` по смыслу операции. Ответ шаблона сохраняет
формат общего DTO: `kind`, `snapshot`, `version_id`, `version`, `revision`.
Обычные `/templates` остаются только проектными; задача-заготовка не может случайно
стать источником серии проектов. История обоих видов доступна через
`GET /api/planner/history?object_type=template&object_id=...` с прежней пагинацией.

`entity_template_links` хранит источник и роль связи `saved` или `source`, версию
и, для исходного проекта, необязательную серию. Ограничения SQLite проверяют тип
объекта и соответствие версии шаблону. Читаемые DTO дополнены `saved_template_id`,
`source_template_id`; у проекта есть `repeat_series_id`. Эти поля не принимаются
от клиента. В интерфейсе «Сохранено как шаблон» и «Создано из шаблона» различаются;
индикатор повторения независим от них. Сохранение связи увеличивает revision
исходного объекта и добавляет событие, не меняя его содержимое и прежнюю историю.

### Обычный проект → шаблон и повторение

Действия находятся в карточке и общем меню проекта. Используется существующий
редактор дерева шаблона с раскрываемыми настройками задач. Пользователь видит
состав, оформление и независимые относительные плановые даты/крайние сроки.
Начальная опора смещений — дата начала исходного проекта, при её отсутствии —
сегодня по Москве. Смещения можно изменить вручную до сохранения. Ограничение
существующих шаблонов: от −3650 до +3650 календарных дней.

Исходный проект остаётся самостоятельным. Его ID, завершённые задачи, периоды
работы, даты и история не копируются и не переписываются. Новые проекты создаются
с явно показанной «Даты следующего проекта», только от расписания. Независимые
повторения отдельных исходных задач в заготовку не переносятся. Их исходные серии
продолжают работать; закрытие проекта по-прежнему защищено серверными правилами.

Для программного клиента сначала отправьте в `template-preview`:

```json
{
  "expected_revision": 2,
  "anchor_date": "2026-11-21",
  "first_date": "2026-12-05",
  "rule": {
    "schema_version": 1,
    "unit": "weeks",
    "interval": 2,
    "mode": "schedule",
    "allowed_days": {"mode": "any"},
    "adjustment": "none",
    "timezone": "Europe/Moscow"
  }
}
```

Ответ содержит `snapshot`, пять предварительных составов/дат `items` (меньше при
ограничении `end_date`) и `preview_token`. Можно изменить `snapshot` и повторить
предпросмотр. Для сохранения передайте **то же тело**, добавив `preview_token` и
`request_id`, в `save-template`. Для сохранения только шаблона опустите `rule`,
`first_date` и `end_date`.

Токен связывает настройки с полным деревом и revision всех исходных задач, а не
только с revision проекта. Добавление новой подзадачи также делает предпросмотр
устаревшим. При конфликте сервер возвращает 409; форма сохраняет черновик и требует
нового просмотра. Шаблон, версия, серия, новые проекты/задачи, исходная связь,
история и результат идемпотентной команды записываются одной транзакцией. Для
расчёта и материализации переиспользуется тот же `createProjectSeriesTx` и движок
`recurrence`, что у существующих серий. Дата не становится идентификатором цикла.
Повторные запросы с одним ключом возвращают сохранённый результат; разные ключи с
устаревшей версией отклоняются. Обрыв ответа оставляет кнопку безопасного повтора
той же команды, блокируя изменение её параметров до подтверждения.

После создания шаблона новые версии не изменяют уже созданные объекты. Обновление
будущих проектов использует прежний экран повторения, `change-template`,
предпросмотр и защиту ручных/начатых/завершённых экземпляров. Экспорт SQLite включает
новые связи. Проверены обновление схем 001–008 до 009 и экспорт/восстановление 009.
Как и ранее, восстановление требует совместимой схемы снимка; старая резервная
копия сначала восстанавливается совместимой версией приложения, затем обновляется.

Проверки этапа: `internal/planner/entity_templates_test.go`,

### Производственный календарь и фильтры

`GET /api/planner/calendar` дополнен полями `calendar_days` и
`calendar_missing_years`. Каждый день содержит `date`, `kind`, `work_kind`,
`label`, `reason`, `shortened`. Проекция читает только выбранный диапазон
(прежний максимум 93 дня), не выполняет импорт и не изменяет повторения.
Классификация выполняется Go-кодом по импортированным `kind`/`reason` и дню
недели. Frontend не вычисляет государственные праздники.

Подсветка работает в месяце, неделе, дне и мобильной недельной ленте:
обычные выходные нейтральные, праздники розовые, переносы дополнительно
подчёркнуты пунктиром, рабочие субботы/воскресенья синие. Цвета самих задач,
статусы и выбранная дата остаются независимыми. Есть легенда, сводка выбранного
дня и tooltip с основанием из импортированного календаря.

Проверены существующие подтверждённые наборы **2026 и 2027**: граница годов,
20 февраля 2027 (рабочая сокращённая суббота), 22 февраля, 5 ноября и
31 декабря (переносы). Эти файлы и их нормативные источники не изменялись.
Неполный или неподтверждённый год не раскрашивается: показано предупреждение
со ссылкой на настройки. Автоматического импорта нет. Требование проверки
файла и явного подтверждения импорта сохранено.

Переключатель «Показывать праздники и выходные» находится в настройках.
Настройка и недавние иконки сохраняются локально в браузере; это предпочтения
отображения, они не входят в SQLite-backup и не синхронизируются между браузерами.

Активный проект и скрытые статусы видны отдельными плашками, включая узкое окно
со свёрнутой панелью фильтров. Показано количество видимых **событий**, а не задач:
периоды работы и указатели срока учитываются отдельно. Сброс сохраняет дату
и режим календаря, убирает проектный фильтр и показывает закрытые события.

### Ограничения

Данные РФ относятся к федеральной пятидневке. Региональные праздники и
индивидуальные графики не добавлены. Названия конкретных праздников не

Для нестандартных причин нерабочего дня используется нейтральная классификация.

дня используется до 900 px, чтобы на планшетной ширине названия не сжимались
в семь узких колонок. Новых финансовых функций, PWA и развёртывания нет.
