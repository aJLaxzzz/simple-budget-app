# Planner UX 3.1

Локальная реализация, синтетические данные. VPS, PROD/STG и настоящие данные не изменялись. Коммит, deploy и promotion выполняет пользователь. Mobile Foundation и PWA не начаты.

## Сохранённое поведение этапа

- N (1–20, по умолчанию 3) ограничивает целые текущие/будущие открытые проекты, включая исходный проект. Просроченные доступны сверх N. Закрытые и архивные не занимают место; уменьшение N не удаляет избыток. Многодневный проект считается текущим до крайнего срока либо, без него, последней даты задач/начала. Materialization сохраняет историю и ID.
- Выполненные календарные задачи остаются на плановых датах. В месяце и блоке «Без времени»: активные → выполненные → отменённые; события со временем сохраняют временные позиции. Настройки видимости находятся в настройках планировщика.
- Группы задач разделены по конкретному проекту, дате и временной секции. Состояние раскрытия сохраняется при синхронизации. Самостоятельные строки и группы сортируются хронологически; без времени — в начале дня.
- Drag & Drop сохраняет конкретную задачу без диалога, не меняет крайний срок или всю серию. Отмена использует ревизию; чужие свежие изменения не перезаписываются. Сохраняются прокрутка, фильтры и черновики.
- Быстрое завершение родителя оставляет подзадачи открытыми. Проект завершается отдельным действием, только когда все задачи выполнены; отменённые/пропущенные не считаются выполненными. Пустой проект не готов к завершению.
- Стартовый URL и «Сегодня» открывают месячный календарь на сегодняшней дате по Москве. Прямые маршруты сохранены.

## Дополнение №3: причины и исправления

### Подзадачи и будущий состав

Пустой регулярный проект мог материализовать будущие экземпляры до добавления задач. Добавление только в выбранный экземпляр не меняло шаблон: будущие проекты оставались пустыми.

Ошибка создания подзадачи воспроизведена для локального родителя, которого нет в общем шаблоне. Для исходного проекта таблица соответствий возвращала ID родителя как ключ, но такого узла в шаблоне не было: нормализатор дерева сообщал о недопустимой вложенности/цикле. Для будущего экземпляра отсутствовало само соответствие ID → ключ шаблона.

Теперь при общем добавлении ребёнка отсутствующий обычный корневой родитель включается в состав вместе с ним. Даты переводятся в смещения от начала выбранного проекта; ключ шаблона сопоставляется с собственным ID родителя каждого будущего экземпляра. Названия не используются как идентификаторы. Проверки глубины, циклов, принадлежности проекту, ревизий и транзакционность сохранены. Родитель с собственным независимым повторением не преобразуется молча.

Контекст действий:

| Место / действие | Область |
|---|---|
| Страница регулярного проекта: добавление, параметры задач, даты, время, порядок | Это и последующие выполнения |
| Общий список / календарь: создание и изменение задачи | Только выбранная задача |
| Выполнение, восстановление, фактический статус | Только выбранная задача/экземпляр |
| «Перенести выполнение проекта» | Только выбранный проект |

Основные селекторы области убраны. Безопасные preview/apply выполняются автоматически. Защищённые исключения и разрушительные операции сохраняют отдельную проверку последствий. Неопределённый сетевой результат повторяется с тем же request_id и payload; не создаётся новая команда поверх возможно сохранённой.

Старые пустые экземпляры автоматически не ремонтируются. Для синтетического проекта можно добавить состав со страницы выбранного проекта; обычные будущие экземпляры обновятся, исключения потребуют просмотра. Настоящие данные сначала проверять через штатный предпросмотр, без массового сброса.

### Независимые проекты и миграция 015

Интерфейс создаёт только независимые серии. Убраны выбор режима, выбор текущего выполнения и предварительные блокировки. Начало нового проекта служит опорой расписания; крайний срок и окончание серии необязательны. Проекты повторяются только по расписанию; обычные регулярные задачи сохраняют отсчёт от завершения. Дополнительный пересчёт относительных дат при преобразовании существующего проекта оставлен в раскрываемом разделе.

При штатном обновлении миграция **14 → 15** выполняется административным этапом до запуска приложения (сам production-запуск старую схему не мигрирует):

1. Добавляет событие `project_mode_changed` для каждой старой последовательной серии.
2. Переводит её `project_repeat_state.mode` в `independent`, очищает выбор текущего проекта и `needs_decision`.
3. Увеличивает ревизию серии, чтобы старые клиентские команды не применились без проверки.

Миграция **не переписывает** проекты, задачи, экземпляры, даты, пользовательские исключения, версии расписания, runtime и инциденты. Старые поля и явная legacy-поддержка API сохранены для совместимости; их нет в основном UI. Повторное открытие не повторяет миграцию. Следующая обычная materialization может заполнить свободные места до N; существующие избыточные экземпляры сохранятся полностью.

Проблема «выберите текущее выполнение» исчезает как неактуальная проекция; существующая история не удаляется. Устаревшие вычисляемые поля в сохранённых baseline не делают нетронутые будущие проекты ложными пользовательскими исключениями.

**Перед PROD:** пользователь проверяет миграцию на STG и штатную pre-update копию. Старый бинарник не следует запускать поверх схемы 15; возврат к нему выполняется штатным восстановлением соответствующего поколения данных. В этой работе миграция запускалась только на временных синтетических БД. `server-install` не требуется: административный протокол не менялся.

### Переносы

Разовое действие переносит начало и сохраняет длину интервала проекта по крайнему сроку; даты открытых задач сдвигаются только при выбранном варианте «вместе с проектом». Расписание и даты других экземпляров не меняются. При пересечении с другим открытым экземпляром UI предлагает сохранить оба либо выбрать другую дату. Автоматического объединения/удаления нет.

### Архив и старые шаблоны

Добавлена вкладка «Архив»: проекты, их задачи и архивированные серии, фильтр типа, открытие, восстановление и существующее защищённое удаление. Активные списки/фильтры исключают архивные проекты; календарная история не уничтожается. Дата архива серии берётся из истории, если доступна.

В текущей модели у отдельной задачи нет самостоятельного признака архива. Она архивируется вместе с проектом; действие подписано **«Вернуть проект с задачами»**, чтобы не скрывать последствия. Восстановление серии вновь разрешает materialization, сохраняя экземпляры и runtime; для отсутствующей опоры отсчёта от завершения требуется явное решение. Активные паузы сохраняются.

Архив серии прекращает новые выполнения, но не архивирует автоматически уже созданные проекты/задачи. Это прежняя семантика; архив проекта касается конкретного проекта. Полноценный отдельный архив самостоятельных задач потребовал бы расширения модели — параллельное хранилище не добавлено.

Шаблоны не удалены и не превращены в архивные сущности. Доступ: настройки → «Старые шаблоны · дополнительные инструменты».

### «Внимание»

Две вкладки: **Активные** и **История**. Активные сгруппированы:

- Невыполненные вовремя: открытые просрочки и необработанные инциденты; причины/действия различаются.
- Отложенные: напоминания с будущей датой рассмотрения. Они исключены из счётчика; в существующей модели отсрочка задаётся датой и заканчивается в полночь по Москве, не меняя срок задачи.
- Проблемы планирования: отсутствующая опора или ошибка расчёта.

Одна запись входит в одну группу. История показывает все обработанные инциденты, включая несколько последовательных инцидентов одного выполнения. Legacy API-фильтры сохранены. Счётчик отражает актуальные необработанные проблемы без отложенных, а не размер истории.

### Семантика действий

| Действие | Обычный проект | Выполнение регулярного проекта | Серия |
|---|---|---|---|
| Завершить | Только после выполнения всех задач, без каскада | Тот же контроль; освобождает место для будущего выполнения | Массового завершения нет |
| Отменить | Закрывает проект; последствия для открытых задач подтверждаются | Закрывает выбранный экземпляр, расписание остальных сохраняется | Не подменяет архивирование/отключение |
| Перенести | Меняет выбранный проект/даты согласно выбранному действию | Только выбранный экземпляр; пересечение допустимо после предупреждения | Изменение правила — отдельный preview/apply |
| В архив | Скрывает проект вместе с задачами | Скрывает конкретный проект, не всю серию | Прекращает дальнейшее создание; существующие экземпляры сохраняются |
| Удалить навсегда | Физическое удаление с проверкой зависимостей и подтверждением | Только выбранное выполнение при выбранной области | Отдельно подтверждённое удаление всей серии и её выполнений |

### Остальное

STG обозначен компактной меткой в верхней навигации на desktop/mobile и в заголовке вкладки. В локальном `make budget` по умолчанию выбрана acceptance/STG, `SUDO_MODE=session`. Открытие меню не запускает STG. Явный выбор PROD и безопасные значения прямых Make-команд сохранены.

## Ручная приёмка на STG после коммита пользователя

1. В `make budget` проверить выбранный STG, установить свой закоммиченный release пунктом 2. PROD не обновлять до приёмки.
2. Проверить сохранение старой последовательной серии: те же ID, даты, история и исключения; все открытые выполнения доступны без выбора текущего. Проверить N=1/3/5, просроченный проект сверх N, уменьшение N без удаления избытка.
3. Создать пустой еженедельный проект, добавить корневую задачу и подзадачу обоими способами. Проверить родителей и задачи в будущих экземплярах. Повторить для родителя, созданного только в одном экземпляре.
4. Со страницы проекта изменить дату/время: будущие задачи получают относительные смещения. Из календаря/общего списка изменить ту же задачу: другие экземпляры неизменны. Проверить индивидуальное исключение и конфликт двух клиентов.
5. Завершить родителя с открытым ребёнком: ребёнок доступен, проект не готов. Отменить завершение. Завершить все задачи и затем отдельно проект.
6. Перенести 20–21 на 21–22: следующие 27–28 и 4–5 неизменны. Перенести на уже занятую неделю: увидеть предупреждение, оставить два отдельных выполнения.
7. Архивировать проект и серию по отдельности; проверить вкладку архива, фильтры, дату, открытие, восстановление. Удаление проверять только на специально созданной синтетической сущности. Проверить доступ к старым шаблонам.
8. Создать просрочку, пропуск, отложенное напоминание; проверить две вкладки, отсутствие дублей и счётчик. Срок самой задачи при отсрочке не меняется.
9. На Mac и OnePlus проверить компактный STG, календарную историю, быстрый DnD на 15:00 и отмену, прокрутку, черновик и Live Sync между двумя клиентами. Мобильный редизайн в этот этап не входит.

## Дополнение №4 — повторения и общая навигация

### Причина и исправление

На новой синтетической БД воспроизведены варианты с редактированием исходного проекта и будущего экземпляра: пустой ежедневный проект → корень и подзадача → разные даты → общее изменение даты → еженедельное расписание → повторное изменение даты. Отдельно проверены добавление ребёнка непосредственно в будущем экземпляре и настоящая индивидуальная правка.

**Подтверждённый дефект:** общее изменение состава обновляло шаблон и baseline последующих проектов, но выбранный материализованный экземпляр изменялся как обычный локальный объект. Его `template_version_id` и baseline оставались прежними. При смене расписания сравнение с baseline ошибочно давало `protected_user_changes`: старое ежедневное выполнение оставалось на прежней дате, занимая свой `cycle_index`. Новое еженедельное выполнение с тем же номером уже не создавалось. Это реальные старые экземпляры, а не двойная отрисовка одной задачи; так возникают наложения в первой неделе и свободное место в следующей. Точную историю конкретного STG-проекта не читали и не меняли.

Теперь выбранный экземпляр принимает новую версию и baseline в той же транзакции, **только если** до команды был нетронутым и после команды его полное содержимое соответствует новому шаблону. Сравнение сопоставляет ID задач и родителей со стабильными ключами шаблона. Даты остаются относительными к началу каждого выполнения. Индивидуальные изменения, начатые/закрытые задачи, история и исключения сохраняют защиту. Проверки ревизий, preview token, повтор команды и уникальность циклов остаются действующими.

Смена расписания обновляет нетронутые будущие экземпляры, сохраняя ID проектов, выполнений и задач. Разовый перенос по-прежнему меняет только выбранное выполнение. Повторная materialization не создаёт дубликаты и соблюдает N; просроченные остаются сверх лимита.

**Старые наложения не ремонтируются автоматически.** Прежний baseline нельзя безопасно переписать задним числом без проверки индивидуальных изменений. В preview теперь явно сказано: защищённые выполнения сохраняют даты и номера циклов; возможны наложения и свободные недели. Для такого случая пользователь проверяет каждое сохранённое выполнение и при необходимости явно переносит его. Автоматического объединения, удаления или нового клонирования нет.

### Группы задач

Сценарий «родитель одного выполнения и ребёнок предыдущего выполнения попали на один день» корректен, если ребёнок имеет относительное смещение +1 день. Родители проверены по ID, даты не менялись ради отображения.

Новая внешняя группа использует **ID серии + дату + временную секцию**. Это заменяет прежнее правило отдельной внешней карточки на каждый экземпляр. Для нескольких экземпляров строки отмечены периодом выполнения; подзадачи — названием родителя, даже когда родитель завершён или назначен на другой день. Для одного экземпляра дополнительных вложенных уровней нет. Обычные проекты с одинаковыми названиями остаются отдельными.

Прогресс берётся из фактических статусов задач этого дня, без двойного подсчёта, включая завершённые задачи экземпляра, в котором больше нет активных строк. Фильтр конкретного экземпляра остаётся конкретным. Хронология и раскрытие сохраняются при SSE.

### Навигация

Одна общая панель с переключателем **Планы / Бюджет**. Основные вкладки меняются вместе с модулем; контекстные вкладки планировщика сохранены. Шестерёнка и компактный STG остаются доступны. Финансовый бэкап вызывает прежнее скачивание, поиск и финансовые экраны сохранены.

Последний маршрут каждого модуля запоминается в пределах открытой страницы; полная перезагрузка базового URL по-прежнему открывает месячный календарь на сегодня. Прямые hash-ссылки, Back и возврат после авторизации используют прежнюю маршрутизацию. Черновик планировщика защищён прежним диалогом; при переходе с несохранёнными финансовыми полями требуется явное решение, отмена перехода сохраняет поля. Новые CSS/JS включены в явный manifest embedded frontend.

Новых миграций нет: актуальна схема **15** из дополнения №3. Административный протокол не менялся, `server-install` не требуется.

### Финальная ручная приёмка

1. После своего коммита установить release только на STG штатным пунктом 2. Проверить SHA. `server-install` не нужен.
2. Создать новый синтетический ежедневный проект, добавить корень и ребёнка с разницей в один день. В «Завтра» раскрыть одну карточку серии: строки разных выполнений имеют периоды и правильного родителя. Завершить родителя — открытый ребёнок остаётся доступен.
3. В будущем экземпляре со страницы проекта изменить дату ребёнка. Сменить ежедневное расписание на еженедельное через preview. Ещё раз изменить дату ребёнка. Проверить несколько недель, относительные смещения, родителей, N и отсутствие лишних копий после обновления страницы.
4. Создать отдельную индивидуальную правку из календаря. При смене правила проверить предупреждение и сохранность этого исключения. Старые проблемные данные не сбрасывать ради приёмки; автоматического ремонта у них нет.
5. Переключить Планы → Бюджет → Планы; проверить последние разделы, контекстные вкладки, шестерёнку, Back, прямую ссылку и компактный STG. Проверить отмену ухода с черновиком. В бюджете проверить поиск, месяцы, аналитику, категории и прежнее скачивание бэкапа.
6. На двух устройствах проверить обновление дат и прогресса группы без потери раскрытия/прокрутки. Продвижение в PROD выполнять отдельно после приёмки, этим заданием оно не выполнялось.
