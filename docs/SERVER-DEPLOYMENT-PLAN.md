## Доступ

```text
Mac / Android → https://171.22.237.16 → Caddy (публичный TLS + обязательный mTLS)
 → 127.0.0.1:3001 → Go (обязательный пароль, точные Host/Origin)
```

Без доменного имени, Tailscale, обязательного VPN, Docker, Nginx и отдельной СУБД. Один Go ELF со встроенным frontend. SQLite для планировщика, JSON для финансов. Финансовый last-write-wins и отсутствие push приняты для первой серверной версии.

Caddy сохраняет `/var/lib/caddy/ip-acme-production`, действующие сертификаты и публичную CA/leaf в `/etc/caddy/pki`. Certbot не требуется и не устанавливается. Перед применением automation фактический Caddyfile адаптируется, проверяется каждая TLS policy, включая fallback. Все обязаны требовать `require_and_verify` и одинаковый точный allowlist. HTTP80 — ACME/404, чужой HTTPS Host —404; отключение strict SNI/Host в Caddy не отменяет эти проверки и строгую политику приложения.

Automation сохраняет исходный Caddyfile и создаёт проверенный управляемый JSON из него, меняя защищённую страницу на proxy. Управляемый Caddy admin API отключён, конфигурация применяется validate+restart; full restart закрывает существующие TLS-соединения. Ticket resumption явно отключён. При ошибке нет доступа без mTLS. Возврат тестовой страницы строится по **текущему registry**, не по старому allowlist из backup.

Go production: `BUDGET_ENV=production`, `BUDGET_ADDR=127.0.0.1:3001`, `BUDGET_PUBLIC_ORIGIN=https://171.22.237.16`, `BUDGET_ALLOWED_HOSTS=171.22.237.16`, `BUDGET_PROXY_MODE=loopback-https`, `BUDGET_MIGRATIONS=check-only`, `TZ=Europe/Moscow`. Абсолютные DATA_DIR/BACKUP_DIR и installation ID обязательны. Пароль через systemd LoadCredential: минимум 12 символов, рекомендуется 16; максимум 4096 байт UTF-8. Это актуальная политика вместо исторического минимума 32 в сохранённом аудите. Localhost не обходит авторизацию; forwarded headers не являются основанием доверия. Передача Host/Authorization через настоящий Caddy проверяется на VPS.

Отдельная synthetic acceptance: суффикс `-acceptance`, отдельный пользователь/ID/data/backup, loopback3002. Тесты не используют настоящую production installation.

## Backup и восстановление

Используется реализованный stage2 CLI, без параллельной системы. Daily03:30 Europe/Moscow/Persistent,7 успешных daily,2 обычных pre-update и защищённые rollback/pending копии. Обязательная копия перед обновлением. Минимум свободного диска max(2GiB,15%) плюс staging; inode проверяются. Предупреждение об устаревании **26 часов** заменяет36 часов первоначального этапа2.

Снимок при короткой остановке, возобновление до сжатия обычного backup, проверка SQLite/JSON/manifest/SHA и атомарная публикация. Deployment удерживает maintenance. Full archive содержит planner.db, data.json, categories.json, несекретные настройки, manifest и инструкцию. Иконки внутриSQLite. Нет паролей/ключей/ACMEstate/PKIcontainers/WAL/logs/source/другихbackup. Пользователь скачивает проверенный архив наMac; автоматического внешнего хранения нет.

Restore — только admin CLI, проверка ID/ledger/checksums, отдельный staging и forward migration, recovery journal для переключения набора; прежнее поколение сохраняется. Секреты и PKI восстанавливаются отдельно. Legacy Mac экспортируется в согласованный клон без изменения исходного marker/данных; сервер создаётся с ID проверенного архива.

## 2. Что проверено в репозитории

### Сборка и зависимости

Фактически выполнено на Mac, Go `1.25.5`:

```sh
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -o /tmp/<audit>/budget-linux-amd64 .
```

Результат: статически слинкованный ELF для x86-64, `GOAMD64=v1`, 18 276 042 байта (17,43 MiB), без stripping. `go version -m` подтверждает commit и отсутствие изменённых исходников при сборке. Рабочий `./budget` этой командой не затрагивался. **Запуск Linux ELF на VPS или Linux VM в этом аудите не выполнялся.**

`go.mod` требует Go 1.24.0; основные зависимости — `modernc.org/sqlite v1.39.1` и `golang.org/x/image v0.32.0`. Остальные закреплены в `go.mod`/`go.sum`: modernc libc/memory/mathutil, x/sys, x/exp, uuid, go-humanize, go-strftime, go-isatty, bigfft. `go mod verify` прошёл. CGO, системный SQLite development package, Node.js и Playwright на production для работы приложения не нужны. Node/браузеры нужны только для разработки и тестов.

Миграции, builtin SVG, каталог и производственные календари 2026/2027 уже встроены через `go:embed`. `time/tzdata` подключена в `internal/planner/series_service.go`. **HTML/CSS/JS пока читаются из внешнего `static/`**, поэтому один нынешний бинарник без ресурсов не запустится. `static.go` читает разрешённые файлы в память при старте.

Решение: встроить существующий frontend в бинарник, сохранив allowlist и проверки маршрутов. Внешний `BUDGET_STATIC_DIR` оставить только как явный dev override. Не добавлять CDN. Производственный release будет содержать бинарник и небольшой manifest, без дерева репозитория.

Проверка контрольных сумм модулей не является проверкой отсутствия уязвимостей. До выпуска инфраструктурного release отдельно выполнить `govulncheck ./...`, проверить поддерживаемый Go toolchain и патчи зависимостей; результаты этого сканирования сейчас отсутствуют.

Серверный backup не может сохранить браузерные настройки и открытые несохранённые формы. Ручной порядок, хранящийся в SQLite, сохраняется; выбранный браузером способ отображения может отличаться на двух Mac и телефоне. Новый HTTPS origin также получит отдельное browser storage. Это не потеря задач.

`Store.Open` создаёт отсутствующую БД, применяет миграции и seed до запуска сервиса. Отсутствующий финансовый JSON воспринимается как новое хранилище. В production это опасно при ошибке пути: приложение может выглядеть пустым вместо отказа запуска. Нужны отдельные `init/import` и режим обычного запуска, который **не создаёт новую установку молча**.

### SQLite и финансовые записи

`internal/planner/store.go`: один SQL connection, общий mutex, транзакции, foreign keys, WAL, `synchronous=FULL`, busy timeout 5 секунд. Flock защищает БД от второго процесса; ссылки и hardlink обходы проверяются. Linux amd64 сборка этих механизмов прошла. Не следует разворачивать два экземпляра приложения с одной БД или запускать backup-команду, открывающую второй обычный `Store` поверх работающего сервиса.

`storage.go`: финансовые API сериализованы `financialMu`; запись через временный файл, fsync и rename; при ошибках до commit восстанавливается состояние в памяти. Это защищает файлы от разорванной записи, но не заменяет общий backup и optimistic concurrency между пользовательскими формами.

Существующий `Store.Export` использует `VACUUM INTO`, проверяет application ID, schema version, ledger checksums, integrity, foreign keys и изображения, публикует новый файл без перезаписи существующего. `VACUUM INTO` создаёт согласованный снимок; прерванный процесс не гарантирует пригодность незавершённого файла. Поэтому публиковать можно только проверенный результат. [SQLite: VACUUM INTO](https://www.sqlite.org/lang_vacuum.html).

### HTTP, авторизация и reverse proxy

В `server.go` middleware охватывает planner API, финансовые API и статику. Есть:

- точный allowlist Host и ограничение loopback peer для локального listener;
- HTTP Basic (`budget` + пароль от 32 символов), если пароль задан; постоянновременное сравнение;
- Origin / `Sec-Fetch-Site` / JSON Content-Type проверки;
- CSP, nosniff, запрет iframe, no-store;
- native TLS с минимумом TLS 1.2 при соответствующей конфигурации;
- явный список статических ресурсов, отсутствие раздачи всего рабочего каталога, защита от traversal и symlink ресурсов.

**Подтверждённый блокер:** Origin сравнивается со схемой upstream-запроса (`r.TLS`). За Serve браузер присылает HTTPS Origin, а локальный Go upstream получает HTTP. В изолированном smoke-тесте правильный HTTPS Origin дал 403; добавление `X-Forwarded-Proto: https` не помогло. Это ожидаемо для текущей реализации: forwarded headers специально не считаются доверенными.

**Вторая проблема:** loopback binding допускает пустой пароль. Serve тоже обращается с loopback, поэтому установка только Tailscale не превращает текущий local mode в обязательную авторизацию. При заданном пароле обхода через localhost в проверке не найдено: без credentials — 401, в том числе с подставленными forwarded headers.

Предлагаемый контракт конфигурации:

```text
BUDGET_ENV=production
BUDGET_ADDR=127.0.0.1:3001
BUDGET_DATA_DIR=/var/lib/simple-budget
BUDGET_BACKUP_DIR=/var/backups/simple-budget
BUDGET_PUBLIC_ORIGIN=https://<node>.<tailnet>.ts.net
BUDGET_ALLOWED_HOSTS=<node>.<tailnet>.ts.net
BUDGET_PROXY_MODE=loopback-https
BUDGET_PASSWORD_FILE=<systemd credential path>
BUDGET_MIGRATIONS=check-only
TZ=Europe/Moscow
```

Новые переменные здесь — проект интерфейса, **не действующие настройки текущего приложения**. В production требовать пароль/credential, публичный HTTPS origin, конкретный разрешённый Host и существующее provisioned хранилище. Отсутствие любого обязательного параметра — отказ старта.

В proxy mode Origin сравнивать с фиксированным `PUBLIC_ORIGIN`, а не со случайным X-Forwarded-Proto. Peer по-прежнему только loopback. Basic Auth проверять на всех маршрутах, включая localhost, backup и status; заголовки идентификации Tailscale не заменяют пароль. Origin без значения допустим для авторизованного CLI и обычных GET, но `Origin: null`/чужой origin отклоняются. Существующие JSON и cross-site проверки сохранить. Не вводить `AllowedHosts=*`, открытый CORS или доверие произвольному X-Forwarded-For.

На следующем этапе проверить, как **установленная версия Serve** передаёт Host и Authorization. Предпочтителен исходный публичный Host; если proxy его преобразует, требуется отдельная точная настройка upstream Host, а не расширение allowlist на любые значения. Этот нюанс не проверялся настоящим Tailscale в текущем аудите.

Планируемая настройка приватного проксирования после реализации и разрешения на VPS:

```sh
tailscale serve --bg http://127.0.0.1:3001
```

Serve с `--bg` возобновляет работу после перезапуска; это HTTPS-доступ внутри tailnet. Funnel не включать. Проверять `tailscale serve status` и фактическую недоступность приложения извне tailnet. [Tailscale Serve CLI](https://tailscale.com/docs/reference/tailscale-cli/serve).

Настроить MagicDNS/HTTPS, доступ только нужным устройствам/пользователю, восстановление доступа к Tailscale-аккаунту и порядок отзыва потерянного телефона. Выбрать нейтральное имя узла: имя TLS-сертификата попадает в публичный Certificate Transparency, хотя само приложение остаётся приватным. [Tailscale HTTPS](https://tailscale.com/docs/how-to/set-up-https-certificates).

Сохранить простой общий Basic Auth без новой системы пользователей. Ограничения: общий пароль на устройствах, нет индивидуальных ролей и полноценного logout с отзывом browser session. Пароль хранить в менеджере паролей; не передавать в shell arguments, URL, логах или backup. Добавить ограничение частоты неудачной авторизации с ограниченным объёмом памяти; учитывать, что все запросы Serve имеют один локальный peer, поэтому наивный per-IP ban заблокирует все устройства.

### API и несколько устройств

Planner обычные JSON ограничивает 128 KiB, upload иконок — 1500 KiB для JSON/base64; нормализованное изображение ≤1 MiB и ≤1024×1024. Пользовательский каталог ограничен 512 изображениями / 32 MiB, включая сохранённые для истории. В финансовых handlers используется прямой JSON decoder без общего body-size лимита: перед production добавить ограничение транспорта, не меняя финансовую бизнес-логику.

Planner использует `expected_revision`, `request_id`, previews и транзакции; их нельзя убрать при проксировании или retry. Финансовые операции защищены от одновременного повреждения файлов, **но не имеют эквивалентного revision/idempotency протокола**: устаревшее сохранение одного поля или всего списка категорий может перезаписать более новое, а повтор POST после потери ответа — создать ещё одну запись. Автоматические повторы изменяющих финансовых запросов не добавлять. Для первой серверной версии явно принять это ограничение; расширение финансового concurrency-контракта — отдельное решение, не часть миграции инфраструктуры.

Push-синхронизации между устройствами нет: открытая страница другого устройства может оставаться устаревшей до обновления/перехода. Planner revision предотвращает тихую запись поверх изменений, но не делает экран автоматически актуальным. В приёмке проверить сохранение черновика при 409 и актуальные данные после reload. Синхронизация файлов SQLite/JSON через облачный диск между Mac запрещена: все устройства работают с одним серверным HTTP API.

`WriteTimeout=30s` сейчас общий для ответов. Для крупных backup через мобильное соединение этого может не хватить. Будущие download handlers должны стримить с ограничением числа одновременных скачиваний и подходящим контролируемым write deadline; не читать весь архив в RAM и не отключать все таймауты приложения глобально.

### Миграции, фоновые операции, даты

Миграции `001–014` встроены; ledger и checksum проверяются; версия новее поддерживаемой отклоняется. Обратных SQL-миграций нет. Обычный startup сейчас сам мигрирует, поэтому тестовый запуск нового бинарника на production-пути уже является изменением данных.

В production предлагается проверка схемы на обычном startup и явная offline `admin migrate` только внутри deploy после backup. Старые миграции не редактировать. Для самой инфраструктуры новая бизнес-миграция предварительно не нужна.

Материализатор работает без открытой вкладки: немедленно после старта, затем раз в минуту; догоняющие порции — с паузой около секунды. Ограничения: 20 серий за страницу, до 100 циклов серии за порцию, для проектов — 5 циклов/до 2500 задач за транзакцию. Обычный горизонт — 59 дней вперёд; пользовательское расширение ограничено двумя годами, минимальные три выполнения считаются отдельно по циклам. Состояние, уникальность циклов, удалённые циклы, динамическая цепочка, паузы и ручное завершение сохраняются в БД.

Круглосуточная работа не требует cron для материализации. Нельзя одновременно запускать второй materializer через отдельный systemd timer. После длительного простоя catch-up может повысить нагрузку и увеличить журнал. Ошибки расчёта сохраняются по источнику без создания нового инцидента на каждый проход, но лог повторных ошибок нуждается в ограничении объёма.

Planner использует календарные даты Москвы, история — UTC timestamps, браузерный `P.today` — `Europe/Moscow`. tzdata встроена. В финансовых fallback даты операции и имени backup встречается `time.Now().Format(...)` без явной Москвы. Установка `TZ=Europe/Moscow` процессу устранит зависимость от UTC-настроек Ubuntu без изменения финансовых расчётов. Системные часы должны синхронизироваться; установка TZ не исправляет неверное время.

Встроены производственные календари только 2026/2027. Нельзя обещать автоматическую корректную работу рабочих дней РФ на произвольные следующие годы: импортировать опубликованный календарь через существующий механизм и контролировать ошибки недостающего года. Не подставлять обычные будни вместо официальных данных. Ежегодные правила «любые дни» не должны зависеть от этого импорта.

## 3. Предлагаемая серверная структура

```text
/opt/simple-budget/
  releases/<release-id>/budget       # root-owned, неизменяемый Linux binary
  releases/<release-id>/release.json
  current -> releases/<release-id>
  previous -> releases/<previous-id>
/etc/simple-budget/
  app.env                           # только несекретная production-конфигурация
  credentials/app-password         # root-only; в backup не включать
/var/lib/simple-budget/             # единственный каталог live data
  installation.json                # ID установки, окружение; без секретов
  planner.db [+ WAL/SHM/lock]
  data.json
  categories.json
/var/backups/simple-budget/
  daily/<backup-id>/                 # последние 7 успешных ежедневных копий
  pre-update/<backup-id>/            # отдельно ограниченные копии перед обновлением
  .staging/                         # незавершённые, не видны скачиванию
/run/simple-budget-admin/           # административный lock, root-only
```

Основной сервис — отдельный системный пользователь `budget`, без shell-login и sudo; данные 0700/0600. Бинарники и unit-файлы не должны быть ему доступны для записи. Проверенные backups принадлежат административному владельцу; сервису дать только чтение опубликованных архивов через отдельную группу, без права удаления/ротации. staging не раздаётся и недоступен сервису после формирования снимка. Права каталогов для group-read продумать отдельно: 0750/0640 только там, где действительно нужен download.

Веб-сервис не получает право `systemctl`, root или запись в release/credentials. SSH deploy-пользователь и системный пользователь приложения — разные учётные записи. Административный wrapper принимает фиксированные команды и проверенные значения, без `eval` и произвольных путей от web.

Секрет приложению передавать через `LoadCredential` и новый `PASSWORD_FILE`; systemd предоставляет credential через отдельный файловый путь. Совместимость директив сверить с фактической версией Ubuntu/systemd, которую сейчас не определяли. [systemd.exec: credentials](https://www.freedesktop.org/software/systemd/man/257/systemd.exec.html).

Предлагаемый `simple-budget.service`: `User=budget`, `UMask=0077`, `Restart=on-failure`, ограничение частоты рестартов, `TimeoutStopSec=90s`, `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, пустые capabilities; запись разрешена только в live data/необходимый runtime. Читать backups можно, писать нельзя. Не включать `PrivateNetwork=yes`: иначе локальный Serve не достучится. Финальный sandbox проверить SQLite WAL, lock и atomic rename, а не копировать набор ограничений вслепую.

Логи — journald, с ограничением размера и давности, без тел запросов, Authorization, персональных названий в технических метриках. На VPS не нужны Go toolchain, Git checkout, npm, browser binaries и build caches. Пакет `sqlite3` допустим как административная диагностика, но не runtime-зависимость приложения.

## 4. Единый резервный архив

### Состав

```text
manifest.json
planner.sqlite
finance/data.json                    # если существует
finance/categories.json              # если существует
settings/application.json            # только разрешённые несекретные параметры
RESTORE.txt
```

`manifest.json`: format version, ID установки, UTC timestamp и отображение Москвы, причина backup, release/commit, версия схемы и checksums миграций, список файлов, размеры и SHA-256, признаки отсутствующих legacy JSON, результат verification. Пользовательские иконки, настройки планировщика, история, внутренние шаблоны и календари уже внутри `planner.sqlite`. Если позднее появятся внешние пользовательские файлы, включать их только по явному registry/allowlist, а не рекурсивно архивировать весь `/var/lib`.

**Не включать:** WAL/SHM/lock, `.env`, пароль приложения, SSH-ключи, Tailscale state/auth keys/cert private keys, `/etc` целиком, логи, browser drafts, Git, исходники, node_modules, старые backups. Конфигурацию экспортировать по разрешённым полям, а не фильтром «удалить строки с password».

Базовый формат — `tar.gz` с умеренным/быстрым сжатием. Артефакт содержит персональные данные и сам по себе не зашифрован: HTTPS защищает передачу, права ФС — доступ на VPS. Restic не используется. На Mac хранить архив в защищённом пользовательском хранилище/FileVault; отдельное шифрование архива можно согласовать, но оно не является условием нынешней схемы и секрет шифрования не включается в архив.

### Согласованность: рекомендуемый простой механизм

Для версии 1.0 выбрать короткую остановку приложения на время **снятия** общего снимка. Онлайн-снимок одной SQLite не обеспечивает общую согласованность с двумя финансовыми JSON. Общей блокировки всех трёх хранилищ сейчас нет.

1. Административный wrapper получает единый lock backup/deploy/restore; проверяет installation ID, пути, права, свободные байты и inode. Зафиксировать, работал ли сервис до операции.
2. Корректно остановить сервис. Дождаться завершения HTTP, materializer и освобождения SQLite lock. Не убивать процесс после произвольных 2 секунд и не удалять WAL вручную.
3. Backup CLI получает существующий DB lock и открывает **существующую** БД без init, seed, миграций и фоновых задач. Для этого нужен новый безопасный maintenance-entrypoint; текущий `Store.Open` напрямую не подходит.
4. Переиспользовать проверяемый SQLite Export/VACUUM INTO; скопировать оба JSON и разрешённые настройки в уникальный staging. Состояние файлов остаётся неизменным на всём промежутке. Сохранить отсутствие необязательного JSON явно, не выдумывать новый пользовательский файл.
5. Проверить snapshot и JSON, fsync файлы/каталог; закрыть handles и DB lock. Перед возвратом HTTP сделать staging административно недоступным для записи процессу приложения.
6. Для ежедневного backup запустить сервис снова, если он работал до операции; проверить его состояние. Далее сжимать уже неизменяемый staging и проверять архив. Для deploy/restore не снимать maintenance до окончания соответствующей операции.
7. Прочитать архив заново: checksum каждого файла, JSON decoding, schema ledger, `integrity_check`, `foreign_key_check`, icon checksums; извлечь в отдельный ограниченный validation-dir и проверить пригодность к восстановлению без запуска фонового materializer.
8. После успешной проверки атомарно опубликовать backup ID, manifest и архив. Только затем выполнить ротацию. Ошибка не превращает staging в «успешную копию».

В wrapper необходима обработка ошибок/сигналов с восстановлением исходного состояния сервиса. При некорректной БД нельзя бесконечно перезапускать её или автоматически возвращать старые пользовательские данные. Остатки staging удаляются только после проверки их принадлежности операции, не общим `rm` по чужим каталогам.

Ожидается небольшой перерыв на текущем объёме, но его длительность **не измерена на VPS**. До включения timer измерить полный цикл и гарантировать restart при ошибке копирования. Если нулевая пауза станет обязательной, альтернативой будет общий online SnapshotCoordinator для HTTP и worker, с фиксированным порядком блокировок; это отдельное усложнение, не необходимое для первого запуска.

### Ежедневный запуск и ротация

- `simple-budget-backup.timer`: ежедневно 03:30 Europe/Moscow, `Persistent=true`, небольшой `RandomizedDelaySec`, один backup за дату; расписание подтвердить `systemd-analyze calendar` на целевой системе.
- Persistent timer догоняет пропущенный запуск после выключения, а не восстанавливает отсутствовавшие исторические данные за все пропущенные дни. [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html).
- Сохранять последние **7 успешно проверенных ежедневных** копий. При первом запуске их естественно меньше семи. Не считать ошибочный/пустой архив одной из семи.
- Pre-update backup обязательный и отдельный от daily. Предлагаемый предел — последние 2 успешные pre-update копии, включая копию для `previous`; pinned backup для незавершённого обновления не удалять. Частые deploy не должны вытеснять ежедневные точки.
- Удаление старого допускается только после публикации новой проверенной копии. При нехватке места не удалять последнюю исправную копию ради сомнительного нового архива; остановить операцию с понятной ошибкой.
- Статус: последнее успешное время, размер, verification, возраст, причина последней ошибки. При возрасте >26 часов — предупреждение в административном status и блоке backup приложения. Публичный monitoring endpoint без пароля не нужен.

### Скачивание через приложение

Существующий `/api/backup` и финансовую кнопку сохранить. Они продолжают скачивать `data.json`, без обещания полного восстановления планировщика.

Добавить отдельный компактный блок резервных копий в настройках:

- «Скачать резервную копию планировщика» — standalone SQLite из последнего проверенного полного backup;
- «Скачать полный резервный архив приложения» — опубликованный архив;
- рядом дата создания, размер, результат проверки и пояснение, что это состояние на указанное время.

Предлагаемые маршруты: `GET /api/admin/backups` (только безопасные метаданные), `GET /api/admin/backups/{id}/planner`, `GET /api/admin/backups/{id}/full`. Они проходят ту же обязательную app auth и Host/Origin политику. «admin» здесь не новая роль пользователя: восстановление по HTTP **не предоставляется**.

Скачивание не должно останавливать обслуживающий его процесс. По умолчанию отдаётся **последний готовый backup**, не обещается свежий снимок на секунду нажатия. Для свежей внешней копии перед важной операцией: `make backup`, затем скачать новый ID. Если нужен отдельный web-запуск свежего backup, согласовать его как дополнительную административную задачу; не давать веб-процессу sudo.

Файлы выбирать по проверенному backup ID из каталога опубликованных копий; не принимать файловый путь, не следовать symlink, не использовать общий FileServer. GET/HEAD/range должны оставаться авторизованными. `Content-Disposition: attachment`, фиксированные типы, no-store; скрыть staging. Ротация учитывает открытое скачивание. Planner SQLite можно потоково извлекать из архива без отдельной постоянной полной копии и без буферизации в RAM; допустим один ограниченный export-cache с учётом диска.

### Граница защиты

Семь копий на том же VPS защищают от ошибочного редактирования и части повреждений, **но не от потери VPS/диска/аккаунта провайдера**. При полной потере сервера восстановить можно только архив, ранее скачанный на Mac. RPO при локальном сбое — до суток при исправном timer; при потере сервера — время с последнего ручного внешнего скачивания. Рекомендация: скачать проверенный архив после первичного переноса, перед обновлениями и регулярно в период использования. Автоматического внешнего хранения не будет.

## 5. Восстановление и откат

### Восстановление архива

Текущий `Store.Restore` пригоден для совместимой исправной базы, но не закрывает повреждение live DB: до Restore обычный Open может завершиться ошибкой. Он также требует **точно текущую** версию схемы/ledger. Поэтому нужна отдельная административная процедура:

1. Получить lock; показать backup ID, время и установку, запросить подтверждение административной команды. Пока архив не проверен, live data не трогать.
2. Безопасно распаковать в новый staging на том же filesystem: запрет абсолютных путей, `..`, symlink/hardlink, неожиданных файлов; ограничения суммарного размера и числа записей, проверка свободного места.
3. Проверить manifest/checksums, SQLite application ID/ledger/integrity/FK/icons, финансовые JSON. Не исполнять ничего из архива.
4. Выбрать release, совместимый со схемой backup. Для старой схемы — сначала восстановление/проверка в staging, затем forward migration новой версией **на копии**, с повторной проверкой. Более новую схему старому бинарнику не скармливать.
5. Остановить сервис. Если live store ещё читается — сделать pre-restore backup. Повреждённые файлы сохранить в отдельной ограниченной quarantine, если хватает места; не называть их проверенным backup и не удалить автоматически.
6. Переключить целиком набор данных в maintenance. SQLite и JSON нельзя восстанавливать по одному при работающем сервере. Для нескольких rename иметь журнал стадий и fsync, чтобы прерванная операция восстанавливалась однозначно; не заявлять атомарность набора обычных rename без recovery-протокола.
7. Применить владельца/права, оставить серверные credentials вне восстановления, запустить подходящий release, проверить auth/readiness и контрольные данные. Сохранить предыдущий набор до успешной проверки.

Планировщик-only restore допустим отдельной явно выбранной командой: не менять финансы. Full restore восстанавливает весь согласованный набор. Для чужого installation ID нужен отдельный флаг осознанного переноса, а не автоматическое принятие.

### Потеря сервера

Создать чистый VPS, установить утверждённый release и units, заново настроить Tailscale/SSH/пароль, загрузить архив с Mac, выполнить описанный restore. Секретов в архиве нет, поэтому их потребуется создать/получить отдельно. Для восстановления нужно хранить соответствующий исходный commit/release вне потерянного VPS; ссылка на release и схема находятся в manifest. Проверка «архив распаковывается» недостаточна: до эксплуатации провести полный drill на отдельном data dir.

### Откат release

| Ситуация | Допустимый способ |
|---|---|
| Изменился только код, схема и JSON-контракт совместимы | Остановить, переключить `current` на previous, запустить; live data остаются |
| Новая версия повысила схему | Старый бинарник с новой БД не запускать. Восстановить **полный pre-update набор** и совместимый release либо выпустить forward fix |
| После обновления уже были пользовательские записи | Автоматический data rollback запрещён: показать риск потери изменений, сохранить новый набор, получить явное решение |
| Новая версия не прошла проверку до открытия доступа | Можно возвратить предобновлённый набор внутри закрытого maintenance window; зафиксировать результат |

Не делать down-migration путём изменения `user_version`, checksum или старых SQL. Не удалять историю для совместимости.

## 6. Ресурсы VPS

Метаданные текущей локальной установки, без чтения пользовательских записей:

| Показатель | Наблюдение |
|---|---|
| Linux binary без stripping | 17,43 MiB |
| Live SQLite файл | 5,08 MiB; это размер файла, не результат запроса к рабочей БД |
| Финансовые JSON вместе | Менее 7 KiB |
| Frontend resources | Около 642 KiB |
| RSS рабочего Mac-процесса, один замер | 19,63 MiB |
| RSS отдельного пустого Mac-сервера после 30 GET от 3 клиентов | 17,53 MiB |
| `.git` / `node_modules` | Около 328 MiB / 12,60 MiB; на VPS не переносить |

**Вывод:** 1 GB RAM выглядит достаточным для личного использования, но Mac idle RSS не является измерением Linux peak RAM. Не заявляется проверенная ёмкость для большой истории или восстановлений. Go binary на сервере только запускается, не компилируется; Playwright на VPS не устанавливается.

Начальные ориентиры для испытания, не окончательные гарантии: `GOMEMLIMIT=256MiB`, `MemoryHigh=384M`, `MemoryMax=512M` для app, ограничение отдельного backup job до 128–256 MiB, последовательное сжатие. Оставить память Ubuntu/tailscaled/journal и page cache. `GOMEMLIMIT` — мягкий бюджет Go runtime, не лимит всего RSS; MemoryMax — последняя защита, способная убить процесс. Утвердить значения после измерений. [systemd resource control](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control).

Swap 512 MiB–1 GiB можно рассмотреть как запас от кратких пиков после проверки диска; не использовать его как доказательство достаточной RAM. На 1 vCPU backup-сжатию назначить низкий CPU/IO приоритет, не запускать параллельные сборки/сканеры/restore.

15 GB провайдера — примерно 13,97 GiB до расходов файловой системы; реальную доступную ёмкость узнать позже. Бюджет считать так:

```text
занято = Ubuntu + Tailscale + releases(2) + live data + WAL
         + journal + 7*daily_archive + до 2*pre_update_archive

запас для операции = snapshot_staging + новый_архив + restore_validation_copy
                    + новый_release + запас_роста_при_миграции
                    + резерв_свободного_места
```

Планируемый минимальный резерв: максимум из 2 GiB и 15% доступного filesystem; отдельно проверить inode. Не начинать backup/deploy/restore, если после оценки временных копий резерв нарушится. Оценивать архив консервативно, без предположения хорошего сжатия. Копия для верификации и WAL также занимают место.

При нынешних примерно 5 MiB данных семь несжатых снимков — порядка 36 MiB. При росте до 500 MiB семь копий — уже около 3,5 GiB без pre-update, staging и ОС: потребуется повторная оценка. Историю и пользовательские данные ради свободного места автоматически не удалять.

Предложение: journal приложения ограничить суммарно примерно 100–200 MiB (глобальную политику journald согласовать с остальными службами), releases — current/previous, временные релизы и staging — по состоянию операций. Мониторить размер DB/WAL, backups, свободные байты/inode, дату последней проверки. Заполнение диска должно приводить к понятной ошибке сохранения/backup, а не выдаче ложного успеха.

## 8. Последовательность внедрения

1. **Локальная подготовка.** Утвердить решения ниже; реализовать fail-closed production config, canonical HTTPS origin, embed, credentials, maintenance/backup CLI. Никаких production-путей в тестах.
2. **Изолированный Linux.** На disposable VM/CI с Linux amd64 проверить flock, WAL, fsync/rename, systemd unit, restart, backup/restore и resource peak. SSH к рабочему VPS для этого не обязателен. Использовать синтетические данные.
3. **Проверка инфраструктурного release.** Полные Go/race/vet/frontend/browser проверки, security scan, manifest/checksum; протестировать обновление схемы и rollback на копии тестовых данных. Не считать audit cross-build заменой этого этапа.
4. **Первичная установка VPS, отдельный этап с разрешением.** Проверить `/etc/os-release`, uname, RAM, df/inode, filesystem, версии systemd/Tailscale, time sync. Настроить отдельные учётные записи, ключевой SSH и фиксированный административный wrapper. Проверить доступ через tailnet до ужесточения firewall; не потерять аварийную консоль провайдера. Не открывать 3001 или публичные 80/443 для приложения.
5. **Проверка на пустом синтетическом серверном data dir.** Auth через Serve с двух Mac/Android, негативные Host/Origin, restart/reboot, downloaded backup verification. Production-пользовательские данные ещё не переносить.
6. **Перенос пользователя.** Согласованно остановить локальный app, создать и проверить полный архив новым maintenance-механизмом, скачать/сохранить независимую копию на Mac, перенести только архив по SSH/Tailscale. Restore на VPS, сверка checksums/схемы и контрольных данных. До переключения определить единственный источник записи; не продолжать параллельно редактировать старый Mac store. Локальные исходные данные сохранить.
7. **Ввод в эксплуатацию.** После успешной проверки открыть доступ пользовательским устройствам; включить daily timer, выполнить первый backup и ручное скачивание, тест восстановления в отдельный каталог. Проверить reboot всего VPS.
8. **Последующие обновления.** Один deploy-lock; проверить release и свободное место; закрыть входящий пользовательский доступ/дождаться запросов; остановить app; сделать и проверить pre-update backup старым совместимым механизмом; испытать новую миграцию на staged copy; применить к live только в maintenance; атомарно переключить release; запустить и проверить readiness/auth; вернуть доступ. При ошибке до открытия доступа — контролируемый возврат старого согласованного набора. После допуска записей — никакого скрытого отката данных.

Обычный `/` с кодом 200 не является достаточной readiness-проверкой. Нужен авторизованный локальный status/CLI с release ID, ожидаемой схемой и успешным чтением хранилищ. Health-проверка не должна материализовывать серии или добавлять тестовую задачу в production. Первый materializer pass и отсутствие его ошибок проверяются отдельно.

## 9. Защита production от разработки и тестов

Главный барьер — физическое разделение: production вне checkout, отдельный Unix user, ни исходники, ни тесты на VPS не загружаются. `BUDGET_DATA_DIR` production никогда не наследуется командой тестов. Production credentials не доступны обычной локальной тестовой среде.

Текущие Go fixtures используют `t.TempDir`; Playwright создаёт `budget-planner-ui-*`, запускает на 31371, `reuseExistingServer=false`. Это хорошая основа. Но `PLANNER_TEST_DIR` можно задать извне, а browser-server проверяет только basename; нужно дополнить `realpath`, отсутствие symlink, расположение под temp root, одноразовый test marker и отказ при production installation marker. Проверить также вспомогательные review/capture runners.

Добавить два несовместимых marker-контракта: test и production. Тестовый запуск отказывается открывать production marker независимо от имени папки; production startup отказывается открывать test data или молча создавать отсутствующий store. Повторно используемые копии production для диагностики — только явно созданные приватные копии, с отдельным подтверждённым режимом, не общие fixtures и не публикуемые артефакты.

Не включать в deploy archive каталог проекта целиком. Не использовать `rsync --delete` на live data, `git clean` для эксплуатации, автоматическое скачивание production DB в тесты, symlink от data dir к репозиторию. Не менять рабочий Mac binary при `make release-linux` — выход только в игнорируемый `build/releases/<id>/`.

## 11. Решения и риски перед реализацией

**Блокирующие технические изменения:**

1. Исправить proxy Origin contract и обязательность auth в production. Не обходить проблему отключением проверок.
2. Встроить frontend, сделать release manifest/version и fail-closed data directory.
3. Реализовать общий согласованный backup, проверку, retention, offline restore и авторизованное скачивание.
4. Разделить startup и разрешённую миграцию; определить безопасный data rollback.
5. Защитить тестовые пути, добавить HTTP body/backup resource limits и измерить Linux memory/disk.

**Рекомендуемые решения для первой реализации:**

- Простой Basic Auth + Tailscale; без новой модели пользователей.
- Короткий ночной перерыв на общий snapshot; сжатие после возобновления app.
- 7 daily + максимум 2 pre-update, 2 releases; не урезать историю планировщика.
- Кнопки скачивают последний проверенный snapshot с явным timestamp; свежий backup запускается административной командой.
- Production TZ — Москва, timer — 03:30 Москвы, минимальный резерв диска — 2 GiB или 15%, что больше.
- Секреты восстанавливаются отдельно, не из пользовательского архива.

**Что уточнить перед первым подключением/установкой:** фактическая Ubuntu LTS и архитектура, доступный filesystem/free space, SSH способ и аварийная консоль, имя tailnet-узла, доступность ночного перерыва, место хранения ручных копий на Mac. Перед публикацией/распространением Git отдельно решить исторический `categories.json`. Эти вопросы не препятствовали выполнению аудита и не требовали подключения к серверу сейчас.

**Остаточные риски выбранной архитектуры:** потеря всех локальных backup при потере VPS; последняя внешняя точка зависит от ручного скачивания; общие credentials и отсутствие real-time обновления между устройствами; финансовый last-write-wins; рост истории/журнала и необходимость импорта производственных календарей будущих лет. Они описаны явно и не устраняются одним переносом Go binary на сервер.
