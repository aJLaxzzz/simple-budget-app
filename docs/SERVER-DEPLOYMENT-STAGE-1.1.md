# Server Deployment 1.0 — этап 1.1: Regression Cleanup

> Исторический отчёт этапа. Актуальный доступ: Caddy + публичный IPv4 HTTPS + обязательные mTLS и пароль. Tailscale/Serve не требуются; последующие решения — в [текущем плане](SERVER-DEPLOYMENT-PLAN.md) и [Backup & Recovery](SERVER-DEPLOYMENT-STAGE-2.md).

Дата проверки: 24–25 ноября 2026. Основа: `d67a07feff0772ba21182abfc5936496553bf26b` и незакоммиченные изменения Production Core. Этот отчёт дополняет `SERVER-DEPLOYMENT-STAGE-1.md`, не заменяя результаты предыдущего прогона.

## Границы и итог

Регрессионная приёмка завершена: **174/174 браузерных теста прошли на итоговом коде за 10,4 минуты**, без retries, skip и необработанных JavaScript-ошибок. Все 24 исходных сбоя разобраны и закрыты. Go, race, vet, 63 frontend unit-теста, Linux release и оба режима govulncheck прошли. Выполнение Linux-бинарника остаётся отдельным обязательным gate: доступного запущенного Linux runtime нет.

Рабочий процесс на порту 3001 не останавливался и не перезапускался; его бинарник, SQLite и финансовые JSON не использовались для тестирования и не заменялись. Изменены именно исходники frontend в репозитории, перечисленные ниже. VPS не посещался. Backup & Recovery и Deployment Automation не начинались. Новых API, миграций, зависимостей и пользовательских функций в этом этапе нет.

В продуктовый frontend внесены три точечных исправления:

1. В `recurrence-form.js` у повторения от выполнения без подтверждённой опоры больше не передаётся выдуманная `anchor.date` вместе с `kind: unconfirmed`. Это нарушало контракт движка и давало HTTP 422 при автоматическом предпросмотре единого редактора. Теперь до завершения показывается корректное объяснение отсутствия опоры, после завершения используется фактическая дата. Календарная арифметика и материализация не менялись.
2. В `views.js` действие «Повторять проект» размещено в строке дат обычного проекта. Ранее отдельная строка увеличивала шапку; попытка поместить действие рядом со всеми верхними кнопками тоже вызывала перенос строки при длинном названии. В итоговом варианте сохраняются название, статус, описание, даты, прогресс и все действия. Геометрический тест по-прежнему требует начало задач не ниже 500 px на 1440×900, в том числе с длинным свёрнутым описанием. Измерено **493,906 px** для обоих вариантов вместо исходных **514,703 px**; контрольный screenshot на 390 px просмотрен, переполнения нет.

3. В `core.js` переиспользуется единственный `Intl.DateTimeFormat` для Europe/Moscow. Раньше он заново создавался при каждом `P.today()` — в том числе тысячи раз при фильтрации и отрисовке задач. Кэшируется **форматтер, а не дата**: каждый вызов по-прежнему получает новое текущее время. Добавлен тест одной открытой вкладки при московской полуночи, смене года и високосном дне. Это точечное устранение подтверждённых затрат CPU, без смены архитектуры и логики дат.

## Метод разбора

Исходные ошибки взяты из `artifacts/production-core/checks/browser-full.log` и сохранённых failure-contexts. Для каждого сценария сопоставлены фактический DOM, API, код и согласованный UX Beta 3.2. Проверки не заменялись ожиданием произвольного ответа 200: сохранены проверки ID, дат, истории, черновиков, конфликтов, атомарности, точного повторного запроса после потери ответа и геометрии.

В предыдущем этапе на отдельном `git archive HEAD` воспроизведены четыре исходных сбоя: acceptance-flow, visual 1440, ux-actions и ux22. Они существовали до Production Core. Ошибка `unconfirmed + date` также находится непосредственно в исходном `git show HEAD:static/js/planner/recurrence-form.js`. Для остальных сценариев причина установлена по конкретному удалённому элементу и успешному эквивалентному пользовательскому пути; они не объявляются проверенными на baseline, если такого запуска не было.

После перехода московской даты с 24 на 25 ноября дополнительно устранена зависимость сценариев Beta 2 от дня написания теста. Для проверки «сегодня», трёх будущих выполнений и быстрого завершения данные рассчитываются от текущей даты Europe/Moscow; проверки точных исторических дат в других сценариях сохранены. Ожидаемые количества, дата фактического завершения и сортировка по-прежнему проверяются строго.

Ни одного нового `skip`, разрешённого `pageerror` или увеличения timeout ради зелёного результата не добавлено. Существующие два opt-in Go runners для приватной копии и большого визуального аудита не запускались: этот этап не использует реальные данные и не повторяет аудит.

## Перенос мышью и опора повторения

В `regression-cleanup.spec.cjs` добавлены семь сценариев:

- Обычная задача: реальный `dragTo`, запись новой даты без дополнительного диалога, неизменный крайний срок.
- Независимая серия: «Это и все следующие» и «Только следующие», подтверждение preview, прежние ID всех циклов. Вариант «Только это» уже проверяет обновлённый ux-actions.
- Дочерняя задача проекта: все три области, изменение относительного смещения 1 → 2 только для нужной области, обновление уже созданных проектов, сохранение ID и due_date. До подтверждения дата в БД прежняя.
- Предпросмотр completion-серии до и после реального завершения: проверяются HTTP 200, точный payload `anchor`, отсутствие 422 и точная дата следующего подтверждённого цикла после фактического завершения и три настоящих плановых задачи в материализаторе.

Снимок ID для проверки drag берётся **после** открытия календаря: календарь закономерно расширяет материализацию диапазона. Сравнивать количество экземпляров до открытия месяца и после переноса означало бы ошибочно считать допустимое расширение горизонта дублированием.

## Нагрузочная проверка

`zz-acceptance-load` теперь использует отдельный процесс с `GOMAXPROCS=1`, собственным случайным loopback-портом, test marker, пустыми финансовыми fixtures и временной SQLite. Исполняемый файл — только собранный тестовый binary из проверенного `PLANNER_TEST_DIR`. При завершении сервер получает SIGTERM; ненулевое завершение является ошибкой теста. Ни один путь рабочего приложения не используется.

Измеряются:

- Подготовка 100 проектов и 1000 задач через настоящий API.
- Отдельные GET tasks/projects/calendar: latency и размер ответа.
- От открытия каждого экрана до видимого известного элемента, сетевые запросы и интервал после получения данных до наблюдения готовности. Последний интервал включает JavaScript, layout и наблюдение Playwright, **не является чистым временем paint**.
- Реальный click задачи и готовность заполненного редактора.
- HTTP >=400, requestfailed и необработанные JS-ошибки.
- Несколько RSS samples серверного процесса и размеры DB/WAL/SHM. Samples не выдаются за абсолютный пик RAM.

Каждый экран открывается из `about:blank`, чтобы Resource Timing предыдущего SPA-перехода не загрязнял следующий замер. Ожидание известной задачи не заменено произвольной задержкой. Проверяется минимум 1000 отрисованных задач, отсутствие N отдельных запросов карточек при загрузке списка, раскрытие плотного календарного дня.

### Повтор исходного сбоя на сохранённой тестовой базе

Найдена сохранившаяся **синтетическая**, маркированная test-база исходного полного прогона этапа 1. Созданы отдельные согласованные копии через SQLite backup API, оригинальная тестовая база не редактировалась. Запущены старый сохранённый тестовый binary и новая сборка на собственном порту 31375, вне работающего приложения.

На этой базе оказалось 2924 активных задачи и 394 проекта; стандартный фильтр реально строил 2285 строк. Новые 1000 задач в эти replay-копии не добавлялись — они уже находились в сохранённой фикстуре. Таким образом, исходный тест фактически проверял совсем другой объём, чем было заявлено в его названии.

| Сборка / одна и та же исходная фикстура | Видимая задача, мс | Последний ответ данных, мс от navigation | Строк DOM | HTTP/JS ошибки |
|---|---:|---:|---:|---|
| Сохранённый binary исходного прогона | 5279 | 1748 | 2285 | 0 / 0 |
| До оптимизации форматтера, текущий frontend | 11425 | 2656 | 2285 | 0 / 0 |
| После переиспользования форматтера | 3380 | 1893,5 | 2285 | 0 / 0 |

Прогоны выполнялись при фоновых проверках; разницу 5,3 → 11,4 s нельзя выдавать за регрессию Production Core: в коде загрузки списка между этими двумя сборками изменений не было, а занятость CPU отличалась. При этом конкретный старый предел 5 s действительно воспроизведён, и значительная часть ожидания происходит после получения данных, в браузере.

Дополнительный изолированный microbenchmark Chrome на одинаковых 10 000 вызовах: прежний `P.today` — **8172,8 ms**, тот же расчёт с переиспользованием `Intl.DateTimeFormat` — **508,3 ms**. Результат согласуется с ускорением настоящего экрана на копии старой базы. Объекты/статусы/даты не заменялись заглушками. Этот замер не подменяет полный browser gate.

Ещё одна диагностическая копия состояния нового прогона с добавленными 1000 задачами содержала 2425 активных задач/438 проектов: 3581 ms до видимости, 1677 строк, без HTTP/JS ошибок. Это отдельная фикстура, её числа не смешиваются с исходными 2924 задачами.

В предварительных полных прогонах нового нагрузочного теста обнаружены `ERR_ABORTED`, созданные самим тестом: он уходил на `about:blank`, пока после закрытия редактора обновлялся список. Трасса показала переход через 26 ms после запуска трёх GET. Простого `networkidle` недостаточно: до обработки hashchange ещё действует состояние предыдущего документа. Теперь ожидания всех трёх конкретных ответов регистрируются перед закрытием редактора; затем проверяются завершение ответов, отсутствие редактора и новый отрисованный список. Только после этого тест покидает документ. Переход из плотного месяца в день также проверяет готовую временную сетку. Проверка отсутствия requestfailed **сохранена**, ошибки не добавлены в allowlist. Ожидание завершения запросов не включено в измерение скорости первоначальной отрисовки.

Это локальный benchmark, не обещание такой же скорости на Serv-Tech. GOMAXPROCS ограничивает одновременно исполняющийся Go-код, но не эмулирует CPU VPS, диск, память Linux или Android. На VPS обязательны повторный замер RSS/startup/catch-up под лимитами и проверка отсутствия OOM. SQL decoration содержит запросы на каждую задачу; при существенно большей нагрузке возможна пакетная выборка зависимостей. Серьёзная переработка хранения/виртуализация списка в этом этапе не выполнялась.

### Служебные сообщения при отмене запроса

В stderr итогового полного набора сохранились 7 строк `planner internal error (*errors.errorString)`. Они не скрыты из лога. Существующий `WriteAPIError` так же журналирует отменённый контекст HTTP-запроса; по одной строке без причины нельзя отличить его от другой внутренней ошибки.

После полного прогона отдельно повторён сценарий выбора иконки с trace на чистой базе (PASS, 4,1 s) и согласованной копии большой **синтетической test-базы** (PASS, 8,1 s). В этих trace нет HTTP >=400 или сетевых failures. Затем на той же маркированной копии намеренно прерваны три GET задач: получены три клиентских AbortError и две такие же строки stderr; следующий непрерванный запрос вернул 200, процесс штатно завершился. Результат — `cancellation-diagnostic.json`. Это подтверждает источник такого диагностического шума, но не доказывает причину каждой из семи исходных строк по отдельности. Это ограничение наблюдаемости отмечено для серверной приёмки; новых ошибок браузера или повреждения данных в проверках не обнаружено. Продуктовый обработчик и его логирование в этом этапе не менялись.

## govulncheck и Linux release

Проверены `golang.org/x/vuln@latest` и `@master`: оба разрешились в **v1.10.0**, commit `ef4cb2f7cae47fe3e21fc596455f694951867b29`, 17.11.2026. Анализатор сам собран Go **1.27.4**, зависимости инструмента включают `x/tools v0.53.0`. Это не попытка использовать старый binary. Проверка версии: Go module proxy и [официальный upstream](https://go.googlesource.com/vuln/+/refs/heads/master).

**Source-mode выполнен успешно:** `No vulnerabilities found` для Linux amd64. Блокер предыдущего этапа оказался несовпадением toolchain в окружении, а не отсутствием совместимой версии govulncheck.

Первоначально повторились ошибки `generic method requires go1.27 or later`, `new(...) requires go1.26 or later` и ошибки promoted fields в `internal/poll/splice_linux.go`. Исследован `x/tools/internal/gocommand/version.go`: для определения версии он запускает `go list ... unsafe` с `GO111MODULE=off`. В этом окружении `/usr/local/bin/go` — старый Go 1.25; при выключенных modules он возвращает release tags только до `go1.25`, **даже с `GOTOOLCHAIN=go1.27.4`**. Поэтому type checker получал неверную версию языка стандартной библиотеки.

После помещения `bin` настоящего Go 1.27.4 первым в PATH вспомогательная команда вернула release tags до go1.27, а полный source-mode прошёл. Анализатор, Go compiler, модуль приложения и его зависимости не патчились и не понижались. Воспроизводимый способ:

```sh
stage11_toolchain_bin="$(GOTOOLCHAIN=go1.27.4 go env GOROOT)/bin"
PATH="$stage11_toolchain_bin:$PATH" GOTOOLCHAIN=local \
  GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  /path/to/govulncheck ./...
```

`govulncheck` должен быть v1.10.0, собранный Go 1.27.4; в этой сессии использован `/tmp/budget-production-core-tools/govulncheck`. Проверка выполнена на итоговых исходниках. Изначальные логи неудачных запусков сохранены вместе с успешным `source-vuln-direct.log`, чтобы было видно, почему изменился вывод аудита.

Итоговый Linux release: `build/releases/d67a07feff07-20261124T205225Z/`. Статический stripped ELF Linux amd64, Go 1.27.4, embedded frontend, схема 14. В release только `budget` и `release.json`, 15 118 496 байт binary. SHA-256:

`ac8814dfb27e0fac7998666160735c7029d9f37467d85e7225d179e7fe7f4a2d`

Checksum пересчитан и совпадает с manifest. Binary-mode govulncheck на **этом файле**: `No vulnerabilities found`. Source-mode и binary-mode проверены отдельно: зелёный результат одного не подменяет другой.

## Оставшиеся ограничения

- При запуске govulncheck необходимо явно выбирать bin Go 1.27.4 в PATH: одного GOTOOLCHAIN поверх старого системного Go недостаточно. Source- и binary-mode прошли.
- Общий обработчик журналирует отменённый клиентом запрос как internal error без кода причины; этот шум воспроизведён отдельно. На серверной приёмке такие строки нельзя автоматически считать ни доказанными сбоями, ни безопасными отменами без корреляции запросов.
- Linux runtime, фактический Tailscale Serve и ресурсные пределы реального VPS требуют отдельной серверной приёмки.
- Нельзя переносить результаты Mac benchmark непосредственно на 865 MiB RAM VPS.
- В release `modified: true`, поскольку исходники не закоммичены. SHA-256 различает фактические сборки; требование чистого зафиксированного release остаётся для последующего этапа доставки.
- Следующие этапы не начаты. Результат этого задания — регрессионная основа, а не разрешение заменить работающий бинарник или мигрировать production.
