# Резервные копии и аварийное восстановление

Контракт приложения, формат 1, Server Deployment stage 2. Команды ниже предназначены для администратора **будущей серверной установки**. В этом этапе они проверены только на временных синтетических установках; systemd/SSH-обвязка ещё не установлена. Ни одна команда не требует Tailscale. Внешний доступ: Caddy, HTTPS по IPv4, mTLS устройства и пароль Go-приложения.

## Каталоги и права

Рекомендуемая структура следующего этапа:

```text
/opt/simple-budget/releases/<release>/budget      root:root, приложение не пишет
/etc/simple-budget/                             конфигурация/секреты, НЕ архивируются
/var/lib/simple-budget/                          root:budget, 0750, отдельный родитель
  live/                                         budget:budget, 0700
    installation.json                           0600
    planner.db / data.json / categories.json     0600
  .live.admin.lock                              административная блокировка установки
  .live.restore.json                            административный recovery journal
  .live.restore-<operation-id>/                  подготовленный набор
  .live.previous-<operation-id>/                 сохранённый прежний набор
/var/backups/simple-budget/                      root:budget, 0750
  repository.json                               root:budget, 0640
  daily/<backup-id>/backup.tar.gz + receipt.json
  pre-update/<backup-id>/backup.tar.gz + receipt.json
  manual/<backup-id>/backup.tar.gz + receipt.json
  schedule.json                                 наблюдение реального timer, 0640
  pins/                                         0700, защита rollback
  staging/                                      0700, неопубликованные данные
  admin.lock / operation.json                    0600
```

Публичные подкаталоги архива имеют 0750, готовые файлы — 0640. Администратор задаёт группу корня репозитория; публикация наследует её явно. Web-пользователь читает готовые копии, но не пишет в репозиторий, staging, release или конфигурацию. Production startup отвергает backup-root, владельцем которого является сам web-процесс, а также group/world-writable root. Проверка ACL и фактических прав разных Linux-пользователей обязательна на этапе 3. Не выдавать web-пользователю sudo.

`BUDGET_BACKUP_DIR=/var/backups/simple-budget` — новый необязательный параметр. Если он не задан, настройки честно показывают «Резервное копирование ещё не настроено». Если задан, репозиторий обязан уже существовать и соответствовать installation ID и окружению. Web-процесс ничего не инициализирует. Каталоги live и backups не могут совпадать или находиться один внутри другого. Пользовательские symlink и hardlink запрещены.

Приложение держит shared flock **на дескрипторе родительского каталога live**, административная операция — exclusive flock на том же inode. Поэтому блокировка переживает замену всего live-каталога. Нужен выделенный родитель: установки-соседи делят эту блокировку. Существующий SQLite flock сохраняется, в том числе для защиты от старого процесса без parent lease. Все backup/restore операции дополнительно сериализуются `admin.lock` репозитория и отдельным `.live.admin.lock` родительского каталога. Последний запрещает одновременный stop/resume даже при выборе разных репозиториев одной установки; check/migrate используют ту же административную блокировку. NFS/сетевые filesystem не поддерживаются.

## Формат полного архива

Обычный потоковый `tar.gz`, format_version=1. Разрешены ровно шесть regular entries в следующем порядке:

1. `manifest.json`.
2. `planner.db` — согласованный `VACUUM INTO`, без WAL/SHM, включает задачи, ID, историю, повторения, календари, оформление, ручной порядок и пользовательские иконки.
3. `data.json` — финансовые данные, исходные байты.
4. `categories.json` — категории, исходные байты, включая совместимый старый массив категорий.
5. `settings.json` — только разрешённая несекретная серверная настройка `timezone: Europe/Moscow`.
6. `RESTORE.txt` — краткая инструкция, читается без приложения.

Серверные настройки планировщика находятся в SQLite. Настройки интерфейса, локальные черновики и фильтры в localStorage конкретного браузера не входят в серверный архив. Host/Origin, пароль, Caddy/mTLS, ACME, SSH и systemd восстанавливаются отдельно; env и конфигурационные каталоги целиком не копируются.

Manifest содержит: формат, случайный backup ID (`YYYYMMDDTHHMMSSZ-16hex`), installation ID, UTC-время создания, причину (`daily`, `pre-update`, `manual`), build information приложения (application, Go, commit/revision, dirty, schema, embedded frontend), версию SQLite-схемы и упорядоченные SHA-256 миграций. Для каждого из пяти payload-файлов записаны имя, размер и SHA-256. Перечень успешно выполненных проверок: application/schema/ledger, SQLite integrity/FK, иконки, финансовая модель JSON, SHA-256 файлов. Версию приложения идентифицирует commit и признак dirty; для релиза необходим чистый зафиксированный commit.

`receipt.json` находится **рядом с архивом**, не внутри него: повторяет manifest, добавляет размер и SHA-256 всего tar.gz и время успешного повторного чтения. Self-checksum manifest не объявляется. Перед скачиванием весь архив повторно хешируется по тому же открытому файловому дескриптору, по которому передаётся клиенту.

Архив не содержит пароль, SSH/TLS/CA private keys, PKCS#12, ACME credentials, VPN state, WAL/SHM/lock, логи, исходники, Git, тестовые артефакты и другие backups. Включение по строгому списку, а не исключение нескольких известных имён. Архив **не зашифрован** и содержит личные данные: хранить его на защищённом Mac/зашифрованном диске. SHA-256 обнаруживает повреждение, но не заменяет цифровую подпись доверенного источника.

Ограничения формата: compressed и суммарный expanded payload до 8 GiB; каждый финансовый JSON до 16 MiB, 200 000 JSON-токенов и глубины 64; manifest до 64 KiB, settings до 4 KiB, инструкция до 64 KiB. JSON проверяется совместимым decoder текущей модели, без изменения исходных байтов. Абсолютные/вложенные пути, traversal, symlink, hardlink, PAX, лишние/повторные записи, неверный размер/хеш, несовместимая схема, неверный gzip CRC и хвост данных отвергаются. Архив не загружается целиком в память. Число JSON-токенов ограничивается до выделения массивов финансовой модели, чтобы небольшой по байтам массив миллионов пустых объектов не исчерпал RAM.

## Команды

Примеры используют локальные shell-переменные. Они не содержат пароль. Пути должны быть абсолютными; каталог backups предварительно создаёт администратор с указанными правами.

```sh
budget_bin=/opt/simple-budget/releases/current/budget
budget_live=/var/lib/simple-budget/live
budget_backups=/var/backups/simple-budget
budget_id='ЗАМЕНИТЕ_НА_INSTALLATION_ID' # из installation.json или проверенного manifest
```

`current` здесь обозначает выбранный release: deployment может разрешить свой указатель до реального пути бинарника. Пути **данных** через symlink запрещены.

Свежая ручная копия (остановить приложение заранее либо передать controller):

```sh
"$budget_bin" admin backup create --environment production \
  --data-dir "$budget_live" --backup-dir "$budget_backups" \
  --installation-id "$budget_id" --reason manual
```

Для ежедневной операции `--reason daily`; для обновления `--reason pre-update --protect`. `create` может инициализировать пустой backup-root; данные live должны уже существовать и пройти production marker/schema checks. Повтор daily в ту же московскую дату проверяет и возвращает существующую успешную копию, а не создаёт вторую. Для дополнительного свежего снимка в этот день используйте `manual` или `pre-update`.

```sh
"$budget_bin" admin backup list --backup-dir "$budget_backups" --installation-id "$budget_id"
"$budget_bin" admin backup status --backup-dir "$budget_backups" --installation-id "$budget_id"
"$budget_bin" admin backup verify --archive /absolute/budget-copy.tar.gz
"$budget_bin" admin backup rotate --backup-dir "$budget_backups" --installation-id "$budget_id"
"$budget_bin" admin backup protect --backup-dir "$budget_backups" --installation-id "$budget_id" --backup-id <id>
"$budget_bin" admin backup unprotect --backup-dir "$budget_backups" --installation-id "$budget_id" --backup-id <id> --confirm
```

Результаты — JSON, ошибка — ненулевой exit code. `list` перечисляет проверенные при публикации записи; `verify` повторно распаковывает и полностью проверяет архив. `status` не выполняет дорогое полное чтение payload, показывает последний успешный результат и stale после 26 часов. При скачивании хеш проверяется заново, повреждённый файл не отдаётся. `unprotect` использовать только когда ни rollback, ни незавершённая deployment-операция не зависят от копии.

### Остановка и возврат сервиса

Все create/restore принимают `--controller /absolute/trusted-executable`. Без controller работа разрешена только при свободных блокировках: CLI **не пытается сам найти или убить процесс**. Закройте сервис административно и после успеха запустите его. С controller CLI сохраняет исходное состояние, останавливает только работавший сервис и возвращает его после снимка, до сжатия; ранее остановленный сервис остаётся остановленным.

Исполняемый controller не может быть symlink или group/world writable. Он вызывается без shell, с двумя аргументами:

| Вызов | Успех (exit 0) означает |
|---|---|
| `status INSTALLATION_ID` | Это нужная установка, сервис запущен |
| `stopped INSTALLATION_ID` | Это нужная установка, сервис подтверждённо остановлен |
| `stop INSTALLATION_ID` | Сервис штатно остановлен, включая завершение процесса |
| `start INSTALLATION_ID` | Сервис запущен; wrapper должен дождаться authenticated readiness |

Если ни status, ни stopped не подтверждают состояние, операция отказывается. Timeout одного вызова 90 s; stderr/stdout controller не попадают в пользовательские логи. Wrapper обязан проверять ID/конфигурацию, не маскировать ошибки systemd как «остановлен», не зависеть от пути ещё отсутствующего live во время recovery и не расширять полномочия web-пользователя. Продуктовый wrapper/systemd unit будут реализованы на этапе 3. Тестовый controller запускает только отдельный временный сервер, включая реальный stop/start.

Последовательность create: preflight ресурсов/путей → admin lock → durable operation journal → подтверждённый stop → parent lease + SQLite lock → `VACUUM INTO` + JSON → полная проверка и fsync снимка → освобождение storage locks → возврат исходного состояния сервиса → streaming gzip → повторное чтение/проверка → receipt → pin при необходимости → атомарный rename готового каталога → fsync → ротация. Web видит только полностью опубликованный каталог. Неудачный backup не удаляет предыдущие исправные копии.

## Ротация и ресурсы

- 7 обычных успешных daily, до 2 обычных pre-update. Защищённые pins не учитываются в лимите и не удаляются.
- Manual не удаляются автоматически: администратор контролирует их количество и место. Это осознанное отличие от daily; бессрочно создавать manual на VPS 15 GiB нельзя.
- Pin записывается и синхронизируется **до** публикации защищённого архива. Незавершённая административная операция блокирует новую операцию/ротацию.
- Перед удалением проверяются хеши более новых сохраняемых архивов. Повреждённый заменяющий архив блокирует удаление старого. Открытые download FD остаются действительными при unlink старого архива; новый запрос к уже удалённому ID получает 404.
- `rotate` также удаляет только известные незавершённые каталоги `staging/.work-*`, `.verify-*`, `.retired-*` под admin lock и без operation journal. Неизвестные файлы сохраняются с ошибкой. Прежние live-каталоги и восстановительные кандидаты вне staging автоматически не удаляются.
- Резерв диска — `max(2 GiB, 15% ёмкости filesystem)` **после** учёта временного пространства. Проверяются и свободные inode (с запасом 64). Backup учитывает DB/WAL/JSON и до четырёх размеров источника; распаковка резервирует три expanded payload +64 MiB для снимка/SQLite migration journal. Оценка по сжатому размеру не используется как единственная.
- При недостатке места операция отказывается. История, пользовательские данные и защищённые копии ради места не удаляются. После успешного restore старый набор занимает дополнительное место до отдельного решения администратора.

Для VPS 15 GiB/около 8,5 GiB свободного: только базовый резерв около 2,25 GiB (точное значение по Statfs), затем фактический объём поколений/стейджинга. Текущая пользовательская база в тестах не измерялась. Перед production-переносом оценить реальные размеры, runtime RSS и запас с Caddy/Ubuntu на 864 MiB RAM +1,7 GiB swap.

## Восстановление полного архива

1. Получить сохранённый на Mac tar.gz по защищённому административному каналу. Не распаковывать его поверх live.
2. Установить совместимый бинарник, отдельно настроить доступ/секреты. Выполнить `version` и `admin backup verify`. Сверить installation ID и происхождение архива. Не выполнять `admin init` поверх каталога, куда восстанавливаются данные.
3. Подготовить выделенный родитель и backup-root. Для новой установки можно передать отсутствующий live; при root-команде рекомендуется заранее создать **пустой live 0700 с владельцем будущего приложения**, чтобы restore перенёс владельца на новый набор. Существующий непустой live обязан иметь тот же ID и environment. Другой ID не переопределяется флагом force.
4. Остановить сервис либо передать проверенный controller. Выполнить явную административную команду:

```sh
"$budget_bin" admin backup restore --environment production \
  --data-dir "$budget_live" --backup-dir "$budget_backups" \
  --installation-id "$budget_id" --archive /absolute/budget-copy.tar.gz \
  --scope full --confirm
```

5. CLI сначала распаковывает отдельный private-кандидат и проверяет все SHA-256/SQLite/JSON. Старую совместимую схему мигрирует **на кандидате**, проверяя ledger/DDL до и после. Более новая или изменённая схема отвергается. Схема live не мигрирует при обычном запуске.
6. После stop и storage locks: формируется marker, сохраняются UID/GID live, проверяется весь кандидат; записывается sibling restore journal; старый live переименовывается в `.live.previous-ID`, кандидат — в live. После каждого перехода — fsync родителя и запись фазы. Это **не объявляется атомарным переключением нескольких файлов**: целостность обеспечивает recovery-протокол, запрет startup при journal и сохранённый прежний каталог.
7. После проверки нового live journal удаляется, блокировки освобождаются, исходно работавший сервис запускается. Проверить `ready`, ID/историю, календарь, финансовые данные. Сохранённый путь прежних данных возвращается в `previous_data` (при новой установке каталог может отсутствовать). Не удалять его до успешной приёмки.

Повреждённая SQLite не должна успешно открываться для восстановления: проверяются marker, допустимые типы файлов и flock, но не её содержимое. Неизвестные файлы внутри live не удаляются: операция откажет до stop, предложив безопасно разобраться с ними. Восстановление заменяет весь набор, а не объединяет изменения нескольких поколений.

### Только планировщик

Та же команда с `--scope planner` берёт SQLite из полного проверенного архива и сохраняет **текущие** `data.json` и `categories.json` побайтно. Нужны существующая установка с тем же ID и исправные финансовые JSON. Между финансовой моделью и planner нет внешних ссылок; режим не переносит финансовые записи из другого поколения.

Отдельная кнопка планировщика скачивает raw SQLite последнего full backup. Такой файл полезен как проверенный экспорт, но в нём нет installation ID/manifest полного приложения. Новый защищённый CLI restore намеренно принимает полный tar.gz, в том числе для `--scope planner`; для аварийного восстановления сохраняйте **полный бэкап**, а не только `.db`. Импорт произвольной SQLite без manifest/проверки происхождения в новый CLI не добавлен.

### Прерывание и recovery

SIGINT/SIGTERM отменяют потоковую работу и запускают возврат исходного состояния сервиса; непроверенный архив не публикуется. SIGKILL/потеря питания не могут выполнить defer: сохраняются operation journal и, если переключение началось, restore journal. Следующий обычный startup откажет при незавершённом переключении. Не удаляйте журналы вручную.

```sh
"$budget_bin" admin backup recover --environment production \
  --data-dir "$budget_live" --backup-dir "$budget_backups" \
  --installation-id "$budget_id" --decision finish --confirm
# Или --decision rollback для возврата прежнего набора.
```

`finish` проверяет и выбирает восстановленный набор; `rollback` возвращает прежний. Если прежняя база была повреждена, откат не сделает её исправной: нужен finish исправного кандидата либо повторное restore. Если в момент SIGKILL ещё не началось переключение, recover возвращает исходное состояние сервиса. Если сжатие backup прервано уже после resume, operation journal отсутствует: использовать `rotate` для безопасной очистки неопубликованного staging.

Каталоги `.live.previous-*` и оставшиеся `.live.restore-*` сохраняются для разбирательства и не входят в daily retention. После ручной проверки отсутствия journal/использования, актуальной внешней копии и успешной работы выбранной установки администратор может отдельно разрешить их удаление. Автоматический массовый `rm` в этом этапе не добавлен. При неоднозначном расположении каталогов recovery отказывает, не угадывает нужное поколение.

## UI и HTTP

Путь: **Планы → шестерёнка → Резервные копии**, `/#/plans/settings?section=backups`.

- Финансовая кнопка `/api/backup` сохранена.
- `GET /api/backups/status`: дата/размер/проверка, количество daily, предупреждение, состояние автоматизации.
- `GET|HEAD /api/backups/<verified-id>/full`: готовый tar.gz, Range поддерживается.
- `GET|HEAD /api/backups/<verified-id>/planner`: SQLite из этого же архива, Range не поддерживается (416).
- Изменяющих, create или restore HTTP endpoints нет. Новый backup создаёт только администратор.

Все endpoints проходят общий пароль, точный Host/Origin, Fetch Metadata и security headers. Нет path-параметров; staging и backup-root не раздаются статическим сервером. Attachment/no-store, потоковая передача; максимум **2** одновременных скачивания, затем 429/Retry-After. До начала передачи проверяется SHA-256 архива. Общий предел download 20 минут, idle write deadline 90 секунд; остальные HTTP timeouts прежние. Через будущий Caddy проверить отсутствие меньшего proxy timeout, корректные Host/Authorization и mTLS, включая Range. Для медленной/оборванной связи полный tar.gz удобнее raw SQLite благодаря Range.

Состояние timer не выводится из одного наличия архива. Пока `schedule.json` отсутствует — «Автоматическое копирование ещё не установлено». После реального включения/проверки systemd обвязка этапа 3 обновляет наблюдение:

```sh
"$budget_bin" admin backup schedule --backup-dir "$budget_backups" \
  --installation-id "$budget_id" --enabled --next-at <фактический RFC3339 NextElapse>
```

Это **не установка timer**. Только наблюдение с source=systemd, возрастом <24 h и будущим next_at позволяет UI показать «Включено». Просроченное/невалидное наблюдение — «Состояние требует проверки». Без `--enabled` записывается выключенное/неподтверждённое состояние, а не создаётся расписание.

## Контракт этапа Deployment Automation

| Будущая команда | Обязательные шаги |
|---|---|
| `make backup` | SSH-администратор → create manual с доверенным controller → проверить exit/receipt → показать ID/размер |
| `make fetch-backup` | Получить status/list → выбрать ID → скачать готовый архив (SSH либо защищённый HTTPS) → локальный verify, не передавать секреты в CLI/log |
| `make restore` | Показать ID/дату/область → явное подтверждение → verify → restore с controller → readiness и сохранение previous_data |
| `make status` | app readiness, backup age/space/pins, actual systemd timer, Caddy/certificate status отдельно |
| `make deploy` | Создать **pre-update --protect** старым совместимым бинарником → сохранить backup/release ID в deployment journal → stop/migrate/переключить release/start → readiness; защита rollback не снимается до решения политики двух releases |
| Daily timer | `OnCalendar=*-*-* 03:30:00 Europe/Moscow`, Persistent; create daily с controller; после подтверждённого результата обновить next_at, проверить место/возраст; до 7 успешных daily |

Если ОС была выключена, Persistent догоняет пропущенный запуск, но не создаёт фиктивные архивы за отсутствовавшие дни. Timer, controller, users/groups, unit hardening, SSH, Makefile и rollback deployment пока не установлены/не реализованы как production-обвязка. В stage 2 реализован контракт и локальное ядро этих операций.

После полной потери VPS восстановить данные из архива и отдельно: SSH/пользователей/firewall, пароль приложения, канонический IPv4 Host/Origin, Caddy и получение нового публичного сертификата, публичную клиентскую CA/allowlist. Закрытый ключ клиентской CA остаётся на административном Mac; если ключ устройства потерян, выпустить новое удостоверение и исключить старое. Архив приложения не заменяет внешний защищённый реестр доступа.
