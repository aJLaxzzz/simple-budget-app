# Server Deployment 1.0 — этап 2: Backup & Recovery

Дата: 25 ноября 2026. Исходная регрессионная основа: этап 1.1, 174 browser / 63 frontend. Код этапа 2 находится в рабочем дереве поверх `d67a07feff0772ba21182abfc5936496553bf26b`. Схема SQLite остаётся **14**, старые миграции не менялись, новых зависимостей нет.

## Реализация

Добавлено локальное ядро полного backup/restore, административные команды и компактный экран скачивания готовых копий. Архивирование независимо от reverse proxy. Актуальная архитектура доступа: **Caddy → HTTPS по IPv4 → mTLS устройства → обязательный пароль Go**, upstream `127.0.0.1:3001`. Tailscale не требуется. Caddy, сертификаты, VPS, systemd timer и SSH deployment в этом этапе не настраивались.

Рабочее приложение на 3001, SQLite и финансовые JSON не использовались для тестов; процесс не останавливался и не перезапускался. Файл `./budget` пользователь самостоятельно пересобрал параллельно тестам и подтвердил это в переписке; агент его не заменял, поэтому неизменность файла за весь период не заявляется. Все новые операции выполнялись на синтетических временных каталогах. Production-код не внедряет финансовую аналитику и не меняет финансовую модель.

Подробная инструкция: [BACKUP-RECOVERY.md](BACKUP-RECOVERY.md). Она содержит формат tar.gz, права, controller-контракт, все команды, восстановление после полной потери сервера, незавершённого переключения или повреждения SQLite, а также контракт будущих Makefile-команд.

### Архив и проверка

Строгий allowlist из manifest и пяти payload-файлов: standalone `planner.db` через существующий `Store.Export/VACUUM INTO`, исходные `data.json`/`categories.json`, разрешённые несекретные settings и инструкция. Иконки уже находятся в SQLite. Manifest включает installation ID, случайный backup ID, UTC-время/причину, build version/commit, схему и checksums миграций, размеры/SHA-256 файлов и результаты проверок. Опубликованный receipt дополнительно содержит SHA-256 всего tar.gz и время повторной проверки.

Проверяются application ID, user_version, migration ledger/checksums, фактическая DDL по встроенным миграциям, integrity_check, foreign_key_check, иконки и текущая JSON-модель. Архив повторно читается целиком до публикации. Новая проверка DDL не доверяет одному только manifest или подменённому ledger. Кэшируется лишь успешно построенный эталон DDL неизменяемых встроенных миграций по версии схемы; ни один результат проверки пользовательского снимка не кэшируется. Старые схемы проверяются по соответствующему префиксу миграций; forward migration проходит только на отдельном кандидате.

Нет рекурсивного копирования каталогов конфигурации: пароль, SSH/TLS/CA private keys, P12, ACME state, WAL/SHM/lock, Git, логи и соседние backups не входят в архив. Настройки интерфейса, остающиеся в localStorage устройств, не являются серверными данными. Архив не шифруется; пользователь хранит скачанную копию на защищённом Mac.

### Согласованность и прерывание

`admin.lock` репозитория и `.live.admin.lock` установки сериализуют операции, в том числе при разных backup-root; shared/exclusive parent-directory flock защищает live-каталог при его замене, прежний SQLite flock сохранён. Опциональный доверенный controller подтверждает installation ID, исходное состояние сервиса, stop/start/readiness. Без controller требуется заранее остановленное приложение; занятое хранилище не открывается вторым Store.

После stop создаются и проверяются SQLite/JSON, выполняется fsync, освобождаются storage locks и возобновляется исходно работавший сервис. Сжатие и повторная проверка выполняются уже после resume. Архив и receipt публикуются атомарным rename готового каталога. Защита rollback записывается до публикации; неудачная операция не ротирует старые исправные копии.

Restore сначала готовит полный проверенный кандидат вне live. Journal фиксирует фазы prepared → old-moved → new-live; после каждого rename синхронизируется родитель. До удаления journal startup отказывает. Прежний каталог сохраняется. Это recovery-протокол, **не заявление об атомарности нескольких последовательных rename**. Ошибка штатно откатывает переход; SIGKILL/потеря питания требует явного `recover --decision finish|rollback --confirm`.

Для повреждённой SQLite достаточно marker/ID и свободных блокировок, успешное открытие старой базы не требуется. Полный restore работает в новой установке по одному архиву и совместимому бинарнику. `--scope planner` берёт SQLite из полного архива, оставляя текущие финансовые JSON побайтно. Другой installation ID, неизвестные live-файлы, небезопасные ссылки или несовместимая схема блокируют операцию до изменения данных.

### Ротация и ресурсы

Сохраняются 7 обычных daily и 2 обычных pre-update, pins защищены сверх лимита. Для обновления предусмотрен `create --reason pre-update --protect`; deployment journal/rollback release — следующий этап. Daily идемпотентен в пределах московской календарной даты. Manual не удаляются автоматически. Старые live-наборы после restore сохраняются до отдельного решения.

Свободное место проверяется через Statfs с резервом `max(2 GiB, 15%)`, дополнительным staging/распаковкой/SQLite migration journal и запасом inode. Expanded размер проверяется отдельно от compressed. gzip, hash, copy и HTTP работают потоково; archive не читается целиком в память. Лимиты формата/передачи и политика очистки staging перечислены в инструкции.

### UI и HTTP

**Планы → шестерёнка → Резервные копии**. Дата/время МСК, размер, успешная проверка, количество daily, состояние автоматизации, следующий запуск при известном фактическом расписании и предупреждение об отсутствии/возрасте >26 часов (порог уточнён на этапе 3). Кнопки скачивают готовые копии; свежего backup или restore через HTTP нет. Финансовый JSON сохранён.

| Endpoint | Поведение |
|---|---|
| `GET/HEAD /api/backups/status` | Read-only metadata, отсутствие конфигурации не маскируется успехом backup |
| `GET/HEAD /api/backups/<id>/full` | Проверенный полный tar.gz, attachment/no-store, Range |
| `GET/HEAD /api/backups/<id>/planner` | SQLite из того же архива, attachment/no-store, Range 416 |

Все маршруты внутри существующего auth/Host/Origin middleware. Выбор только по проверяемому ID, не по пути. До передачи SHA-256 проверяется по тому же FD; ротация не обрывает уже открытый файл. Максимум два параллельных download, 429 для остальных. До 20 минут на скачивание, 90 секунд на запись без прогресса; после длинного download общий write deadline восстанавливается относительно фактического момента завершения, а не начала запроса. Web-процесс не получает sudo или запись в административный репозиторий.

Автоматическое копирование пока **не установлено**. `schedule` записывает лишь наблюдение будущего реального systemd timer; только свежее наблюдение с будущим next_at даёт статус «Включено». Снимок экрана с этим статусом использует явно синтетическую тестовую запись, не свидетельствует об установленном timer.

CLI не читает HTTP password для backup-операций; доступ к ним определяется административными правами ОС и явным installation ID/подтверждением restore. Production units, controller для systemd, SSH и Makefile не добавлены преждевременно.

## Целевые проверки

1. Round-trip полного архива сравнивает содержимое **всех пользовательских таблиц** (упорядоченные fingerprints), ID, историю, дерево, периоды работы, настоящие ежегодные выполнения, импортированный календарь, пользовательскую PNG-иконку и исходные байты финансовых JSON.
2. Новая установка из одного архива, восстановление повреждённой SQLite, planner-only без изменения текущих финансов.
3. Совместимый архив схемы 7 → текущая 14 на копии, сохранение ID; исходный снимок остаётся v7.
4. Повреждённые checksum/gzip, обрезанный архив, неверный installation ID, неверный application/DDL/ledger/icon checksum, oversized entries, traversal/absolute paths/symlink/hardlink/неожиданные записи отвергаются.
5. 9 daily, protected pin, daily replay и 4 pre-update подтверждают политику 7/2 + protection; отказ места/публикации не удаляет предыдущие исправные копии.
6. Конкурентный администратор и работающий parent lease блокируют maintenance. Открытый download FD остаётся читаемым после ротации. Третий параллельный download получает 429.
7. Ошибки в каждой фазе restore откатываются. Отдельный тестовый subprocess **реально убивается SIGKILL** на трёх границах; все шесть комбинаций finish/rollback восстанавливают нужное поколение, обычный startup до recovery запрещён.
8. Controller-tests подтверждают stop во время snapshot и resume до compression, включая ошибки. Браузерный helper проверяет настоящий stop/start другого тестового Go-процесса и смену PID.
9. Неизвестные live-файлы сохраняются; отменённая операция не публикует архив; prod marker блокирует test snapshot до SQLite-open.
10. Resource-tests проверяют точные границы 2 GiB/15%, inode, размеры распаковки и сложность JSON до выделения финансовой модели; отдельный writer-test с 32 MiB входа проверяет отсутствие полного буфера.
11. Browser: auth 401 для всех новых маршрутов, прямой static/path доступ 404, настоящий download и повторная CLI verify, SQLite magic, Range, no-store, честный статус timer, 1440 и 390 px.

## Ограничения и следующий этап

- Linux runtime не запускался: Docker не запускался без согласования, к VPS не подключались. Cross-build — отдельная проверка, не runtime. На Linux обязательны реальные flock/WAL, uid/gid/read-only web, длительный download, stop/reboot/power-loss recovery и ресурсный замер под ограничениями VPS.
- Ежедневный 03:30 Europe/Moscow timer, systemd controller/units, SSH/Makefile, предобновительный workflow и две версии release остаются этапом Deployment Automation. Ядро CLI/защита pre-update/pins готовы; никто не обещает уже работающий nightly backup.
- Caddy, IP certificate renewal, mTLS/отзыв и device acceptance отдельно; backup не содержит секретов доступа. Проверить download через реальный proxy до настоящих данных.
- Raw SQLite download не содержит installation ID/manifest; защищённый CLI восстанавливает планировщик из полного tar.gz (`--scope planner`). Для аварийной внешней копии скачивать полный архив.
- Архив format 1 не принимает данные >8 GiB/JSON >16 MiB. Резерв диска может отказать существенно раньше на VPS 15 GiB; это безопасный отказ, а не повод автоматически удалять историю.
- Manual/pinned copies и старые restore-каталоги требуют административного контроля места и осознанного снятия защиты/очистки. Автоматическое удаление неизвестных файлов не добавлено.
- Сбой питания не может автоматически исполнить defer; требуется recovery. Неоднозначные каталоги сохраняются, сервис не запускается поверх сомнительного набора.
