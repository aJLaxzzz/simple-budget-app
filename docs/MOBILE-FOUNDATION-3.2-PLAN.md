Статус: **предложение для согласования, реализация не начата**. Основание — текущий код после принятого Stage 3.1. Целевые устройства: OnePlus 13 / Chrome и Mac / Chrome. На шаге планирования код, данные и инфраструктура не менялись; тесты не запускались.

### Конкретные препятствия

- Мобильные правила распределены между `planner.css`, `calendar.css`, `navigation.css`: 390, 600, 640, 700, 768, 900, 1050 px. Есть взаимно перекрывающиеся правила: сетка полей на 390 px сначала становится одноколоночной, позднее снова двухколоночной.
- Общие вкладки сейчас flex-строка с небольшим gap: свободное место остаётся справа. В мобильном варианте они просто переносятся под верхнюю строку.
- Разные оболочки форм проекта и задачи затрудняют единое поведение сохранения, прокрутки и Back.
- `P.closeEditor()` сейчас меняет hash на базовый маршрут панели; отмена перехода в `P.guardForm` использует `pushState`. Нужно проверить цепочки Back/Forward и исключить повторное открытие закрытой формы или лишние записи при отмене ухода.
- Редакторы автоматически фокусируют название. На телефоне это может сразу открыть клавиатуру даже при просмотре существующей задачи.
- Toast находится снизу на 22 px, индикатор синхронизации — на 8 px; после появления нижней навигации они будут с ней пересекаться.
- Календарь уже имеет собственные мобильные ветки 700/900 px и `layoutKey`, включающий ширину окна. Его resize может вызвать `P.refresh()`. Во время открытой формы обновление пропускается; после закрытия нужно согласовать отложенное изменение компоновки.

Полная переработка CSS, модулей `beta*`, роутера или финансовых экранов для этих задач не нужна.

## 2. Выбранная архитектура оболочки

**Один DOM и одни обработчики; разные CSS-компоновки.** Не создавать пары `MobileTaskEditor` / `DesktopTaskEditor` и два экземпляра одной навигации.

Desktop: переключатель модуля слева → равномерно распределённые основные вкладки в доступной центральной области → существующие инструменты, настройки и STG справа. Для вкладок использовать равные колонки внутри выделенного им пространства; не растягивать всю верхнюю панель за пределы текущего контейнера. Финансовый поиск и бэкап сохраняются.

Mobile, модуль Планы:

1. Компактная верхняя панель: переключатель модуля, настройки, STG. Отдельное повторение названия раздела добавлять только там, где без него теряется контекст.
2. Контент и существующие контекстные вкладки выбранного раздела.
3. Постоянная нижняя навигация: Календарь / Задачи / Проекты / Внимание. Четыре равные области, иконки существующего набора, короткие подписи, `aria-current`, счётчик внимания. Без глобальной кнопки «+».

Тот же `#module-tabs` на desktop находится в верхней панели, на mobile — фиксируется снизу через CSS. В мобильном header убрать `backdrop-filter` и не добавлять transform/filter/contain, создающие для его fixed-потомка отдельный containing block. Верхняя панель получает непрозрачный фон текущей палитры. Это позволяет обойтись без перемещения DOM при resize и без второго меню.

Mobile, модуль Бюджет: тот же переключатель и общие инструменты; существующие бюджетные вкладки компактно располагаются под верхней строкой. Поиск и бэкап остаются доступными. Нижняя навигация планировщика здесь не показывается. Новую финансовую навигационную модель не вводим.

Основная страница продолжает прокручиваться документом. Не превращать всё приложение в фиксированный контейнер с новым внутренним scroll root: от `window.scrollY` уже зависят возврат из карточек и Live Sync. Таблицы/календарные сетки при необходимости имеют локальную прокрутку, но не растягивают всю страницу.

## 3. Breakpoints

| Ширина CSS viewport | Поведение общей оболочки |
|---|---|
| 320–767 px | Мобильная панель, нижняя навигация Планы, полноэкранные редакторы, поля по умолчанию в одну колонку |
| 768–1023 px | Компактный desktop: верхние вкладки, боковой редактор; сокращённые отступы, допустим отдельный ряд финансовых инструментов |
| От 1024 px | Полный desktop, равномерные вкладки, текущая ширина рабочих контейнеров и боковых редакторов |

768 px — граница, выбранная по месту для четырёх вкладок, переключателя и инструментов, а не по модели устройства. 1024 px меняет плотность, но не состояние/маршрут. 480 px — тестовая точка, не обязательный новый breakpoint. `pointer: coarse` может увеличивать зоны нажатия независимо от ширины; user-agent и физическое разрешение OnePlus не используются.

Унифицировать только правила оболочки и общих форм. Существующие calendar-specific границы 700/900 px оставить до Stage 3.4; не выполнять массовую замену всех media queries. Проверять границы 767/768 и 1023/1024 отдельно.

Палитра, умеренные скругления, иконки и типографика берутся из текущих CSS-переменных. Новые библиотеки не нужны.

## 5. Полноэкранный редактор, черновик и история

Добавить небольшой общий helper оболочки рядом с `P.dialog` в `planner/core.js`: создать dialog, header, прокручиваемый body и footer, принять существующую форму и callback закрытия. Это helper представления, а не новый менеджер бизнес-состояния.

Подключить редактор задачи, редактор существующего проекта и создание проекта к этой оболочке. Для template-based создания использовать существующий `workflow.host`, при необходимости добавить минимальную передачу host из `beta3.js`. Не менять сериализацию, scope, preview/apply, request_id и expected_revision.

На mobile header содержит понятное «Назад» и название формы; footer — действующую кнопку сохранения. На desktop сохраняются боковая панель и закрытие. Во время полного редактора нижняя навигация недоступна и не конкурирует с сохранением; native modal обеспечивает недоступность фонового интерфейса.

Resize меняет размеры **того же dialog/form**, без удаления DOM, повторного API GET и реконструкции черновика. Сохраняются введённые значения, раскрытия, вкладка редактора, выделение текста и прокрутка body. Не менять область применения действий в зависимости от viewport.

Закрытие кнопкой, Escape, системным Back и переходом по ссылке должно сходиться в существующий guard. Для редактора, открытого из приложения, хранить минимальную отметку происхождения в namespaced `history.state`: Back возвращает на исходный маршрут. Для прямой ссылки без собственного предыдущего entry закрытие заменяет URL на `P.panelURL()`, а не уводит пользователя с сайта. Не создавать новый history entry на resize, refresh или каждый показ подтверждения. Не перехватывать глобально Back и не удерживать пользователя в приложении.

Отдельно проверить topmost dialog и вложенные подтверждения: закрывается верхний слой; родительская форма сохраняется. Когда клавиатура открыта, её системное закрытие не должно считаться командой отмены формы. При отказе от ухода черновик и URL редактора сохраняются без бесконечного накопления history entries. Изменения в `disclosure.js` ограничить этим жизненным циклом.

Черновики остаются в текущей памяти страницы. Закрытие вкладки, выгрузка процесса Android и offline-восстановление не входят в гарантии 3.2.

## 6. Viewport, safe areas, клавиатура и фокус

- Расширить viewport meta параметрами `viewport-fit=cover, interactive-widget=resizes-content`, сохранив `width=device-width, initial-scale=1`. Не устанавливать `user-scalable=no` или ограничивающий maximum-scale.
- Базовые размеры: `100vh` как fallback и `100dvh` для актуальной высоты. Insets — через `env(safe-area-inset-*, 0px)`. Нижний отступ контента и scroll-padding включают реальную высоту нижней панели с её safe area; inset не прибавляется дважды.
- Native dialog редактора: непрокручиваемые header/footer и единственный flex-body с `min-height:0; overflow-y:auto`. Сохранение не уезжает в конец длинной формы.
- Сначала использовать поддерживаемый Chrome режим изменения viewport. Сам по себе `100dvh` не является достаточной защитой от экранной клавиатуры: в стандартном режиме Chrome Android может уменьшать только visual viewport. [Chrome: viewport и клавиатура](https://developer.chrome.com/blog/viewport-resize-behavior).
- `VisualViewport` не вводить как обязательный второй источник геометрии. Только если проверка OnePlus выявит проблему, добавить небольшой ограниченный адаптер для открытого редактора: обновление CSS-высоты/смещения, без `P.refresh()`, без угадывания клавиатуры по произвольному порогу пикселей и без противодействия pinch zoom. [MDN: VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport).
- Safe areas относятся к вырезам и системным краям, а не заменяют расчёт доступного места при клавиатуре. [MDN: env()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/env).
- При открытии существующей карточки на mobile фокусировать заголовок/контейнер с `preventScroll`, чтобы просмотр не открывал клавиатуру автоматически. Desktop сохраняет удобный фокус ввода. При переходе к полю и ошибке валидации прокручивать только нужную область формы.
- При закрытии восстанавливать доступный исходный элемент и положение страницы; если исходная строка исчезла после сохранения — ближайший осмысленный контейнер. Resize не меняет фокус.
- Не применять глобальное `overflow-x:hidden` для маскировки дефектов. На desktop блокировка фоновой прокрутки при dialog не должна сдвигать страницу; переиспользовать текущую блокировку, уточнив восстановление при вложенных окнах.

## 8. Последовательность реализации после утверждения

1. **Оболочка и desktop:** согласовать единые CSS-параметры, распределить вкладки, подключить responsive styles. Проверка 1024/1440 и embedded manifest.
2. **Мобильная навигация:** та же nav снизу, компактный header/STG, корректные отступы и доступный Бюджет. Проверка всех маршрутов, включая settings и прямые ссылки.
3. **Оболочка редакторов:** сначала задача, затем оба пути проекта; общие body/footer, фокус, safe areas. Сначала проверить resize с заполненной формой, затем сохранение и конфликт.
4. **История и клавиатура:** единый путь guarded close, Back/Forward, вложенный dialog, Android-клавиатура, восстановление прокрутки. VisualViewport fallback — только при доказанной необходимости.
5. **Интеграция Live Sync и приёмка:** положение уведомлений, сохранение DOM/черновиков, отсутствие лишних запросов при resize, целевой STANDARD и скриншоты.

Каждый подэтап заканчивается проверкой своей области. Уже прошедшие неизменённые проверки не запускаются повторно без причины.

## 9. Риски и контроль

| Риск | Контроль |

## 10. Проверки реализации — STANDARD

На текущем шаге тесты не запускались: выполнено чтение исходников и документации браузера.

При реализации:

- Полный быстрый `npm test`; целевые тесты navigation/editor/history helpers.
- Новый Playwright smoke по ширинам **320, 360, 390, 412, 480, 768, 1024, 1440**: оба модуля, editor, длинные названия, границы кнопок, отсутствие горизонтальной прокрутки документа, отсутствие перекрытия последнего элемента нижней панелью. ## 11. Отложенные этапы и зафиксированный бэклог

### Stage 3.3 — задачи, проекты, внимание, настройки, архив

Полная мобильная компоновка этих экранов, включая следующие согласованные изменения:

**Server Manager:** PROD, STG и local HEAD показывают короткий SHA, название точного коммита, дату/время по Москве до секунд, Git-связь с local HEAD и локальные изменения. Метаданные брать из точного Git-объекта; недоступность явно обозначать. Последний известный `origin/main` можно показывать отдельно как локально известную ссылку: без автоматического fetch/дополнительной сети, без подмены push-time временем коммита и без сравнения актуальности только по датам. Перед каждым пунктом — заметный заголовок с номером, действием и целью, до SSH/sudo. Исправить подписи этапов, в частности скачивание бэкапа. Сохранить clear, адаптивность, цвета, опасные подтверждения и STG по умолчанию. В Stage 3.2 административный код не трогать.

**Подзадачи:** отступ и отдельный символ в раскрытой группе; действительный родитель и экземпляр определяются по ID. Не связывать визуально с одноимённым чужим родителем и не нарушать хронологию.

**Группировка (заменить текущую модель только в 3.3):**

| Секция | Ключ внешней группы |
|---|---|
| Сегодня | Серия + день, несколько экземпляров допустимы |
| Завтра | Серия + день, несколько экземпляров допустимы |
| На этой неделе | Конкретный экземпляр + отдельная дата |
| В ближайшие 30 дней | Конкретный экземпляр + секция; задачи разных дат объединяются в карточку |
| Позже | Конкретный экземпляр + секция, как в ближайших 30 днях |
| Без даты | Конкретный экземпляр |
| Просроченные | Текущая семантика; изменения только после отдельного согласования |

Многодневные карточки сортировать по ближайшей активной задаче; внутри — разделение по датам и время по возрастанию. Сохранить фактический прогресс, ID, фильтры, раскрытие и Live Sync. Плоский список остаётся строго хронологическим. Обычные независимые проекты с совпадающими названиями не объединять.
